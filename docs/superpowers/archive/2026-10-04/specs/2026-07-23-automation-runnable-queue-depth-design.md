# 自动工作流可执行队列深度设计

## 问题

当前队列维护规则允许新增 1–3 张任务卡，但没有定义维护完成后的可执行队列深度。责任方新增 1 张卡后已经满足规则，下一小时又会优先执行这张唯一合法候选，形成“补 1 张、执行 1 张”的交替循环。

## 方案比较

1. 每次固定新增 2–3 张。实现直接，但权威来源不足时会诱导责任方制造任务。
2. 维护结束时尽量保留至少 2 张可执行卡，单次最多新增 3 张；不足时只补能够安全形成的卡并记录原因。该方案兼顾吞吐与事实约束。
3. 每次业务执行后顺带维护队列。会扩大普通执行职责，并破坏“每轮一个责任方”的薄路由边界。

采用方案 2。

## 规则

- 三类执行、复审和外部 AI 候选均为空时，队列维护先提升满足条件的完整 backlog 卡。
- 队列维护结束时，若权威来源足够，当前队列必须至少包含 2 张合法可执行卡。
- 单次维护最多新增 3 张卡；已有可执行卡计入深度，但完成、阻塞、冻结、待决定、执行器不可用或与人工改动冲突的卡不计入。
- 如果权威来源只能形成 1 张或 0 张合法卡，责任方不得制造任务；应补入所有能够安全形成的卡，并在提交结果中记录不足原因。
- 本轮仍只维护任务事实，不执行新增业务任务；控制器、租约和固定调用器职责不变。

## 修改范围

- 更新 `开发管理/自动工作流规则.txt` 和 `开发管理/状态与建议维护规则.txt` 的队列补充后置条件。
- 更新 `tools/check-automation-workflow.ps1` 与 `tools/test-check-automation-workflow.ps1`，让静态契约检查能够阻止规则退化回仅有 `1–3` 的模糊范围。
- 不修改控制器选择逻辑、租约、CLI session、队列数据结构或自动化配置。

## 验证

1. 先让新增契约测试因缺少“至少 2 张合法可执行卡”的规则而失败。
2. 修改规则后运行 `tools/test-check-automation-workflow.ps1`，确认契约测试通过。
3. 运行 `tools/check-automation-workflow.ps1`、相关文本检查和 Git 空白检查。
