## 1. 背景与结论

最初需求只有一个每小时触发入口，每轮从以下工作中选择一项：

1. 执行全局优先级最高的合法任务。
2. 审核其他 AI 已完成且待复审的任务。
3. 调用 Claude/DeepSeek 执行其主责范围内的最高优先级任务。
4. 三类工作均无合法候选时，根据项目现状补充任务。
5. 执行者遇到必须由负责人决定的问题时，通过飞书通知；收到回复后继续原任务。

旧 WF1、WF2、WF3、WF4 分别承担队列维护、Codex `1`、Claude/DeepSeek `1` 和 Codex `2`。把四个独立定时器合并为一个每小时调度入口，正确解决了多写入者、共享锁竞争、空转预检和全局优先级失真；但后续实现把“统一调度”扩张成“统一执行协议”，引入了十五个 action、逐 action request JSON、发现网关、机器任务注册表、逐文件 manifest、决定迁移状态机和中央验证/提交。当前 `tools/hourly-controller-v2/` 已达到 25 个文件、约 6,315 行，且真实自动化仍不能稳定走完 plan-only 清单提交。

本设计保留“一个每小时调度入口”和已经验证有效的 Git/飞书安全组件，删除统一执行协议。最终结构是：

```text
一个自动化
一份薄路由提示
一份短规则
一个最小租约/恢复工具
一个无状态 Codex CLI session 边界
现有 Git 安全脚本
现有飞书桥
```

生产 `tzg-hourly-controller` 在新设计完成、合并并通过受控真实运行前保持 `PAUSED`。

## 2. 第一硬原则：单一责任方端到端完成

一个任务只有一个责任方。责任方从读取任务、实施、验证、更新队列或交接到创建本地提交全部端到端完成。其他流程不得在中间接管、补做、代验证或代提交。

| 角色 | 唯一职责 | 明确不做 |
|------|----------|----------|
| 每小时调度器 | 汇总候选、选择一个、取得/释放租约、启动对应流程、记录最终类别 | 不实施、不验证、不提交、不复审 |
| Codex 执行 | 按纯 `1` 完成任务、验证、闭环队列并提交 | 不处理复审对象 |
| Codex 复审 | 按纯 `2` 审核目标 commit、形成结论、更新审核事实并提交 | 不提前介入外部 AI 的实施或提交 |
| Claude/DeepSeek | 完成自己的任务、验证、自行提交、写交接和 commit SHA | 不等待 Codex 代验证或代提交 |
| 队列维护 | 检查现状、补充/修正任务、验证并提交队列修改 | 不顺带执行任务或复审 |
| 飞书桥 | 原样传递问题和回复、定位原任务恢复指针 | 不解释回复、不改任务范围、不代替执行者 |

流程之间只传递稳定结果：

- 调度器到执行者：任务 ID 和路由类型。
- 外部 AI 到复审：commit SHA 和交接记录。
- 飞书到原任务：负责人原始回复。
- 执行者到调度器：成功、失败、等待决策或阻塞。

半成品修改不得转交另一责任方继续 stage、验证或提交。后续正式复审按审核规则做独立验证，属于复审本身，不是执行阶段的重复收尾。

## 3. 总体架构与每小时流程

生产环境只保留一个启用的 `TZG Hourly Controller`。旧 WF1、WF3、WF4 保持暂停，在新流程稳定后归档其配置；它们不能被另一个自动化按 ID 调用，也不作为运行时处理器。

自动化提示不创建四份新处理器提示。当前 Codex 任务选择路由后，调度器通过一个无状态 PowerShell 边界启动 CLI-native Codex session，再由该 session 进入已有规则入口。不得把 Codex Desktop、VS Code 或 subagent rollout ID 当作 npm Codex CLI session ID。四种路由继续使用：

- Codex 普通执行：`开发管理/AI协作规则.txt` 的纯 `1`。
- Codex 复审：`开发管理/审核入口.txt` 和纯 `2`。
- 外部 AI 执行：`开发管理/DeepSeek工作提示词.txt` 与 Claude/DeepSeek 主责边界。
- 队列补充：`开发管理/状态与建议维护规则.txt`、当前队列和相关 backlog。

每轮流程固定为：

```text
每小时触发
  -> 读取当前队列、审核/交接入口和必要项目状态
  -> 汇总 Codex 执行、复审、外部 AI 三类合法候选
  -> 按统一项目优先级选择一个候选
  -> 没有合法工作候选时才选择任务补充
  -> 取得单写入租约
  -> Codex 路由创建 CLI-native session；其他路由启动对应责任方
  -> 当前责任方按既有入口端到端执行、验证并提交
  -> 释放租约并记录简短结果
```

候选选择本身是只读操作。整点轮次与飞书即时续跑可能同时选择，但只有取得租约的一方可以开始项目写入；未取得者落盘排队或结束，不启动第二个写入者。

## 4. 候选资格与统一优先级

### 4.1 候选来源

- Codex 执行：当前任务队列中状态为待处理、主责属于 Codex/ChatGPT5.5 的任务。
- Codex 复审：审核入口、未通过审核清单和 AI 交接中已具备目标 commit/diff 与必要材料的对象。
- 外部 AI 执行：当前队列中状态为待处理、非复审，且主责明确属于 DeepSeek V4 Pro、Claude Code 或 Claude/DeepSeek 的任务。

### 4.2 合法条件

候选必须同时满足：

- 状态允许执行或复审。
- 前置依赖已完成；外部 AI 前置产物要求复审通过时，未通过前不满足依赖。
- 没有尚未回复的负责人决策。
- 不违反内容冻结、领域规范或模型主责边界。
- 任务卡给出足以判断与人工改动是否冲突的文件或目录范围。
- 所需执行器当前可用；外部 CLI 只在真实选中外部候选后预检。

任务范围与人工改动明显冲突时跳过该候选并继续扫描。当前责任方开始修改前仍必须调用 workspace guard，以实际 Git 基线作为最终边界判断。

### 4.3 全局排序

三类候选统一排序，不设置固定“复审优先”或“Codex 优先”：

1. 项目明确标注的 P0、P1、P2 等优先级。
2. 已收到负责人回复、需要续跑的原任务。
3. 能解除更多高优先级任务阻塞的候选。
4. 同等条件下等待时间更长的候选。
5. 最后以稳定任务 ID 排序，保证结果可重复。

复审对象继承被审核任务及其被阻塞下游的最高优先级。任何提示、规则或工具不得硬编码具体 TQ/HANDOFF 编号。

## 5. 各路由的端到端责任

### 5.1 Codex 执行

调度器选中 Codex 普通执行后，不在当前 Codex Desktop 自动化线程内实施，也不派生 Desktop subagent 作为可恢复责任方。它调用唯一的 PowerShell CLI session 边界，以 `codex exec` 创建来源为 `exec` 的持久 session，并把任务 ID、`runId`、仓库根和纯 `1` 入口作为首次输入。该 CLI session 是从读取任务卡到提交的唯一责任方。

当前 CLI-native Codex 任务按纯 `1` 读取任务卡和必要事实源，修改、运行最小充分验证、更新队列/归档并创建一个路径限定本地提交。自产工作完成必要验证后直接闭环，不进入额外复审队列。PowerShell 边界不读取项目事实、不解释模型输出、不验证、不提交，只负责启动、提取 CLI session ID、转发固定进度和返回进程结果。

### 5.2 Codex 复审

调度器选中 Codex 复审后，使用与普通执行相同的 PowerShell Start 边界创建独立 CLI-native session，但首次输入改为审核入口、纯 `2` 和目标稳定 ID。该 Codex 任务读取审核入口、目标 commit/diff 和必要事实源，独立验证并给出通过、部分通过或不通过。复审者自行更新交接、未通过清单、归档或队列，并提交自己的审核结果；不在外部 AI 提交前介入。

### 5.3 Claude/DeepSeek 执行

调度器只传入已选任务 ID 与路由。外部 AI 自己：

1. 按项目规则确认实际身份和主责授权。
2. 读取任务卡及必要事实源。
3. 调用 workspace guard 记录基线并确认范围。
4. 实施修改并运行任务直接要求的最小充分验证。
5. 标记“已修改/未审核”并写 `开发管理/AI合作沟通.txt`。
6. 调用 whitespace/finalizer，自行创建路径限定的未审核本地提交。
7. 在交接中登记真实 commit SHA、已验证、未验证和残留风险。

外层 Codex 不阅读和判断业务修改、不重跑检查、不代 stage/commit。调度结束只接受外部 AI 的最终状态与 commit SHA；正式业务判断留给后续 Codex 复审。

现有 `AGENTS.md`、`开发管理/AI协作规则.txt` 和 `开发管理/DeepSeek工作提示词.txt` 中“外部 AI 子进程不得 stage/commit、由控制器代提交”的规则必须同步改为上述边界。

### 5.4 队列补充

只有三类工作都没有合法候选时，本小时才进入队列维护。调度器通过同一 PowerShell Start 边界创建 CLI-native Codex 维护 session，并只传入状态维护入口和本轮 `runId`。维护者自行检查、修改、验证和提交，不在同一小时顺带执行新任务。

## 6. 写入隔离、验证与提交

继续保留并由当前责任方直接调用：

- `tools/automation-workspace-guard.ps1`
- `tools/automation-finalize-commit.ps1`
- `tools/check-pending-whitespace.ps1`

不新增中央验证/提交包装器。谁执行任务，谁调用 guard、领域检查、whitespace 和 finalizer；每项检查只调用一次。

责任方必须：

1. 在修改前记录 HEAD、staged、unstaged、untracked 和重命名/删除基线。
2. 不修改、stage 或提交运行前人工改动。
3. 只处理任务卡授权范围；范围不明时不靠猜测执行。
4. 按 `AGENTS.md` 和领域规则运行直接相关的最小充分验证。
5. 使用路径限定提交；不 stash、reset、checkout、clean 或自动推送。
6. 提交后证明运行前人工差异的路径、内容和 staged 状态保持不变。

验证失败由同一责任方修复，只重跑受影响检查。HEAD、基线或范围失败时不创建部分提交，不由调度器接手。

## 7. 决策通知与无 token 等待

### 7.1 修改前决策

责任方应在修改前完成必要事实读取并尽量一次性识别需要负责人决定的问题。尚未修改项目时：

1. 责任方形成原始问题与选项。
2. 飞书桥原样发送，并保存私有恢复指针。
3. 释放写入租约，当前模型轮次和外部 CLI 进程结束。
4. 其他不相关任务可以继续按小时运行。
5. 回复到达后立即尝试恢复原任务。

### 7.2 Codex 与外部 AI 恢复

- Codex 任务从首次运行起就是 npm Codex CLI 创建的 `exec` session。首次启动使用 `codex exec --json -`，从 CLI 事件中提取并保存原 `sessionId`；回复到达后只调用 `codex exec resume --json <sessionId> -` 并通过 stdin 传入负责人原文。
- `tools/codex-cli-session.ps1` 是 Start/Resume 共用的唯一 Codex 进程边界。它由 PowerShell 7 解析本机 `codex` 命令，不硬编码 npm 安装目录，不转换或修补 rollout 文件，也不接受 Desktop/VS Code/subagent session 作为自动恢复输入。
- 飞书 Node relay 只消费签名回复、取得租约并通过 `pwsh -NoProfile -ExecutionPolicy Bypass -File tools/codex-cli-session.ps1` 调用 Resume；Node 不直接启动 `codex`、`codex.cmd` 或 npm 内部 `codex.js`。
- Claude/DeepSeek 调用时使用私有 `sessionId`；外部 AI 返回 `needs_decision` 后退出。回复到达时中继只调用 `claude --resume <sessionId>` 并原样传入回复。

Claude CLI 已确认支持 `--session-id`、`--resume` 和 `--continue`。外部 AI 不能自行接收飞书事件，因此调度器作为通信中继是唯一必要例外；它不解释回复、不重新规划、不验证或提交外部 AI 工作。

### 7.3 锁占用与 token

回复到达但租约被占用时：

1. 将回复引用和原任务恢复指针写入私有待续跑队列。
2. 当前对话立即结束，不 sleep、不轮询、不保持模型或 Claude CLI 进程。
3. 当前写入任务释放租约时只检查一次待续跑队列并触发原任务。
4. 异常未释放时，由下一个小时轮次在租约过期后优先恢复。

等待期间不消耗模型 token；只有真正启动续跑轮次时才重新产生模型调用。

### 7.4 修改后意外决策

如果责任方已经产生未提交修改，则不切换到其他任务：

- 保存任务 ID、责任方会话和实际变化路径。
- 当前任务成为唯一可恢复对象，整点调度不选择其他任务。
- 收到回复后恢复同一责任方继续验证和提交。
- 不把半成品交给另一 AI，也不自动清理。

### 7.5 第一期进度可见性与飞书 Tasks 后置

第一期只在 `TZG Hourly Controller` 当前自动化运行任务的终端显示进度。调度器输出已选择任务；PowerShell CLI 边界根据实际 CLI 事件输出 `session 已启动`、`正在执行`；调度器再根据既有 runtime 和进程结果输出 `等待决定`、`已完成` 或安全的失败原因。不得从命令名称猜测“正在验证”或“正在提交”，不得输出原始模型 JSON、prompt、回复正文、provider 标识或 secret。

进度不引入项目文件、数据库、阶段状态机或新的长期 runtime 字段。结构化结果继续使用现有 `lastResult` 和 recovery；终端进度只是同一事实的可读投影。飞书回复触发的隐藏后台 Resume 不能回写已经结束的旧自动化终端，第一期只在现有私有 runtime 记录该续跑的最终结果，下一次状态读取可见。

飞书任务模块属于独立第二期。只有 CLI-native Start/Resume、一次真实任务和进度输出稳定后，才另行设计 Task v2 权限、任务清单、任务 GUID 映射和更新频率。第一期不调用飞书 Tasks API，不新增任务清单配置，也不为未来集成预埋字段。

## 8. 失败、恢复与自动暂停

- 修改前失败：释放租约，下一轮重新比较所有候选。
- 修改后失败：下一轮只允许原责任方恢复同一任务。
- 验证失败：原责任方修复并重跑受影响检查。
- 提交失败：原责任方恢复提交步骤，不重新实施任务。
- 正常没有候选：进入任务补充；无法产生合法新任务时干净结束。

存在候选但完整扫描后全部因冲突、依赖、权限或工具故障阻塞时，记录阻塞集合指纹。相同或等价阻塞连续出现两轮后：

1. 通过 Codex 自动化管理能力将 `tzg-hourly-controller` 设为 `PAUSED`。
2. 飞书发送阻塞候选和原因摘要。
3. 保存最小恢复信息，等待负责人手动恢复。

任何成功执行、成功补充任务或阻塞集合实质变化都重置计数。存在任务自有未提交修改时不等待两轮：停止普通调度，只允许原任务通过回复或人工指令恢复。

## 9. 任务补充与项目状态

### 9.1 补充顺序

1. 读取当前任务队列和相关分线 backlog。
2. 优先提升已有且满足依赖、主责和冻结规则的任务。
3. 没有合法 backlog 时读取项目当前状态和下一步建议。
4. 根据真实缺口创建 1–3 个最小、可验证、可提交的新任务。
5. 更新队列、运行必要文本检查并自行提交。
6. 新任务从下一小时开始参与全局优先级竞争。

任务卡只需保存任务 ID、标题、优先级、主责、状态、依赖、大致文件/目录范围、完成条件和必要验证；不维护重复的机器 JSON 注册表，也不预列全部潜在文件。

### 9.2 状态闭环

- Codex 执行在自己的业务提交中更新队列和必要归档。
- 外部 AI 在自己的未审核提交中把任务标为待复审、写交接和 commit SHA。
- Codex 复审通过后关闭任务和交接；不通过则更新未通过清单。
- 队列维护只维护任务事实。
- 调度器不修改项目任务状态，只记录私有运行结果。

`开发管理/自动工作流状态.txt` 不再记录每小时锁、检查点或空转结果，只保留负责人需要看到的长期阻塞、最近有效成果和迁移事实。普通轨迹写自动化 memory 或私有状态，不为无任务制造提交。

## 10. 最小租约与私有状态

只保留一个小型本机租约/恢复工具，使用用户级 ACL 受限目录和原子写入。它只管理：

- 获取、释放和过期恢复单写入租约。
- 当前 `runId`、任务 ID、责任方类型和启动时间。
- 任务自有未提交修改的最小恢复指针。
- 等待决定的 Codex CLI `sessionId` 或 Claude `sessionId`。
- 待续跑队列。
- 连续全部阻塞次数与阻塞集合指纹。
- 最近一次运行结果。

它不选题、不读取项目内容、不运行验证、不 stage/commit、不解释飞书回复、不调用 AI，也不维护业务阶段枚举。调用使用固定参数，不创建逐 action request JSON。

## 11. TQ-057 业务事实归位

## 15. 验收标准

- 生产环境只有一个启用的写入型自动化。
- 每小时最多完成一个执行、复审、外部 AI 或任务补充工作。
- 三类候选按统一项目优先级选择，类型不形成固定优先顺序。
- 没有合法工作候选时才补充任务，并优先使用现有 backlog。
- 每个责任方自行修改、验证、更新状态和提交；调度器不代做。
- Codex 自动化责任方从首次启动起就是来源为 `exec` 的 CLI session；飞书回复只恢复该原 CLI session，不尝试用 npm CLI 打开 Desktop/VS Code/subagent rollout。
- 外部 AI 自行创建未审核提交，该 commit 可直接进入 Codex 复审。
- 安全检查在执行阶段只运行一次，正式复审按审核规则独立取证。
- 决策等待不保持模型/CLI 进程，不轮询且不持续消耗 token。
- 当前自动化运行任务只显示由真实事件支持的固定进度，不显示原始模型 JSON 或敏感标识；后台续跑的最终结果写入既有私有 runtime。
- Claude/DeepSeek 决策通过原 session 恢复，调度器只原样中继。
- 运行前人工 staged、unstaged、untracked 和内容差异保持不变。
- 连续两轮全部阻塞会自动暂停并通过飞书通知。
- 通用提示、规则和工具没有 TQ-057 或其他具体任务硬编码。
- TQ-057 五项决定完整归位到正式任务卡，不重问、不丢失。
- manifest、发现网关、机器任务注册表和旧复杂状态机退出活动路径。

## 16. 明确不采用的方案

- 不恢复四个独立定时写入自动化：会重新引入抢锁、空转和全局优先级失真。
- 不创建“调度器 + 四个不可真实调用的 Codex 处理器”：Codex 自动化没有按 ID 调用暂停自动化的能力，四个处理器只会变成重复提示。
- 不让生产自动化长期运行在独立 worktree：会引入分支同步、自动合并、队列漂移和冲突恢复；生产仍在主工作区按路径避让人工改动。
- 不保留中央 manifest、发现和验证协议：确定性安全交给现有脚本，业务工作由当前责任方端到端完成。
- 不修补、转换或复制 Codex Desktop rollout 供 npm CLI 恢复；现有 TQ-057 只由原 Desktop 任务人工续跑。
- 第一期不接入飞书 Tasks、不预建任务 GUID 映射、进度数据库或新阶段状态机；稳定后另开第二期规格。
