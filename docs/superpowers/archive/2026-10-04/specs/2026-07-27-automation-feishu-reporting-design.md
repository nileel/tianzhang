# 日报、周报与自动化任务飞书通知设计

## 1. 背景

现有 `tzg-daily-automation-briefing` 与 `tzg-weekly-project-summary` 都会在 Codex 中生成只读报告，但不会把报告发送到飞书。项目已经有一条健康的飞书决策桥，具备私有配置、收件人绑定、连接健康检查、消息发送、幂等存储和脱敏结果；现有发送入口只支持需要回复的决策卡片。

首次周报还暴露出事实核验问题：

- 周报把正式 `AdventureScene` 的环境档案绑定列为风险，但 `U-2_5D-01D` 已归档，场景与运行时代码已有显式绑定。
- 周报把一级属性重分配列为未锁定，但 `N-FPD-GROWTH-01` 已由 BattleSim 锁定；`开发管理/设计-当前状态.txt` 的风险条目没有同步。
- 冻结范围、设计边界、已有 backlog 任务和真正需要负责人决定的事项被混写在同一个风险段。

负责人已确认：

1. Codex 与飞书双端保留。
2. 飞书发送完整日报和完整周报，不发送缩略版。
3. 复用现有飞书桥，不建立第二套计划任务或调度器。
4. 每个有意义的自动化终态都发送飞书通知；无业务变化的小时轮询和普通队列维护不发送。
5. 完成或待复审任务使用五段式通知：任务目标、本次完成、实际影响、验证结果、后续关系。

## 2. 目标

- 日报、周报生成后，将与 Codex 中相同的完整正文发送给当前已配对的飞书收件人。
- 自动化任务到达有意义的终态时，立即发送足以理解任务内容的结构化通知。
- 不为任务通知额外启动总结模型；摘要由原责任方在同一轮收尾时形成。
- 修正周报风险核验，使已完成事项、证据冲突、冻结任务、阻塞任务、待决定事项、缺少任务和纯设计边界得到不同处理。
- 复用现有飞书私有配置、健康检查、传输、幂等和脱敏边界，不改变决策回复协议。

## 3. 非目标

- 不替换 Codex 内的日报、周报或任务终态输出。
- 不新增飞书机器人、Webhook、收件人配置、Windows 计划任务或第二套自动化调度。
- 不让日报、周报执行项目任务、领域验证、队列维护或事实源修复。
- 不把飞书投递结果写入项目任务状态，不因通知失败回滚业务提交。
- 不把模型原始回复、隐藏推理、私有配置、provider 标识或收件人原文发送或提交到仓库。
- 不修改飞书决策卡片、回复绑定、回调验签、回复消费和首个有效回复胜出协议。

## 4. 总体架构

### 4.1 单一飞书传输，三类通知

在现有 `tools/feishu-decision-bridge/` 中增加独立的普通通知入口，支持：

- `task_outcome`
- `daily_report`
- `weekly_report`

普通通知复用：

- `parsePrivateConfig`
- `readHealthSnapshot`
- `createLarkTransport`
- 用户级私有幂等存储
- 现有错误脱敏规则

普通通知不得调用决策卡构造器，不得创建 `pending-bindings.json`，不得修改决定恢复请求，也不得进入回复 inbox。

### 4.2 规范与实时配置

仓库中的以下文件继续作为 prompt 事实源：

- `开发管理/自动工作流控制器提示词.txt`
- `开发管理/自动化简报提示词.txt`
- `开发管理/每周项目总结提示词.txt`

实现完成后，只通过 Codex 自动化管理能力同步三个现有自动化的完整配置；不得直接编辑用户级 `automation.toml`。同步时保留现有 ID、名称、schedule、workdir、model、status 和无关配置。

### 4.3 通知触发责任边界

- Codex 业务任务继续由 `tools/invoke-codex-responsibility.ps1` 在已核验终态关闭后发送；实时控制器 prompt 不重复发送。
- 外部 AI 继续由每小时控制器按现有 identity、session、双提交、元数据、任务卡与工作区门禁关闭终态；`RecordResult` 与 `Release` 成功后，控制器调用现有普通通知脚本一次。该行为由实时控制器 prompt 约束，不新增 external closeout wrapper。
- 日报与周报仍由各自实时 prompt 在最终正文确定后调用普通通知脚本。当前 automation schema 没有可用的 post-run hook，脚本不能在不接管整次报告模型调用的情况下取得最终正文。
- 不新增 external closeout wrapper、报告 runner、Windows 计划任务、第二调度器或 lease 层通知钩子；`tools/hourly-automation-lease.ps1` 保持只管理控制面状态。

### 4.4 自动化任务通知摘要契约

不新增第二份提交元数据协议。继续使用现有 `Result`、`Impact`、`Verify` 三行，但对未来自动化业务提交收紧为以下单行结构：

```text
Result: 问题=<原问题>；完成=<具体交付>
Impact: 影响=<实际行为变化>；边界=<明确未涉及范围>
Verify: 验证=<关键检查与结果>；后续=<解锁项、剩余依赖或下一状态>
```

约束：

- 六个子字段都必须存在且非空。
- 内容必须是可由任务卡、实际提交、终态投影和已执行验证支持的事实。
- 不得填入私有标识、provider 信息、收件人、模型隐藏推理或未经验证的业务结论。
- 每个子字段使用有界单行文本；不得以文件清单代替行为说明。
- `边界` 必须说明本任务明确没有完成的相邻范围，避免把数据契约写成玩法已实现。
- `后续` 必须说明解锁、复审、决定、残留依赖或没有直接后续，不得自行重排队列。

原责任方在同一任务轮次内形成这些字段，不新增模型调用。预计只增加少量收尾输出 Token，飞书 API 调用不消耗模型 Token。

## 5. 数据流

### 5.1 Codex 业务任务

1. 固定调用器启动已选中的同一任务。
2. 责任方实施、验证，并通过现有 finalizer 创建路径限定提交。
3. 固定调用器核验：
   - Automation、Task、State、Result、Impact、Verify；
   - 六个通知子字段；
   - 唯一提交形状；
   - 工作区无新增残留；
   - 同一任务卡通过 `CodexClosedOrNonReady`。
4. 固定调用器执行既有 `RecordResult` 与 `Release`。
5. 业务终态已经关闭后，通知适配器读取已核验提交元数据、任务标题、终态和提交 SHA，构造五段式飞书卡片。
6. 发送结果只影响通知状态，不改变业务终态。

### 5.2 外部业务任务

1. 外部责任方继续创建 `businessCommit` 和 `handoffCommit`。
2. 控制器先核验 identity、session、提交父子关系、Automation 元数据、handoff 边界、工作区与 `ExternalPendingReview`。
3. 控制器完成既有 `RecordResult` 与 `Release` 后，使用已核验 `businessCommit` 的结构化字段发送 `pending_review` 通知。
4. 外部终态无效且没有新增残留时，控制器记录 `failed`、释放租约并发送一次无提交失败通知；存在新增未提交路径时保留现场和租约，不发送已关闭终态通知。
5. 通知明确说明“等待 Codex 复审”，不得把外部完成写成审核通过。

### 5.3 无提交终态

`waiting_decision`、`waiting_reply`、`blocked` 和 `failed` 可能没有业务提交。此时不调用模型补写摘要，只使用：

- 任务 ID 与任务卡标题；
- 任务卡当前 `stateReason`；
- 控制器稳定 category / detailCode；
- recovery 是否存在、是否有未提交路径；
- 已知的下一人工动作。

这类通知必须明确写“未形成已核验业务提交”，不得伪造“本次完成”或领域验证结论。

### 5.4 日报与周报

1. 自动化先按各自时间窗完成事实核验，形成最终正文。
2. 正文确定后调用普通通知入口一次。
3. 无论飞书成功或失败，Codex 都输出同一份完整正文。
4. 飞书失败时，Codex 正文末尾追加一条脱敏投递状态；报告本身仍视为已生成。
5. 只有完整报告已经形成时才推进各自 memory 游标；飞书失败不回退报告游标。

## 6. 周报准确性规则

### 6.1 成果与当前状态分离

- 时间窗成果以对应提交时的任务事实和权威领域证据为准。
- 当前状态以运行结束时的队列、活跃任务卡、归档、相关 backlog 和权威领域事实源为准。
- 两个时间点不同必须显式标注，不得把后续完成倒写成窗口内成果。

### 6.2 风险候选交叉核验

任何拟进入“风险与决定”的事项都必须先分类：

1. `ready`：当前执行队列中的活跃任务。
2. `blocked`：已有任务且缺少明确前置。
3. `frozen`：已有任务但范围未授权。
4. `pending_decision` / `waiting_reply`：确实需要负责人输入。
5. `pending_review`：已有外部业务提交等待 Codex 复审。
6. `completed`：已有完成归档及相应领域证据。
7. `no_task`：没有任务卡、backlog 项或已批准实施入口。
8. `boundary_only`：只是现行禁止项或设计边界，并非异常或待执行任务。
9. `evidence_conflict`：摘要状态与任务归档、Git 或领域事实源冲突。

### 6.3 输出规则

- `completed` 不得列为当前风险。
- `boundary_only` 不得伪装成待办；只有负责人明确希望改变边界时才说明需要新任务与授权。
- `frozen` 只在阻塞当前固定队列、需要负责人授权或属于已确认近期重点时进入风险段。
- `evidence_conflict` 必须列为数据质量问题，说明冲突两侧和无法采用旧结论的原因；不得自行修复事实源。
- 每项风险或决定都说明对应任务 ID；没有任务时明确写 `no_task`。
- “风险”与“待决定”在同一固定章节内分组表达，不把正常冻结范围写成控制面异常。

## 7. 飞书卡片

### 7.1 任务终态卡片

成功或待复审卡片固定包含：

1. 任务目标
2. 本次完成
3. 实际影响与明确边界
4. 验证结果
5. 后续关系

页首显示任务 ID、标题和终态；页尾可显示短提交 SHA，不显示 provider 消息 ID、chat ID 或私有状态路径。

### 7.2 日报和周报卡片

- 标题分别为“天章日报 · YYYY-MM-DD”和“天章周报 · <Since>—<Until>”。
- 正文与 Codex 输出完全一致。
- 不增加按钮、输入框或回复提示。
- 使用保守的 Unicode code point 上限；日报、周报 prompt 同时限制正文长度，确保单卡可承载。
- 不截断正文。异常超长时飞书失败关闭，Codex 保留完整报告并说明未投递。

## 8. 幂等与私有状态

- `task_outcome` 幂等键由通知类型、TaskId、最终 category 和已核验 commit SHA 或稳定终态指纹构成。
- `daily_report` 与 `weekly_report` 幂等键由通知类型、automation ID 和 `windowUntil` 构成。
- provider uuid 从幂等键确定性派生；同一事件重放不得产生第二条消息。
- 用户级私有状态只保存幂等哈希、内容哈希、脱敏结果和时间，不保存报告正文、收件人原文或 provider 标识原文。
- `PROVIDER_OUTCOME_UNKNOWN` 不自动重试，避免重复发送。

## 9. 失败行为

- 飞书 `CHANNEL_UNAVAILABLE`、明确拒绝、未知结果、输入非法或超长都不得回滚业务提交、改变任务卡、重开租约或创建 recovery。
- 通知发生在业务终态关闭后；通知失败不得把成功任务改成 failed。
- 日报与周报的 Codex 副本始终输出。
- 失败类别保存为脱敏私有状态，并由下一次日报“异常”段报告本时间窗内未投递通知的数量和类型，不披露私有标识。
- 不增加自动重试队列、备用 Gmail、Webhook 或第二套消息服务。

## 10. 修改边界

预计只修改以下逻辑单元：

- `开发管理/自动化简报提示词.txt`
- `开发管理/每周项目总结提示词.txt`
- `开发管理/自动工作流规则.txt`
- `开发管理/自动工作流控制器提示词.txt`
- `开发管理/AI协作规则.txt` 中自动化 closeout 元数据约束
- `tools/invoke-codex-responsibility.ps1`
- 外部 closeout 的现有控制器约束与直接测试
- `tools/check-automation-workflow.ps1`
- `tools/feishu-decision-bridge/` 中新增的普通通知卡、发送入口和直接测试
- 与上述逻辑单元直接对应的 PowerShell / Node 测试

不得修改：

- 飞书私有配置内容
- 现有决策卡、回调、回复绑定和 inbox 协议
- `tools/hourly-automation-lease.ps1` schema
- automation schema 或新的报告 runner / post-run hook
- Git workspace guard、提交隔离和恢复语义
- 日报、周报的 schedule、workdir、model 或 ACTIVE 状态

## 11. 验证

### 11.1 Node 直接测试

- 三类通知输入契约与卡片正文。
- 六个任务摘要子字段的完整性、长度和安全字符。
- 普通通知不会创建决定绑定或回复请求。
- 健康不可用、provider 拒绝、未知结果和超长正文失败关闭。
- 三类幂等键稳定，重复调用不重复发送。
- 私有状态不保存正文和 provider 标识原文。
- 回归现有飞书发送、配对、回调、卡片输入和严格文本回复测试。

### 11.2 PowerShell 与工作流测试

- Codex 成功提交只有在通知摘要字段合法时才通过 closeout。
- 外部 `pending_review` 只在现有双提交与任务卡门禁通过后发送。
- 外部无残留失败由控制器关闭并通知；有残留失败保留现场、租约且不伪造关闭通知。
- 无提交终态不会伪造完成摘要。
- 通知失败不改变 `RecordResult`、`Release`、任务状态或退出类别。
- 日报、周报实时 prompt 与仓库规范一致。
- 周报夹具覆盖：
  - 完成归档与过时状态冲突；
  - Unity `src/` 当前行为推翻旧风险；
  - 冻结任务、无任务和纯边界的分类；
  - `pending_decision` 与普通 frozen 的区分。
- 运行自动工作流一致性检查、飞书桥完整 Node 回归、固定调用器直接测试、相关文本与差异检查。

### 11.3 生产金丝雀

全部离线测试通过并同步实时 prompt 后：

1. 只读确认飞书桥 `CONNECTED`。
2. 在实际发送前再次取得负责人确认。
3. 向现有已配对收件人发送一张明确标记为测试的任务结果卡。
4. 确认飞书收到完整五段正文且没有回复控件。
5. 不为金丝雀创建决定绑定、任务状态、项目提交或重复消息。

## 12. 上线顺序

1. 在隔离 worktree 实现普通通知入口与假传输测试。
2. 收紧未来业务提交的三行结构化元数据，并补固定调用器/外部 closeout 测试。
3. 更新日报、周报和周报风险交叉核验规则。
4. 运行全部直接测试与现有飞书协议回归。
5. 合并前重新调用 `Show`，确认 `lease=null`，并核对主工作区目标路径无 staged、unstaged、untracked 冲突。
6. 集成已验证提交。
7. 通过 Codex 自动化管理能力同步每小时控制器、日报和周报三个现有自动化的完整 prompt，保留所有无关配置。
8. 运行自动化一致性检查并只读确认飞书健康。
9. 负责人在发送动作前确认后执行生产金丝雀。

## 13. 停止条件

遇到以下任一情况停止实施并请求负责人决定：

- 必须修改或复制飞书私有配置。
- 必须改变决策回复、回调、配对或 inbox 协议。
- 必须新增计划任务、Webhook、备用消息渠道、通知重试队列或第二调度器。
- 无法在业务终态关闭后发送，通知失败会影响任务提交、租约或恢复。
- 外部任务无法在不信任模型原始正文的情况下得到已核验摘要。
- 实时自动化配置无法通过自动化管理能力同步，只能直接编辑 `automation.toml`。
- 单卡无法完整承载已批准长度范围，且唯一替代是静默截断。

## 14. 验收标准

- Codex 和飞书收到内容一致的完整日报与周报。
- 每个有意义的自动化终态都得到一次且仅一次通知；无业务变化轮询和普通队列维护不发送。
- 成功或待复审任务通知包含五段可理解内容，而非只有标题和状态。
- 任务通知不新增总结模型调用，飞书发送本身不消耗模型 Token。
- 周报不再把已有完成证据的事项写成当前风险；证据冲突被明确标为数据质量问题。
- 飞书通知失败不改变业务提交、任务卡、租约、恢复或报告游标。
- 普通通知不会创建决定绑定或进入回复链。
- 私有配置、收件人和 provider 标识不进入项目文件、提交、模型输出或飞书正文。
- 现有决策卡片、卡片自定义输入、严格文本回复、幂等和单实例桥接回归全部通过。
