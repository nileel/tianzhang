# 事件驱动任务队列与上下文优化设计

## 目标

在不删除现有安全边界的前提下，降低手动 `1` / `2` 与每小时自动工作流在选题阶段加载的无关上下文，并减少当前队列和分线 backlog 之间的完整任务卡重复。

本设计采用以下核心原则：

1. 当前队列是已经排好固定顺序的 `ready` 工作索引，不是每轮重新计算的候选池。
2. 队列只在任务进入、顺序变化、完成、阻塞、解阻塞、复审转换等事件发生时维护。
3. 正常自动化按固定顺序选择第一项当前可安全执行的工作；只有前项存在临时运行冲突时才继续检查下一项。
4. 每个进入近期调度或从近期调度转为非 `ready` 的任务使用一份独立权威任务卡；队列和 backlog 只保存短投影。
5. 恢复、租约、身份、主责、人工改动隔离、复审、外部双提交、全阻塞暂停和提交验证继续保留。

## 当前问题与基线

2026-07-24 检查得到：

- `开发管理/当前任务队列.txt` 为 19,661 字符。
- 当前队列包含 9 张完整任务卡，只有 `N-GROUP-02C` 状态为待处理。
- 非待处理卡占任务卡正文约 90.2%。
- 当前队列与分线 backlog 会重复保存同一任务的必读、范围、禁止项、验证、完成条件和停止条件。
- 现行每小时控制器还会在无 recovery 时汇总 Codex 执行、Codex 复审和外部 AI 三类候选，每轮重新按项目优先级、下游解锁量、等待时间和稳定 ID 排序。

此前的“短入口 + 分线任务列表”“按章节和符号最小读取”已经降低了事实源加载范围，但没有消除选题入口中的完整任务卡重复，也没有消除自动控制器每轮的多来源候选汇总。

## 非目标

- 不自动生成或自动改写队列。
- 不建立完整依赖图求解器。
- 不新增任务数据库、缓存、长期阶段状态机或兼容格式。
- 不改变现有 decision recovery 与 interruption recovery 的安全优先级。
- 不改变单写入租约、workspace guard、外部 AI 双提交或禁止自审边界。
- 不允许控制器启动的 Codex 自动化责任方创建 linked worktree、任务分支或在固定调用器传入的 `RepositoryRoot` 之外实施。
- 不同时执行整个 `开发管理/规则/`、`开发管理/当前/`、`开发管理/归档/` 目录迁移。
- 不修改 Unity、BattleSim、CSV、asset 或游戏设计事实。
- 不一次性把现有 71 项 backlog 全部拆成独立文件。

## 一、统一的有序当前队列

`开发管理/当前任务队列.txt` 保留现有路径，但改为整个自动工作流的短调度入口。文件只保存边界说明和有序表格：

```text
| ID | 路由 | 主责 | 优先级 | 领域 | 阶段 | 标题 | 任务卡 |
```

允许的路由：

- `codex_execute`
- `external_execute`
- `codex_review`

任务卡中的路由是调度标签，不替代固定调用器的现有参数契约：

- `codex_execute` 映射到 `tools/invoke-codex-responsibility.ps1 -Route Execution`
- `codex_review` 映射到 `tools/invoke-codex-responsibility.ps1 -Route Review`
- 空队列维护映射到 `-Route QueueMaintenance`
- decision / interruption recovery 继续映射到 `-Route Recovery`
- `external_execute` 继续调用现有外部 wrapper，不通过 Codex 固定调用器

队列契约：

1. 行顺序就是自动控制器的固定调度顺序。
2. 只有任务卡 `dispatchState=ready` 的工作可以进入。
3. 阻塞、冻结、待决定、等待回复和已完成工作不进入本表。
4. 优先级是插入或重排时的判断依据，不要求控制器每轮重新排序。
5. 当前队列不再保存完整任务正文、完成记录或历史争论。
6. 外部 AI 完成业务后，同一任务从 `external_execute` 转为 `codex_review`，无需建立第二份完整任务卡。

### 固定顺序的形成

任务进入、解除阻塞或负责人要求重排时，维护者一次性综合：

1. 用户当次明确顺序；
2. 项目 P 优先级；
3. 对高优先级下游的解锁价值；
4. 等待时间；
5. 稳定 ID。

维护者将任务插入确定位置后，普通自动化不再重复计算上述顺序。非 `ready` 任务恢复为 `ready` 时按同一规则重新插入，不因曾经阻塞而自动降级，也不自动排在新任务之后。

## 二、独立权威任务卡

任务卡位于：

```text
开发管理/任务卡/<ID>.txt
```

文件继续使用 `.txt`，顶部为 PowerShell 可原生解析的 JSON 元数据，正文保持中文可读格式：

```text
---TASK-META---
{
  "schemaVersion": 1,
  "id": "N-GROUP-02B",
  "title": "2v2 范围技能空间合法性与显式战场输入",
  "priority": "P3",
  "route": "codex_execute",
  "owner": "codex",
  "domain": "battlesim",
  "stage": "implementation",
  "dispatchState": "ready",
  "blockedBy": [],
  "stateReason": null,
  "expectedPaths": [
    "simulations/BattleSim/GameData.cs"
  ],
  "sourceBacklog": "开发管理/任务列表/数值与战斗任务.txt"
}
---TASK-BODY---

# N-GROUP-02B · 2v2 范围技能空间合法性与显式战场输入

## 来源与当前边界
记录任务来源、已锁定决定和当前实施边界。

## 必查范围
列出按章节、符号、实体或用途定位的事实源。

## 实施范围
记录本任务允许完成的结果。

## 禁止项
记录不得扩展的职责与数据边界。

## 验证
记录本任务要求的最小充分验证。

## 完成条件
记录可以关闭任务的可观察结果。

## 停止条件
记录必须停止实施并请求处理的条件。
```

元数据字段是 ID、标题、优先级、路由、主责、领域、阶段、调度状态、阻塞引用、状态原因、预期修改路径和来源 backlog 的唯一事实源。正文不得重复维护这些字段。

初始枚举：

- `owner`：`codex`、`deepseek`、`claude`
- `domain`：`unity`、`battlesim`、`data`、`content`、`management`、`automation`
- `stage`：`discovery`、`decision`、`design`、`implementation`、`migration`、`verification`
- `dispatchState`：`ready`、`blocked`、`frozen`、`pending_decision`、`waiting_reply`、`completed`

`expectedPaths` 只允许仓库相对精确路径，不允许通配符或目录级授权。验证命令继续保留在正文中；第一期不把它们转成可自动执行的数据。

## 三、非 ready 任务的存放与重新进入

各领域 `开发管理/任务列表/*.txt` 继续作为完整未完成任务视图。顶部短表保留：

```text
| ID | 优先级 | 主责 | 状态投影 | 阻塞于 | 摘要 | 任务卡 |
```

状态位置：

- `blocked`：独立任务卡 + 对应领域 backlog。
- `frozen`：独立任务卡 + 对应领域 backlog。
- `pending_decision`：独立任务卡 + 对应领域 backlog。
- `waiting_reply`：独立任务卡 + 对应领域 backlog；现有私有 recovery 另存 DecisionRequestPath 等安全恢复证据。
- `completed`：任务卡移入 `开发管理/任务归档/`，并从当前队列和未完成 backlog 移除。

backlog 状态是用于发现的短投影，独立任务卡是权威源。检查器负责验证二者一致。

非 `ready` 任务没有执行位置。普通阻塞解除或解冻时，按固定顺序规则重新插入当前队列。`waiting_reply` 保留现行 recovery 语义：回复到达后优先恢复原任务，不与普通 ready 队列竞争；无回复时仍按现行规则报告等待并结束本轮。

本契约只强制约束已经建立独立任务卡的任务。现有 backlog 中尚未卡片化的旧任务可以暂时保留当前短表和详细段落；它们被提升、解除阻塞或因状态事件需要修改时，再建立独立卡并删除对应的重复正文。检查器不得以缺少独立卡为由要求一次性迁移全部 backlog。

## 四、正常自动化调度

每小时控制器的正常路径为：

1. 调用租约工具 `Show`。
2. `pauseRequested=true` 时立即结束，不读取队列。
3. 存在 decision 或 interruption recovery 时继续走现行恢复规则，恢复优先于普通队列。
4. 无 recovery 时读取当前短队列。
5. 按行顺序检查，选择第一项当前可安全执行的工作。
6. 调用 `Acquire`，再按任务卡 `route` 启动唯一责任方。

控制器启动的 Codex 自动化责任方必须直接在固定调用器传入的 `RepositoryRoot` 当前分支工作。任务卡、队列状态、业务修改、验证结果和 `automation-finalize-commit.ps1` 生成的提交必须全部落在固定调用器观察的同一个 `RepositoryRoot/HEAD`。自动责任方不得调用 `using-git-worktrees`、`git worktree add`，不得创建或切换 linked worktree / 任务分支；其他分支存在提交不能作为任务完成结果。

### 执行前仍保留的必要判断

- 队列行与任务卡是否一致；
- 任务卡是否仍为 `dispatchState=ready`；
- 主责和 route 是否匹配；
- 指定执行器是否当前可用；
- 预期路径是否与人工 staged、unstaged 或 untracked 改动冲突；
- 单写入租约是否取得；
- 目标任务要求的依赖、授权、冻结和决定事实是否发生实质变化。

已经确认且相关事实未变化的稳定依赖不重复全量取证；修改前的实时路径冲突必须检查。

### 临时不可执行

执行器暂时不可用或预期路径与人工改动冲突属于临时运行条件：

1. 本轮跳过该行，不改变任务卡状态和队列顺序。
2. 继续按固定顺序检查下一项。
3. 下一轮仍从原顺序重新检查，避免临时跳过变成永久降级。
4. 所有队列项均因同一稳定 fingerprint 连续两轮不可执行时，继续使用现有逻辑暂停规则。

因此正常含义是“执行固定队列中第一项当前可安全执行的工作”，不是遇到队首临时问题就让所有工作停住。

### 明确的任务阻塞

未满足依赖、缺少授权、需要负责人决定、事实源冲突或命中任务卡停止条件属于任务状态事件，不使用时间阈值判断“长期阻塞”：

1. 立即改为对应非 `ready` 状态；
2. 从当前队列移除；
3. 在任务卡和 backlog 投影中记录原因；
4. 后续解除时重新插入。

如果控制器在启动前发现队列把明确非 ready 工作错误投影为 ready，视为队列失配，停止业务执行并进入状态修正；不得跳过错误后把队列当作可信事实继续执行。

## 五、事件驱动的队列维护

队列不在每轮普通触发时维护，只在以下事件发生时变更。

### 进入或顺序变化

- 新任务建立；
- 大任务拆出可执行切片；
- 阻塞解除或解冻；
- 用户改变优先级、主责、授权或固定顺序；
- 新的紧急任务需要插队。

### 离开或路由转换

- Codex 执行完成：从当前队列移除并归档。
- 外部 AI 执行完成：同一队列行改为 `codex_review`，主责改为 `codex`；Git 业务提交仍记录 `State: pending_review`。
- Codex 复审通过：从当前队列移除并归档。
- 复审未通过：移出当前队列，任务卡转为 `blocked` 并进入现有未通过入口。
- 命中停止条件、冻结、等待决定或取消：移出当前队列并保留在 backlog。

### 队列为空

无 recovery 且当前队列为空时，控制器只运行一次队列维护责任：

1. 读取各领域 backlog 顶部短表；
2. 只打开可能转为 ready 的少量任务；
3. 建立独立卡并排出固定顺序；
4. 提交队列维护；
5. 本轮不执行新任务。

本设计取消“每轮统一汇总三类候选”和“队列不足两个就优先补位”的常规判断。所有已批准且 ready 的工作应在形成或解阻塞事件中进入队列；若遗漏则是待修正的管理数据问题，不靠每轮重算掩盖。

## 六、手动 `1` / `2` 与自动路由

- 每小时控制器：按全局固定顺序选择第一项当前可安全执行的 route。
- 纯 `1`：按用户明确语义，只选择队列中当前 AI 可执行的第一项 `codex_execute` 或 `external_execute`，跳过复审 route。
- 纯 `2`：只选择队列中第一项 `codex_review`；DeepSeek / Claude 仍不得自审。
- 用户指定任务：用户当次明确要求优先，但仍执行租约、身份、主责、路径隔离和任务卡边界检查。

审核入口和 AI 合作沟通继续保存审核规则与交接证据；它们不再作为每小时控制器需要重新汇总排序的第二套 ready 任务池。产生可复审交接时，必须同时把同一任务投影为 `codex_review` 队列行。

## 七、按 route 加载规则

为降低稳定规则的固定上下文：

1. `开发管理/自动工作流规则.txt` 只保留租约、暂停、recovery 优先、固定队列顺序、临时跳过、全阻塞 fingerprint、唯一责任方和结果报告等薄路由规则。
2. decision / interruption 恢复细节迁入单独的恢复规则，只在 `Show` 返回 recovery 时读取。
3. `codex_execute` 再读取纯 `1`、目标任务卡和该任务必查范围。
4. `codex_review` 再读取审核入口、交接证据、目标任务卡和目标 diff。
5. `external_execute` 再读取外部执行规则、目标任务卡和必要事实源。
6. 当前队列为空时才读取状态与建议维护规则和分线 backlog。

不为每个细小领域新建一套调度器；领域与阶段只用于任务路由和检索。

恢复规则拆分不得改变固定调用器已经建立的 UTF-8 stdin 契约。自定义决定回复继续由显式 UTF-8 `StreamReader` 读取，测试驱动器也以 UTF-8 写入 stdin；不得退回系统代码页或普通 `[Console]::In.ReadToEnd()`。

## 八、只读任务卡检查器

新增 `tools/check-task-cards.ps1`，仅在创建或修改任务卡、改变任务状态、变更当前队列、队列补位和提交管理文件前运行。普通自动化每轮不运行全量检查器。

检查器验证：

- JSON 卡头可解析且必填字段齐全；
- 文件名与任务 ID 一致，ID 唯一；
- 枚举值合法；
- `expectedPaths` 为精确仓库相对路径；
- 当前队列只引用 `dispatchState=ready` 卡；
- 队列投影与卡头一致；
- 非 ready 卡可从来源 backlog 定位；
- backlog 状态投影与卡头一致；
- completed 卡不残留在当前队列或未完成 backlog；
- `blockedBy` 不包含自身；
- 已卡片化任务之间不存在直接可见的依赖环。

检查器只报告错误并返回非零退出码，不自动选任务、排优先级、改队列、修复文件或执行验证命令。

## 九、复杂度判断

### 保留的必要能力

- `Show`、暂停和两类 recovery 优先；
- 单写入租约；
- 主责、身份和执行器匹配；
- 依赖、负责人决定和内容冻结；
- 人工改动路径冲突检查；
- 临时冲突时检查下一项；
- 所有项不可执行时的 fingerprint 与逻辑暂停；
- 外部 AI 双提交、禁止自审和 Codex 正式复审；
- workspace guard、路径限定提交和最小充分验证；
- runner 等待与同一 session 恢复。
- 固定调用器传入的 `RepositoryRoot` 当前分支是自动 Codex 责任方唯一实施和结果核验面；
- 自定义决定回复的 UTF-8 stdin 传输。

### 被移除的重复工作

- 每轮从执行队列、审核入口和外部交接重新汇总三类候选；
- 每轮重新计算统一排序；
- 为选题加载多张无关完整任务卡；
- 在当前队列与分线 backlog 重复维护完整任务正文；
- 为维持固定深度形成“补一张、执行一张”的反复队列维护。

### 新增的有限复杂度

- 独立任务卡及结构化卡头；
- 当前队列和 backlog 的短投影；
- 一个只读一致性检查器；
- 任务 route 在外部执行和 Codex 复审之间显式转换。

自动化运行逻辑因此简化，管理数据契约略微增加，但没有删除安全步骤或增加新的长期运行状态。

## 十、首次迁移

1. 新增任务卡格式、只读检查器和临时仓库夹具测试。
2. 重新核实当前队列每张卡的实时状态。
3. ready 项迁入独立任务卡并进入短队列。
4. blocked、frozen、pending_decision 项迁入独立任务卡和对应 backlog，不进入当前队列。
5. 已完成或审核完成项直接归档。
6. 若存在有效外部待复审任务，将同一任务投影为 `codex_review`。
7. 更新 `AGENTS.md`、自动工作流核心规则、控制器提示词、状态维护规则、AI 协作规则、审核入口和外部执行提示。
8. 更新自动化与 PowerShell 直接测试，并保留固定 `RepositoryRoot`、禁止自动 worktree 及 UTF-8 决定回复断言。
9. 将新增 `任务卡/` 和恢复规则路径补入未来管理目录迁移映射，但本轮不搬迁现有目录。

## 十一、验证

至少覆盖：

- 合法任务卡与短队列；
- 损坏 JSON、字段缺失和非法枚举；
- 队列与任务卡不一致；
- 非 ready 卡错误进入队列；
- blocked 卡在 backlog 中失联；
- completed 卡残留；
- 正常队首执行；
- 队首存在临时路径冲突时按固定顺序选择下一项；
- 全部项具有相同阻塞 fingerprint 时保留现有暂停行为；
- recovery 优先于普通队列；
- Codex 自动责任方提示词携带固定 `RepositoryRoot`，并明确禁止 linked worktree 与任务分支；
- 任务提交、任务卡和队列状态只能由同一 `RepositoryRoot/HEAD` 的固定调用器核验为成功；
- 自定义决定回复通过 UTF-8 stdin 无损进入 recovery 责任方；
- 空队列只运行维护、不在同轮执行新任务；
- 外部执行完成后同一任务转换为 `codex_review`；
- 纯 `1` 与纯 `2` 保持各自语义；
- 自动化规则与 PowerShell 运行时检查；
- 管理文本检查、路径限定空白检查和 Git 差异检查。

本轮不运行 Unity、BattleSim 或数据链路检查，除非实际实施意外触及其业务输入；若发生该情况，应停止并重新确认范围。

## 十二、验收标准

- 当前队列从 19,661 字符缩减为短索引，目标不超过 2,500 字符。
- 普通无 recovery 且队首无冲突的自动化只需读取短队列和一张任务卡即可选定责任方。
- 前项存在临时冲突时只按固定顺序补读到第一张可执行卡，不读取 backlog 或重新全局排序。
- 队列非空时不进入 backlog 补位流程。
- 队列顺序只在明确事件中变化。
- blocked、frozen、pending_decision 与 waiting_reply 均能从领域 backlog 定位。
- 外部执行与 Codex 复审使用同一任务卡，不复制业务范围正文。
- 自动 Codex 责任方的全部结果都在传入的 `RepositoryRoot` 当前分支形成并由同一 HEAD 核验；不得以其他 worktree 或分支上的提交关闭任务。
- recovery 规则拆分后，UTF-8 自定义决定回复回归继续通过。
- 不新增自动生成器、依赖求解器、数据库、兼容分支或长期 runtime 状态。
- 现有恢复、租约、隔离、复审、提交和全阻塞暂停行为均有回归证据。

## 十三、停止条件

出现以下任一情况时停止实施并重新评估：

- 统一短队列无法在不复制完整交接或审核正文的前提下表示复审工作；
- 必须新增长期 runtime 状态、第二套队列或兼容解析才能维持现有恢复；
- 必须允许自动责任方创建 worktree、任务分支或从固定 `RepositoryRoot/HEAD` 之外返回结果；
- 当前任务状态无法在任务卡、短队列和 backlog 投影之间建立唯一权威关系；
- 实施需要修改 Unity、BattleSim、CSV、asset 或游戏设计事实；
- 迁移开始要求一次性拆分全部 backlog 或同时执行管理目录重组；
- 为保持吞吐必须删除路径冲突跳过、全阻塞暂停、恢复优先或单写入租约。
