# 天章每小时自动工作流控制器 v2 设计

> 日期：2026-07-13
> 状态：用户已确认设计方向，待书面规格复核
> 前身：`docs/superpowers/specs/2026-07-11-hourly-automation-controller-design.md`
> 实施计划：`docs/superpowers/plans/2026-07-13-hourly-automation-controller-v2-implementation.md`
> 范围：队列补充、脏工作区隔离、Codex / DeepSeek 串行调度及相应恢复验证

## 1. 背景与现状证据

当前 `TZG Hourly Controller` 采用单写入控制器和三小时本机租约，解决了旧 WF1、WF2、WF3、WF4 之间的并发写入与共享锁竞争，但两天真实运行暴露了三个新的系统性问题。

1. 队列维护以“当前队列总条数少于 5 条”为触发条件，而且优先于执行任务。队列从 5 条完成一条变为 4 条后，下一小时必然用于补位，即使仍有多个可执行任务。
2. 无恢复指针时，只要 Git 工作区存在任何改动，控制器就整轮只读退出。当前控制器创建待决策项后修改了 `开发管理/自动工作流状态.txt`，但没有提交该有效状态变更；本机租约已回到 `IDLE`，导致后续轮次会把控制器自己的产物误判为人工脏改并持续退出。
3. 队列维护可以提升 DeepSeek 主责任务，但当前唯一启用的写入控制器只执行 Codex 主责任务。TQ-057 曾被提升为 DeepSeek 前置任务，其下游 Codex 任务 TQ-059 因而无法推进，后来只能通过修改主责临时解锁。

这些问题的共同根因不是单个阈值设置，而是控制器没有显式建模“当前真正可执行的任务供应”“脏改的所有权与路径冲突”以及“当前已启用的执行能力”。

## 2. 目标与非目标

### 2.1 目标

- 队列补充以可执行任务供应为依据，不再因总条数从 5 降为 4 占用独立小时轮次。
- 队列中即使存在大量阻塞、冻结、待决策或无执行器任务，也能识别真实供应不足。
- 控制器能够在不覆盖、不暂存、不提交人工改动的前提下，继续执行路径不重叠的任务。
- 控制器自身产生的待决策或状态变更不会遗留为下一轮无法识别的脏改。
- 在仍保持单控制器、单租约、禁止并行写入的前提下，按任务主责串行调度 Codex 或 DeepSeek。
- DeepSeek 不可用时不会把 DeepSeek 前置任务伪装成活跃可执行链，也不会阻塞无关 Codex 任务。
- 保留现有身份确认、内容冻结、审核边界、失败关闭、验证后提交和不自动推送远端等硬约束。

### 2.2 非目标

- 不恢复旧 WF1、WF3、WF4 的独立定时写入能力。
- 不引入多个并行代理、多个并行工作树或自动合并分支。
- 不自动 stash、reset、清理或覆盖用户的本地改动。
- 不因 DeepSeek 暂时不可用而静默把任务改派给 Codex。
- 不改变 DeepSeek 产物必须标记未审核并由 Codex / ChatGPT5.5 复审的规则。
- 不在本设计中处理具体业务任务或替用户回答现有待决策项。

## 3. 方案比较与选择

### 3.1 方案 A：只调整固定条数阈值

把“少于 5 条”改成“少于 3 条”，并继续在任意脏工作区退出。改动最小，但不能识别“总量很多、实际不可执行”，也不能解决自有脏改死锁或 DeepSeek 前置任务缺少执行器的问题。

### 3.2 方案 B：能力感知的单控制器串行调度

用可执行库存替代总条数；按脏路径与候选修改路径判断是否冲突；让同一控制器在同一租约内按主责直接执行 Codex 任务或调用 DeepSeek。普通补位并入任务收尾，只有无安全候选或存在必须先修复的队列事实错误时才使用独立维护轮次。

这是本设计采用的方案。它保留当前单写入架构，同时直接处理三个根因，复杂度主要集中在候选资格计算、提交隔离和回归测试中。

### 3.3 方案 C：专用自动化 worktree 与多执行管线

为 Codex、DeepSeek 和人工工作区建立隔离分支或 worktree，再自动合并或拣选提交。隔离最强，但会引入分支同步、中文管理文件冲突、自动合并、失败回滚和额外恢复状态，超出当前项目需要。

## 4. 核心概念

### 4.1 配置执行器与运行可用性

控制器维护两个不同概念：

- **配置执行器**：本控制器被允许调度的执行身份。v2 配置为 Codex 与 DeepSeek；两者都由同一控制器串行调用，不代表存在两个定时写入者。
- **运行可用性**：执行器在本轮是否通过身份、命令入口和必要环境检查。Codex 在 Node REPL 身份确认成功后可用；DeepSeek 只在真实选中 DeepSeek 候选后才执行 CLI 与代理身份预检，避免无候选时浪费轮次。

DeepSeek 预检失败发生在任何项目修改前时，控制器记录本机退避状态并继续尝试本轮其他 Codex 候选，不把预检失败算作业务任务失败。退避期内 DeepSeek 任务不计入可执行库存，但仍保留原主责和任务事实。

### 4.2 可执行任务

任务只有同时满足以下条件，才计入当前可执行库存：

1. 状态为待处理，不是完成、阻塞、待复审或内容冻结。
2. 所有前置任务已完成；如果前置产物来自 DeepSeek，则必须已完成 Codex 复审。
3. 主责能够唯一映射到配置执行器，且没有违反 `AGENTS.md` 与 `开发管理/AI协作规则.txt`。
4. 任务没有未解决待决策；未解决决定的原任务及其全部传递后继均排除。
5. 内容冻结、G1/G2/G3 闸门和其他项目硬约束均满足。
6. 任务卡提供足够明确的范围，可以在修改前推导完整 `expectedPaths`；范围不明时不能靠猜测执行。
7. `tools/automation-workspace-guard.ps1 Check` 确认 `expectedPaths` 与本轮基线不冲突。

“配置执行器存在但运行预检尚未执行”的 DeepSeek 候选可以进入初步候选集；只有预检成功后才能成为最终执行对象。预检失败后重新计算本轮可执行库存和候选顺序。

### 4.3 可执行库存水位

- **低水位：2 条。** 可执行库存大于 2 时，不因数量触发补位。
- **高水位：5 条。** 需要补位时，最多补到 5 条近期可执行任务。
- 队列总条数只用于展示，不再作为补位触发依据。
- 阻塞、冻结、待决策、待复审、主责无执行器或依赖未满足的条目不计入库存。

## 5. 每小时控制流程

每轮按以下顺序运行，任意时刻只允许一个写入工作单元：

1. 读取项目规则并通过 Node REPL 确认实际模型身份。
2. 获取本机三小时租约，读取恢复指针和待决策状态。
3. Acquire 后调用 `tools/automation-workspace-guard.ps1 Snapshot`，快照完整 Git 基线：已暂存、未暂存、未跟踪、重命名、删除路径及其可复核指纹；dirty submodule/gitlink 或工具失败时失败关闭。
4. 若存在恢复任务，沿用现有严格恢复规则；只有变更全部属于原 `expectedPaths` 且基线证据一致时恢复。
5. 读取审核入口、当前队列、必要 backlog 与执行器配置，计算初步候选。
6. 优先处理能够安全恢复的原任务，其次处理路径不冲突的最高风险待复审对象。
7. 为每个候选先推导完整 `expectedPaths`，再调用 workspace guard `Check`；退出码 20 跳过冲突候选并检查下一项，退出码 21 表示 baseline changed，安全退出并保留必要恢复证据，非法输入或工具失败则失败关闭。通过后从合法候选中选择最高优先级执行对象；Codex 直接执行，DeepSeek 在通过按需预检后由控制器串行调用。
8. 如果存在安全执行候选，队列条数不足不得在执行前抢占本轮。任务验证通过后，在同一收尾过程中按第 6 节执行必要补位。
9. 只有在没有安全执行候选，或者队列事实错误会影响安全选题时，才选择独立队列维护分支。
10. 没有候选且没有必要维护时释放租约并安静退出。

周期性 12 小时队列审计保留，但它是轻量预检，不自动抢占安全业务任务。若审计只更新时间或确认无变化，只更新本机状态和 memory；若发现会影响当前候选正确性的依赖、主责、冻结或归档错误，才进入维护分支。

## 6. 队列补充与维护

### 6.1 任务收尾补位

业务任务完成并准备闭环队列时，重新计算完成后的可执行库存：

- 库存大于 2：不补位。
- 库存为 1 或 2：从 backlog 提升确定性最高、依赖满足、主责有配置执行器的任务，最多补到 5 条。
- 库存为 0：先尝试同一收尾补位；如果当前任务无法成功闭环，则下一轮进入独立维护。

补位必须是无需新设计决定的管理动作，并与任务闭环使用同一提交。若候选主责、范围、依赖或冻结状态需要判断，则不在收尾中擅自补入。

### 6.2 独立维护触发

只有以下情况可以占用独立轮次：

- 没有安全可执行任务，且可从 backlog 补出至少一个合法候选。
- 当前队列含完成未归档、依赖状态错误、主责无配置执行器、冻结内容误入等会影响安全路由的事实错误。
- 12 小时审计发现必须提交的项目事实修正，而且没有能够在业务任务收尾中安全合并的对象。

### 6.3 无候选抑制

若维护确认 backlog 中没有合格候选，控制器调用 `RecordQueueState` 在本机记录队列与相关 backlog 的内容指纹。指纹未变化、没有任务完成、没有待决策解决且未到下一次 12 小时审计时，不重复执行同一无效维护。

## 7. 脏工作区隔离

### 7.1 基线分类

控制器在选择任务前记录：

- 已暂存路径及暂存内容指纹。
- 未暂存路径及工作区内容指纹。
- 未跟踪路径及文件内容指纹；无法可靠取指纹的目录或特殊文件视为冲突。
- 当前 HEAD、索引状态和重命名/删除关系。

基线只用于证明人工改动未被改变，不进入 Git 项目文件。

### 7.2 候选路径判定

每个候选在 `task_selected` 前必须得到完整、项目相对的 `expectedPaths`：

- 与任一基线脏路径重叠、父子路径包含关系不明确或可能通过生成器间接覆盖时，跳过该候选。
- 路径完全不重叠时可以继续，不因其他目录存在人工改动而全局退出。
- 一个候选冲突后继续检查下一候选；只有所有合法候选都冲突时才安静退出。

控制器不得为了制造不重叠而缩小任务真实修改范围。任务范围无法完整推导时按不安全候选处理。

### 7.3 提交隔离

提交必须满足以下结果约束：

- 只 `git add -- @expectedPaths`，并用 `git commit --only -m "$commitMessage" -- @expectedPaths` 提交本轮路径，不得包含基线中任何已暂存或未暂存人工改动。
- 不使用 stash、reset、checkout、clean 或临时覆盖人工文件。
- 允许存在不相关的预先暂存改动，但实现必须使用经过回归验证的路径限定提交机制；如果当前 Git 状态无法证明隔离，则本轮不写入。
- 提交前后都调用 workspace guard `Verify`；退出码 21 表示 baseline changed，安全退出并保留恢复指针，非法输入或工具失败则失败关闭。提交后所有原 staged、unstaged、untracked、rename、delete 路径、内容指纹和暂存状态必须与执行前一致。
- 任一人工差异发生变化都视为验证失败，不继续提交完成状态，并保留准确恢复证据。

### 7.4 控制器自有状态变更

创建待决策、写入有效阻塞摘要或其他项目可见控制器结果时：

1. 在修改前把对应状态文件登记到本轮 `expectedPaths` 并写入检查点。
2. 状态写入成功后执行文本、行尾空白和 Git 差异验证。
3. 将该有效状态作为独立的控制器结果提交，提交信息明确为记录待决策或状态结果。
4. 提交失败或进程中断时保留恢复指针，下一轮按控制器自有 `expectedPaths` 恢复，不能释放为无恢复指针的普通脏工作区；禁止 `IDLE + no recovery + controller-owned dirty file`。

现有 `开发管理/自动工作流状态.txt` 待决策差异属于部署迁移入口。实施 v2 前必须把它认领为控制器自有结果并安全提交，或建立与其完全匹配的恢复指针；不得把它当成人工改动覆盖或回退。

## 8. Codex / DeepSeek 串行调度

### 8.1 单控制器边界

- `TZG Hourly Controller` 仍是唯一启用的写入型定时自动化。
- DeepSeek 不拥有独立定时器，不与 Codex 并行修改工作区。
- 控制器取得租约、选择 DeepSeek 任务、完成身份与授权检查后，才调用 DeepSeek 执行一个最小任务切片。
- 控制器负责基线快照、`expectedPaths`、最终验证、路径限定暂存和提交；DeepSeek 子进程不得 stage、commit 或扩大路径，只有控制器拥有 stage/commit 权限。

### 8.2 DeepSeek 执行要求

选中 DeepSeek 候选时，控制器必须读取 `开发管理/DeepSeek工作提示词.txt` 与 `开发管理/AI协作规则.txt`，并执行既有身份和授权自检。DeepSeek 只能处理待处理、非复审、主责明确属于 DeepSeek / Claude 执行范围的任务。

DeepSeek 产物必须：

- 标记 `⚠️ 已修改/未审核` 和实际修改方。
- 在 `开发管理/AI合作沟通.txt` 写入完整交接。
- 运行任务卡要求的机械检查和回归，但不得自审为通过。
- 修改范围严格落在控制器预先登记的 `expectedPaths` 内。

控制器验证修改范围和基础检查后提交未审核产物。下一轮 Codex 将该交接作为待复审对象优先处理；依赖该产物的后继任务在复审通过前保持不可执行。

### 8.3 DeepSeek 不可用

- 无 DeepSeek 候选时不运行 Claude/DeepSeek CLI 预检。
- 有候选但预检失败且尚未修改项目时，调用 `RecordWorkerFailure` 在本机记录错误和有限退避，继续尝试本轮 Codex 候选；预检成功调用 `ClearWorkerFailure`。
- 退避期间 DeepSeek 任务不计入可执行库存；队列维护可以保留其事实，但不得用它满足近期库存高水位。
- DeepSeek 长期不可用且形成关键路径时，创建明确待决策或交接请求；不得自动改派主责。

## 9. 待决策与依赖处理

- 未解决待决策排除原任务及其全部传递后继任务，但不阻塞无关任务。
- 待决策状态必须按第 7.4 节形成可恢复、可提交的控制器结果。
- 有效回复解决决定后，原任务恢复为最高优先级候选；如果工作区存在不相关人工改动，仍按路径隔离规则判断，不做全局退出。
- DeepSeek 任务完成但未复审时，状态视为“待复审”，不能让下游依赖满足。
- 队列维护发现“无配置执行器的任务成为活跃前置”时，应修正队列路由或提出决策，不得只补更多下游任务掩盖问题。

## 10. 本机状态扩展

在现有租约、恢复、待决策状态之外，本机状态需要保存以下最小信息：

- 最近成功队列审计时间与队列/backlog 指纹。
- 最近一次确认“无可补候选”的指纹，用于抑制重复维护。
- DeepSeek 最近预检错误、失败次数和退避截止时间。
- 当前任务的执行器身份，以及现有 `taskKind`、`taskId`、`checkpoint`、`expectedPaths` 和恢复次数。

人工脏改的完整内容指纹只需在单轮运行和必要恢复证据中保存，不写入项目状态文件或自动化最终回复。

## 11. 失败与恢复策略

- 身份未知、租约损坏、恢复路径越界、任务范围无法确定、验证无效等现有失败关闭条件继续保留。
- 人工脏改不再是全局失败条件；只有与所有候选冲突或无法证明提交隔离时才结束当前轮次。
- DeepSeek 预检失败但未产生项目改动时不是业务恢复失败，不消耗任务恢复次数。
- DeepSeek 或 Codex 已开始修改后发生失败，统一由控制器的 `expectedPaths` 与检查点恢复，不重新选择其他任务。
- 控制器自有状态写入中断必须保留恢复指针，不允许回到 `IDLE + 无恢复指针 + 自有脏文件` 的静默死锁状态。
- 无候选、全部候选与人工改动冲突、执行器处于退避或 backlog 未变化时，只记录 automation memory 和本机状态，不制造项目提交。

## 12. 验证设计

### 12.1 队列与库存场景

1. 总条数 4、可执行 4：直接执行，不进入独立维护。
2. 总条数 10、可执行 0：进入维护或准确安静退出，不能把阻塞条目计入库存。
3. 可执行库存 2：先执行最高优先级任务，成功收尾时补到最多 5 条。
4. 任务处于待决策、内容冻结、待复审或主责无配置执行器时，不计入库存。
5. backlog 无合格候选时记录指纹；下一小时事实未变时不重复维护。

### 12.2 脏工作区场景

1. 存在不相关未暂存改动：执行路径不重叠任务，提交后人工差异指纹完全不变。
2. 存在不相关未跟踪文件：执行其他路径任务，未跟踪文件保持原样且不进入提交。
3. 存在不相关已暂存改动：路径限定提交只包含本轮文件，原暂存差异仍保持暂存且内容不变。
4. 候选路径与人工脏路径重叠：跳过该候选并选择另一候选。
5. 所有候选均重叠：安静退出，不 stash、不 reset、不提交。
6. 待决策状态由控制器产生：状态变更被提交，或中断后存在准确恢复指针；不得留下无恢复指针的自有脏改。

### 12.3 执行器与依赖场景

1. DeepSeek 无候选：不调用 CLI 预检。
2. DeepSeek 候选存在且预检成功：同一租约串行执行，产物标未审核并生成交接。
3. DeepSeek 预检失败：记录退避并继续选择安全 Codex 候选。
4. DeepSeek 任务完成但未复审：下游依赖仍不满足。
5. DeepSeek 未配置或处于退避：其任务不计入近期可执行库存，队列补位不能用它凑数。
6. 队列出现 DeepSeek 前置、Codex 后继且无可用 DeepSeek 执行器：维护必须识别为能力断链。

### 12.4 项目级验证

- 扩展本机状态工具回归，覆盖队列指纹、执行器退避与自有状态恢复。
- 扩展自动化静态检查，确认仍只有一个启用的写入型控制器，旧 WF1/WF3/WF4 保持暂停。
- 验证控制器提示不硬编码任务编号，DeepSeek 只在有合法候选时调用。
- 运行项目文本检查、暂存前行尾空白检查、`git diff --cached --check` 和 `git diff --check`。
- 使用临时 Git 仓库回归路径限定提交，覆盖预先 staged、unstaged、untracked、重命名和删除场景，证明人工基线不变。
- 完成至少三个真实金丝雀轮次：干净工作区 Codex 任务、不相关人工脏改下的安全任务、DeepSeek 执行后 Codex 复审。

## 13. 部署与回滚

1. 暂停 `TZG Hourly Controller`，保留日报只读运行。
2. 先处理当前控制器自有的待决策状态脏改，确保它被安全提交或纳入准确恢复指针。
3. 实现并验证本机状态扩展、候选资格计算、路径隔离和提交隔离测试。
4. 更新项目规则、状态维护规则、AI 协作路由、控制器提示和静态检查。
5. 旁路运行只读候选计算，确认它对当前队列给出的库存、主责与依赖结论正确。
6. 启用控制器，依次完成项目级金丝雀验证。

若金丝雀发现人工差异变化、提交混入路径、执行器越权或恢复证据不完整，立即暂停控制器并保留本机状态。回滚到旧提示时必须同时恢复“任何脏改全局退出”的保守策略，不能只回滚一半路径隔离逻辑。

## 14. 完成标准

- 队列从 5 条降为 4 条时，若仍有 3 条以上可执行任务，不产生独立补位轮次。
- 队列总量很多但可执行库存低于或等于 2 时，能够正确补充或报告无合格候选。
- 不相关人工改动存在时，控制器可以完成路径不重叠任务，并证明人工 staged、unstaged、untracked 差异均未变化。
- 控制器创建待决策后不会留下 `IDLE + 无恢复指针 + 自有脏文件`。
- DeepSeek 主责任务只有在同一控制器能够实际调度时才进入可执行库存；其后继任务在复审通过前不解锁。
- DeepSeek 无候选时不浪费轮次预检，DeepSeek 暂时不可用时无关 Codex 任务仍可继续。
- 单控制器、单租约、禁止并行写入、不自动推送和必要验证后提交等现有安全边界全部保留。
