# 预防型错误经验记忆系统设计

日期：2026-08-24
状态：2026-08-25 Codex 已核对 DeepSeek V4 Pro 0813 评审事实并完成规格修订，用户明确批准；尚未开始实施规划或业务实施

## 目标

建立一套在相关工作开始前主动暴露已知风险的项目级经验系统。系统不以“保存了多少复盘”为目标，而以减少重复误判、无效尝试和返工为目标。

采用“任务级风险预检 + 选择性自动门禁”：任务根据当前领域、阶段、预期路径、代码符号和内容类型，只命中少量高相关经验；能够确定性检测的高价值经验再升级为门禁。普通任务不得全文读取经验库，也不引入向量数据库、外部服务或新的自动化 runtime 状态。

首期只启用技术与工作流经验。设计、内容和数值经验沿用同一结构，但必须在首期证明命中质量、预防价值和读取成本后才逐域开放。

## 当前基础与缺口

- `开发管理/开发-技术经验.txt` 已是技术实现的经验入口，包含 Unity、BattleSim、PowerShell、数据配置和素材流程等经验。
- `AGENTS.md` 已要求只读取该文件中与当前问题相关的章节，证明项目不接受每次全文加载。
- 任务卡已经提供 `domain`、`stage`、`expectedPaths`、必查范围、实施范围、验证和停止条件，可作为风险匹配输入。
- 项目已建立 L0 入口、L1 速查、L2 事实源、L3 归档的资料分层，可复用“短索引定位精确正文”的读取方式。
- 当前缺口不是缺少历史根因，而是缺少从“当前任务特征”到“开工前相关经验”的稳定路由。大量根因只存在于任务归档、验证记录或长篇技术经验中，执行者通常在问题发生后才可能找到。
- 现有经验也缺少统一的适用条件、排除条件、失效条件和门禁指针，不能安全地作为强制前置输入。

因此，单纯扩写 `开发-技术经验.txt` 只能形成复盘库，不能形成预防系统。

## 方案选择

### 方案一：每个领域固定读取完整防错清单

实现简单，但清单会随经验增长。小范围任务也会加载大量无关内容，长期产生 token 膨胀和清单疲劳，不采用为主方案。

### 方案二：任务级风险预检

为经验登记路径、符号、实体和显式引用条件，在任务 ready 前及正式写入前进行确定性匹配，只输出少量命中项。该方案与现有任务卡和最小上下文规则直接兼容，采用。

### 方案三：所有经验直接实现自动检查器

确定性问题的预防能力最强，但设计、内容和语义判断无法可靠自动化；若每条经验都新建检查器，会扩大工具维护面，不单独采用。

最终采用方案二，并只把后果严重、重复出现且可确定性识别的经验选择性升级为方案三。系统保持两条原则：能由测试或检查器防止的错误不长期只靠文字提醒；不能可靠自动化的经验不得伪装成硬门禁。

## 系统边界与权威顺序

经验系统只回答：

- 开工前应定位什么；
- 哪些做法已经证明会失败；
- 最短的正确处理顺序是什么；
- 哪些检查必须执行；
- 出现什么迹象时应停止并重新确认根因。

经验系统不保存或裁决当前业务事实。发生冲突时：

- 设定与设计事实以 `docs/` 当前原文为准；
- 当前任务范围、主责和验证以活动任务卡为准；
- Unity 当前行为以 `src/` 为准；
- 数值结论以 BattleSim 的当前实际运行为准；
- 当前管理状态以 `开发管理/` 对应事实源为准。

经验与上述事实冲突时，经验立即退出强制匹配并转为待复核；不得添加兼容分支或兜底文本让冲突经验继续生效。

系统不负责预测从未发生且没有项目证据的新风险，也不承诺消除所有人为或模型判断错误。

## 信息架构

经验系统采用四层结构：

| 层级 | 内容 | 默认读取方式 |
|---|---|---|
| L0 | `AGENTS.md` 与管理规则中的风险预检路由 | 任务准备和实施入口读取 |
| L1 | `开发管理/经验库/风险索引.json` | 本地脚本解析；模型不全文读取 |
| L2 | 现有技术经验精确章节或独立经验卡 | 只读取命中的精确章节 |
| L3 | 已废弃经验及其失效原因 | 仅追溯、冲突或复核时读取 |

首期不迁移全部现有经验。`风险索引.json` 的 `detailRef` 可以直接指向 `开发管理/开发-技术经验.txt#具体章节`；只有需要独立适用边界、根因证据或失效历史的复杂经验，才建立 `开发管理/经验库/经验卡/<ID>.txt`。

废弃经验保留稳定 ID 和取代关系，正文可移入 `开发管理/经验库/已废弃/`。活动索引不得把 L3 内容返回给普通任务。

## L1 风险索引

索引使用可由 PowerShell 原生解析的 JSON，不使用自由格式 Markdown 表格作为机器合同。顶层结构固定为：

```json
{
  "schemaVersion": 1,
  "experiences": [],
  "gates": []
}
```

单条经验索引示例：

```json
{
  "id": "EXP-BS-003",
  "title": "战斗机制双侧分支对称接入",
  "preflightSummary": "修改战斗机制前先定位双方执行分支，避免只接入单侧。",
  "status": "active",
  "level": "must_read",
  "triggerMode": "path_and_text",
  "domains": [
    "battlesim"
  ],
  "stages": [
    "implementation",
    "verification"
  ],
  "pathPatterns": [
    "simulations/BattleSim/Combat.cs"
  ],
  "textPatterns": [
    "Simulate",
    "Simulate2v2",
    "战斗机制"
  ],
  "detailRef": "开发管理/经验库/经验卡/EXP-BS-003.txt#开工前",
  "gateRefs": [
    "battlesim-release-build"
  ],
  "lastVerified": "2026-08-24"
}
```

字段合同：

- `id`：稳定且全局唯一，格式为 `EXP-<DOMAIN>-<NNN>`；发布后不得复用。
- `title`：单一风险的短标题。
- `preflightSummary`：不超过 100 个汉字的开工前提示；`notice` 只返回该字段。
- `status`：`candidate`、`active`、`review_required` 或 `retired`。
- `level`：`notice`、`must_read` 或 `gate`。`notice` 只展示摘要；`must_read` 加载 `detailRef`；`gate` 默认不加载经验根因，但必须至少登记一个 `gateRefs`。`must_read` 也可以同时登记门禁。
- `triggerMode`：`path`、`path_and_text` 或 `explicit_only`。
- `domains`、`stages`：可选过滤条件；非空时当前任务必须分别命中其中一个枚举值，空数组表示不限。
- `pathPatterns`：项目相对路径或 glob；统一使用 `/`。
- `textPatterns`：精确代码符号、实体 ID 或明确术语，不接受“任务”“角色”“战斗”等宽泛词独立形成强制匹配。
- `detailRef`：精确到 `路径#章节` 的 L2 指针。
- `gateRefs`：已有、稳定、可验证的门禁 ID；没有门禁时为空数组。
- `lastVerified`：最近一次依据当前事实源核验的日期。
- `supersededBy`：仅在被新经验取代时出现，指向新稳定 ID。

`<DOMAIN>` 代码与任务卡 `domain` 枚举的映射固定为：

| 经验 ID 代码 | 任务卡 domain |
|---|---|
| `UNITY` | `unity` |
| `BS` | `battlesim` |
| `DATA` | `data` |
| `CONTENT` | `content` |
| `MGMT` | `management` |
| `AUTO` | `automation` |

不接受别名。跨域经验的 ID 使用主要事实源或主要所有者对应代码，`domains` 可以列出多个任务卡枚举值。

索引只保存匹配和路由信息，不复制根因历史或规则正文。`gates` 是同一 JSON 内的固定门禁登记表，不是第二索引。每项结构固定为：

```json
{
  "id": "battlesim-release-build",
  "instructionRef": "开发管理/开发-技术经验.txt#模拟器",
  "entryPaths": [
    "simulations/BattleSim/BattleSim.csproj"
  ],
  "lastVerified": "2026-08-24"
}
```

具体命令与适用边界写在 `instructionRef` 指向的 L2 章节。风险预检脚本只验证门禁 ID 唯一、指针与入口路径存在并返回指针，不执行索引或经验正文中的命令，避免把 JSON 变成任意命令执行面。

## 匹配规则

风险预检输入来自活动任务卡现有内容：

- `domain`、`stage` 和 `title`；
- `expectedPaths`；
- `必查范围`；
- `实施范围`；
- 任务卡显式登记的经验 ID。

路径匹配先把 `\` 归一化为 `/`，在 Windows 项目中按不区分大小写比较。文本匹配使用字面量子串，不执行来自索引的正则表达式。

三种触发方式固定为：

1. `path`：任一 `expectedPaths` 命中任一 `pathPatterns`。
2. `path_and_text`：先满足路径命中，再由标题、必查范围或实施范围命中任一 `textPatterns`。
3. `explicit_only`：不自动推断，只有任务卡显式列出该经验 ID 才命中。

`domains` 和 `stages` 只作附加过滤，不能单独产生匹配；经验必须同时满足状态、过滤条件和对应 `triggerMode`。

`explicit_only` 用于设计语义、剧情信息边界、管理经验和其他误报代价较高的场景。首版不加入向量检索、相似度分数、关键词权重或模型二次排序。

结果收敛规则：

- 从所有命中经验汇总并返回全部 `gateRefs`，不得因阅读条数限制丢弃门禁；
- `must_read` 总数不超过 3 条时全部返回，不进行静默截断；显式引用在展示顺序中优先，其后是精确路径加精确文本、精确路径；
- `notice` 最多返回 2 条 `preflightSummary`，其余低优先级提示可以截断，不自动加载 L2 正文；
- `candidate`、`review_required`、`retired` 不参与普通任务自动提醒；
- 零命中必须明确返回空集合，不用泛化建议填充结果；
- 普通原子任务若命中超过 3 条 `must_read`，不丢弃任何一条后继续，而是返回 `preflight_overbroad`，先判断任务是否过大或索引是否过宽，不提高上限掩盖根因。

## L2 经验卡

独立经验卡固定使用以下结构：

```text
# EXP-BS-003 · 战斗机制双侧分支对称接入

## 状态
状态、最后核验日期、适用版本或事实源版本。

## 开工前
- 适用条件
- 排除条件
- 修改前必须定位的路径、符号或实体
- 禁止采用的做法
- 必须执行的检查
- 停止条件

## 正确处理
最短且已验证的处理顺序。

## 根因与弯路
已发生的问题、已证实根因和失败做法。

## 证据
来源任务、提交、测试、运行记录或审核证据。

## 失效条件
哪些架构、文件、接口、版本或规则变化后必须重新核验。
```

`## 开工前` 正文控制在 120～200 个 Unicode 字符，不含标题。无法在 200 字符内表达的根因历史移入后续章节；不能通过删掉适用边界压缩。普通实施只读取这一节；只有诊断相似故障、判断经验冲突或执行经验维护时才读取完整卡片。

每张经验卡只承载一个可独立判断的风险。同一根因造成的多个症状可以共用一张卡；根因或适用边界不同的经验不得为了减少文件数量而合并。

## 任务卡投影

`riskPreflight` 是任务卡 schema 2 的新增合同。强制阶段的 ready 任务卡在 `TASK-META` 中把顶层 `schemaVersion` 改为 `2`，并新增：

```json
"riskPreflight": {
  "explicitRefs": [],
  "matched": [
    "EXP-BS-003",
    "EXP-BS-007"
  ],
  "gates": [
    "battlesim-release-build"
  ]
}
```

- `explicitRefs` 保存规划者明确选择的 `explicit_only` 经验。
- `matched` 是确定性匹配与 `explicitRefs` 的去重并集。
- `gates` 是所有命中经验的门禁去重并集。
- 零命中也必须保存三个空数组，证明预检已经执行。
- 不保存时间戳或每轮 token 统计，避免无事实意义的任务卡 churn。

schema 迁移口径固定为：

- `tools/check-task-cards.ps1` 同时接受 schema 1 和 schema 2；历史 completed 归档不批量迁移。
- schema 2 必须包含字段集合精确的 `riskPreflight` 对象；schema 1 不得包含该对象。
- 强制阶段启用时，当时所有 ready 卡必须在同一迁移任务中重算并升级为 schema 2；此后 schema 1 的 ready 卡一律拒绝。
- 尚未进入 ready 的既有 blocked、frozen、pending_decision 或 waiting_reply 卡可以暂时保持 schema 1；下一次转 ready 时必须升级为 schema 2。已经是 schema 2 的卡转为非 ready 时保留最近投影，重新 ready 前重算。
- 检查器读取历史 completed 卡时继续接受 schema 1 或 schema 2，不改写历史证据。

`tools/check-task-cards.ps1` 在强制阶段重新计算活动 ready 卡的高置信结果，并验证任务卡投影一致。索引变更时，只重算当前 ready 队列和本轮直接修改的任务卡，不预分析整个 backlog 或历史归档。

## 开工前运行流程

计划新增单一只读入口 `tools/get-experience-risk-preflight.ps1`。它接收任务 ID 或任务卡路径，解析任务卡、L1 索引和命中的 L2 `## 开工前` 章节，向 stdout 输出一个 JSON 对象，不修改任务卡、索引或 runtime。结果至少绑定 `taskId`、任务卡 digest、索引 digest、命中 ID、`notice` 摘要、`must_read` 的精确正文、门禁指针和必读正文总字符数；执行者不需要再次全文打开经验文件才能看到开工前内容。

完整流程为：

1. 任务准备者冻结任务卡现有原子范围。
2. 风险预检计算 `explicitRefs`、自动匹配项和门禁。
3. 任务卡记录短投影；任务进入 ready。
4. 执行者在任何项目写入前再次调用同一入口。
5. 实时结果与任务卡一致后，执行者消费结果中已经嵌入的 `must_read` 精确正文；只有正文缺失、与事实冲突或需要追溯根因时才按 `detailRef` 打开原章节。
6. 确认所有 `gateRefs` 对应的固定检查入口存在，再开始实施。
7. 完成时把命中的门禁加入任务原有验证集，并只运行一次最小充分验证。

模型只接收匹配器返回的短 JSON 和命中的精确 L2 章节，不接收完整 L1 索引。普通任务目标是命中 0～3 条 `must_read`，额外阅读通常控制在约 1000 token 内。

确定性上下文边界使用字符数而不是依赖特定模型 tokenizer：所有命中 `must_read` 的 `## 开工前` 正文合计不得超过 600 个 Unicode 字符；超过时返回 `preflight_overbroad`。约 1000 token 是试运行的平均评估目标，不是单任务硬上限；匹配结果 JSON、最多两条各 100 字符的 `notice` 和不同 tokenizer 可能使个别任务高于该值，但不能放宽 600 字符合同。

## 手动与小时自动化强制点

强制阶段同时覆盖手动 AI 对话和小时自动化，不能只把调用要求写在本规格中：

- `AGENTS.md` 增加 L0 路由：选中 ready 任务并建立规定的 worktree 后、任何项目写入前，手动 Codex、DeepSeek 或 Claude 必须在该 worktree 对同一任务卡运行风险预检，读取命中章节，并确认结果与 schema 2 投影一致。范围变化时重新运行。
- `开发管理/状态与建议维护规则.txt` 把 schema 2 风险投影和写前预检加入 runnable／ready 维护合同；建立、重新 ready 或改变 `expectedPaths` 时必须重算。
- `开发管理/自动工作流规则.txt` 固定自动责任方强制点和失败行为，不把该合同复制进模型 prompt。

小时自动化的确定性所有者是共享入口 `tools/invoke-hourly-owner.ps1`，不是 Codex 或 DeepSeek candidate adapter：

1. 把 `tools/get-experience-risk-preflight.ps1` 加入共享入口依赖检查。
2. 对非 `queue_maintenance` run，在 `New-CandidateWorktree` 成功后、`Get-HourlyCandidateArguments` 和 `candidateScript` 调用前，以 `run.worktree + run.taskId` 调用预检。
3. 预检必须读取 owner worktree 内的索引和任务卡，验证实时匹配、schema 2 `riskPreflight` 投影、门禁指针和 600 字符边界；通过后由共享入口用既有私有路径与 ACL helper 把完整短结果写入 `StateRoot/preflight-results/<runId>.json`，文件内容绑定同一 taskId、任务卡 digest 和索引 digest。
4. `tools/hourly-owner-adapter.ps1` 给非 `queue_maintenance` candidate 增加必填的预检结果路径参数；`invoke-codex-candidate.ps1` 与 `invoke-deepseek-responsibility.ps1` 只接受已位于批准 StateRoot、文件名绑定 runId、内容绑定 taskId 与任务卡 digest 的结果，并把其中的 `notice`、`must_read` 正文和门禁指针直接放入首条责任提示。adapter 只消费共享入口已经验证的结果，不自行选择是否运行预检。
5. 共享入口只有在私有结果写入并形成 candidate 参数后才允许调用 Codex 或 DeepSeek candidate script。失败时不得启动模型责任方或伪造零命中；沿用现有 `attention_required` 和 worktree 保留合同，记录稳定 `experience_preflight_*` detailCode，不增加 runtime state、重试或 owner 专属分支。私有结果是本轮证据文件，不进入项目 Git 或 schema 5 runtime 字段。
6. `queue_maintenance` run 本身不做业务经验预检，也不传预检结果路径；但它创建或重新 ready 的任务卡必须由扩展后的 `check-task-cards.ps1` 验证 schema 2 投影，未通过不得正式集成。

这样，手动路径由 L0 规则前置，小时 Codex 和 DeepSeek 则在共同控制器中被同一个确定性闸门拦截，并在首条责任提示中直接收到相关坑；candidate adapter 不承担是否调用预检的判断。

## 范围变化

实施过程中出现以下任一事件时，暂停写入并重新运行预检：

- `expectedPaths` 新增路径；
- 文档任务扩大为代码、数据或 Unity 资产修改；
- 新发现直接调用者、运行时所有者或跨模块依赖；
- 修改对象新增代码符号、实体类型或内容类型；
- 原定技术路线发生变化。

重新匹配后先读取新增经验，再按现有任务原子性规则判断能否继续。新命中本身不创建新状态；若它证明任务已突破原停止条件或不再原子，沿用现有 `attention_required`／任务拆分规则停止，不建立经验系统专属状态机。

## 自动门禁

经验只有同时满足以下条件，才允许升级为 `gate`：

- 问题能够被确定性识别；
- 检查结果具有明确通过或失败；
- 已有稳定正反例，误报率足够低；
- 检查成本明显低于再次返工成本；
- 失败输出能指向具体路径、符号、实体或下一检查动作；
- 门禁自身有测试或固定 fixture。

设计趣味、人物自然度、剧情体验、未经运行的数值平衡等判断不得成为自动门禁。

新增经验不能在没有授权时顺带新增检查器。门禁实施必须是独立原子任务，冻结脚本路径、正反例、回滚边界和验证；门禁通过复审后，经验索引才能把候选门禁引用改为活动 `gateRefs`。

风险预检入口只返回门禁，不直接执行任意脚本。具体门禁继续由任务卡验证、现有统一验证入口或明确的固定命令执行。相关输入未变化时不重复运行同范围检查。

## 新经验采集与晋级

业务任务发现新问题时，不顺带创建正式经验卡或修改全局索引。若满足以下任一条件，只在该任务本来就会写入的归档正文中增加 `## 经验候选`：

- 同类问题已经重复出现；
- 错误方向造成实质返工；
- 根因不直观且容易再次误判；
- 审核发现了可泛化问题；
- 问题可以形成确定性门禁。

候选固定记录：现象、已证实根因、可能复用范围、证据和是否存在门禁可能。一次性拼写错误、明显编译错误、只对已删除实现有效的问题不记录。

候选不自动生效，也不进入普通任务预检。独立经验维护任务通过固定标题检索新归档中的候选，只把它们作为线索；每条正式经验仍须独立完成去重、事实核验、适用边界、索引触发条件和失效条件。普通队列维护不因此全文扫描历史归档。

## 失效、冲突与取代

出现以下任一情况时，经验转为 `review_required`，立即退出强制匹配：

- `detailRef`、目标文件、符号、实体或门禁入口不存在；
- 当前事实源与经验内容冲突；
- 相关架构、schema、版本或所有者发生变化；
- 门禁持续误报或不能给出可操作失败信息；
- 新经验明确取代旧经验。

复核证明经验仍适用时更新证据和 `lastVerified` 后恢复 `active`；证明已失效时改为 `retired`，填写 `supersededBy` 或废弃原因并保留历史。不得静默删除曾经影响任务行为的经验。

## 错误处理

| 情况 | 行为 |
|---|---|
| 零命中 | 返回空集合，正常继续 |
| 索引 JSON 非法 | 强制阶段停止项目写入 |
| `detailRef` 缺失 | 返回稳定错误，经验转待复核前不得强制使用 |
| 门禁入口缺失 | 停止写入，不把门禁降级为普通提示继续 |
| 经验与事实源冲突 | 当前事实优先；停止依赖该经验并登记复核 |
| 模糊语义风险 | 只能作为 `notice` 或 `explicit_only` |
| 命中过多 | 返回 `preflight_overbroad`，检查任务原子性和索引范围 |
| 匹配器自身失败 | 强制阶段停止写入，不返回伪造的零命中 |

首期试运行尚未开启任务卡强制检查时，匹配器错误只使试运行样本失败，不影响现有任务流程。正式强制阶段不保留“匹配器失败但继续实施”的兼容分支。

## 验证设计

风险匹配器至少覆盖以下正反例：

1. 精确路径命中与不相关路径零命中。
2. `path_and_text` 同时满足、只满足路径、只满足文本。
3. `explicit_only` 不被自动触发，显式引用后生效。
4. `candidate`、`review_required`、`retired` 不进入普通结果。
5. 所有门禁保留，`must_read` 和 `notice` 正确限量与去重。
6. 非法 schema、重复 ID、非法枚举、缺失正文指针和缺失门禁返回稳定错误。
7. Windows 路径分隔符与大小写归一化。
8. `expectedPaths` 扩大后产生新增命中。
9. 超过 3 条 `must_read` 返回 `preflight_overbroad`。
10. 匹配器只读，不修改任务卡、索引、runtime 或工作树。

任务卡集成测试覆盖：零命中投影、正常命中投影、显式经验、索引变更导致旧投影失配，以及 ready 卡缺少预检投影在强制阶段被拒绝。

每个新门禁必须有至少一个允许样例和一个拒绝样例。不能稳定形成正反例的经验保持 `must_read` 或 `notice`。

在正式强制前，选取近期已归档的技术与工作流任务做只读回放：以当时任务卡输入运行当前索引，记录是否能在历史错误发生前命中相关经验，同时统计无关命中。历史回放只验证路由质量，不改写归档事实。

## 实施原子性与依赖

本系统是一个父级 initiative，不得作为一张执行卡整体领取。进入实施规划时，必须按项目现有拆分规则一次性建立完整的已知子任务和依赖，至少分为：

1. 索引 schema、经验卡模板、只读匹配器和匹配器测试组成一个基础任务；该任务只使用测试 fixture，不顺带裁决真实历史经验。
2. 每条真实种子经验分别完成根因核验、去重、适用边界和索引登记；不同经验默认是独立判断结果，不因文件都位于经验库而批量塞入基础任务。
3. 种子经验达到批准数量后，以冻结的当前／归档任务样本建立一个只读试运行任务，产出命中、误报和读取量报告。
4. 试运行通过后，先以一个任务让 `check-task-cards.ps1` 支持 schema 1／2、校验 schema 2 投影，但暂不拒绝既有 schema 1 ready 卡；它不修改 L0 或小时入口。
5. 以一个规则任务更新 `AGENTS.md`、`开发管理/状态与建议维护规则.txt` 和 `开发管理/自动工作流规则.txt`，冻结手动与自动责任方的调用时机、失败行为和权威边界；它不修改脚本或 ready 卡。
6. 以一个自动化任务在 `tools/invoke-hourly-owner.ps1`、`tools/hourly-owner-adapter.ps1`、`tools/invoke-codex-candidate.ps1` 与 `tools/invoke-deepseek-responsibility.ps1` 接入同一确定性预检结果和测试；它依赖 schema 2 检查支持及 L0 规则，不迁移任务卡。
7. 上述入口都通过后，以一个激活任务重算当时全部 ready 卡、升级为 schema 2，并让检查器从该提交开始拒绝 schema 1 ready 卡。激活是一次状态迁移，不保留长期 feature flag。
8. 每个新门禁是独立任务；每个非技术领域的开放也分别设计证据门槛和试运行，不在技术首期顺带实施。

本规格只冻结边界和依赖类型，不在当前对话中预分析 backlog、建立任务卡或选择具体种子经验。

## 分阶段落地

### 第一阶段：基础与只读试运行

- 建立 schema 1 风险索引、经验卡模板和只读匹配器。
- 只录入约 8～12 条已经有根因、证据和明确适用边界的技术／工作流经验。
- 优先引用现有 `开发-技术经验.txt#章节`，不批量迁移历史内容。
- 对约 10 个相关当前或已归档任务运行只读回放；不修改任务卡 schema，不阻断现有 ready 任务。

### 第二阶段：评估与强制预检

只有试运行满足以下条件才进入本阶段：

- 普通原子任务稳定不超过 3 条 `must_read`；
- 额外读取通常不超过约 1000 token；
- 高置信经验误报率低于约 15%；
- 没有频繁由匹配器自身问题阻断正常判断。

随后按“实施原子性与依赖”建立有序的独立任务，依次完成：

- 为 ready 任务卡启用 `riskPreflight` 投影；
- 扩展任务卡检查器；
- 更新 `AGENTS.md`、状态维护规则和自动工作流规则中的 L0／runnable／自动化强制合同；
- 在 `tools/invoke-hourly-owner.ps1` 的 owner worktree 创建后、candidate adapter 调用前接入确定性风险预检，并通过共享 adapter 把绑定结果送入 Codex／DeepSeek 首条责任提示；
- 重算当时当前 ready 队列；
- 在项目写入前强制实时预检。

不为试运行和强制阶段增加长期 feature flag、第二套索引或 runtime 状态。

### 第三阶段：门禁与扩域

- 只把已证明高价值且可确定性检测的经验逐条升级为门禁。
- 技术／工作流运行约 20 个相关任务后，再决定是否开放设计、内容和数值类经验。
- 非技术经验默认从 `explicit_only` 或 `notice` 开始；数值经验必须绑定 BattleSim 当前运行入口，不能把历史结果写成长期结论。

## 效果指标与停止条件

试运行只记录支持决策的最小指标：

- 每任务命中的 `must_read`、`notice` 和门禁数量；
- 实际读取的经验章节字符数与估算 token；字符数用于硬边界，token 只用于跨模型成本观察；
- 被执行者判断为无关的高置信命中；
- 门禁在写入或提交前发现的问题；
- 原本准备采用错误路线、但被预检纠正的可观察案例；
- 经验维护所需的独立任务数量。

不按经验条目总数、提醒次数或文档长度判断成功。

出现以下任一情况时停止扩展并重新评估：

- 普通任务持续需要读取超过 3 条必读经验；
- 平均额外上下文明显超过约 1000 token；
- 高置信误报达到或超过约 15%；
- 为维持匹配而不断增加关键词、权重、兼容分支或第二索引；
- 约 20 个相关任务后仍没有可观察的预防价值；
- 维护经验的成本明显高于已避免的返工。

若文本经验证明收益不足，只保留已经证明有效的确定性门禁和现有精确技术章节，不继续扩大系统。

## 非目标

- 不自动扫描、总结或迁移全部历史归档。
- 不把模型对历史的概括直接提升为经验事实。
- 不建立向量数据库、embedding 服务、外部知识库或常驻检索进程。
- 不要求所有任务至少命中一条经验。
- 不因风险系统存在而扩大任务职责、修改 route／owner 或绕过现有原子性规则。
- 不让经验索引成为业务事实源、验证结果或当前状态的第二权威。

## 完成口径

本设计的完整实现应当证明：一个带有冻结路径和符号的任务，在项目写入前能够得到确定性、少量、可追溯的风险提示；命中的经验能指向精确开工前章节和已有门禁；零命中、过期、冲突、范围扩大和匹配器失败都有明确行为；普通任务不加载完整经验库；试运行数据能够支持继续、收窄或停止该系统，而不是因为已经投入建设就默认扩张。
