# 自动工作流待决策与邮件回执设计

日期：2026-07-12
状态：待用户审阅

## 目标

当 `TZG Hourly Controller` 需要项目负责人作出实质性选择时，它不得自行猜测，也不得让该单一事项阻断其他独立、无歧义的任务。控制器应：

1. 创建一个可追踪、可恢复的待决策记录；
2. 同时通过项目状态、自动化任务标题/消息和邮件清晰告知负责人；
3. 继续路由其他已满足前置且无需该选择的工作；
4. 仅在指定邮箱的有效回信明确选择后恢复原工作；
5. 任何通知或回信读取故障都保持待决策状态，绝不代为决定。

邮件通知收件人固定为用户指定的备用邮箱。该地址仅保存在本机控制器状态或本机配置，禁止写入 Git、项目文档、自动化提示正文、提交信息及自动化 memory。

## 范围与非目标

本次只改造唯一写入型的 `TZG Hourly Controller`、其本机状态工具、项目级工作流规则/状态呈现、自动化配置和对应测试。暂停的旧 WF1/WF3/WF4 与只读每日简报不承担决策或邮件职责。

不实现任意自然语言的邮件指令、自动接受未知发件人的决定、推送远端、即时邮件轮询服务、或把所有低风险实现细节都升级为人工决策。

## 需要人工决策的边界

控制器必须请求决策，而非自行选择，至少包括：

- 两个或以上方案都会改变架构、运行时行为、数据语义或对外可见体验，且项目事实源无法唯一推出答案；
- 将扩大已选任务范围、突破内容冻结、改变既定优先级或主责边界；
- 不可逆或高影响操作，例如删除真实资产、迁移/重写保存数据、外部发送、覆盖有歧义的人工改动；
- 多个事实源冲突且无法按既定优先级消解；
- 任务卡显式要求“选择”“决定”或“批准”，但未给出唯一规则。

已有任务卡、事实源和项目规则能唯一推出的低风险实现细节，控制器可正常执行并记录证据。验证失败、身份未知、工作区越界或恢复路径不符仍按既有失败关闭规则处理，不伪装为待决策。

## 状态模型

`tools/automation-controller-state.ps1` 的本机 JSON 升级为 schema v2，并添加独立的 `pendingDecision` 对象。它不属于运行租约或恢复计数，因此 `Complete` 当前工作单元后不得清除它。

`pendingDecision` 的必填字段为：`decisionId`、`createdAt`、`taskKind`、`taskId`、`taskSummary`、`question`、`options`、`recommendedOption`、`impactSummary`、`status`、`notification` 与 `resolution`。选项具有稳定的短键（A/B/C），`status` 只能为 `PENDING`、`NOTIFIED`、`RESOLVED`、`DELIVERY_FAILED` 或 `REPLY_INVALID`。

本机配置另存收件人、允许的回信发件人和邮件搜索标签；敏感地址不回显于 `Show`、自动化 memory 或项目文件。状态工具提供以下原子操作：

- `CreateDecision`：仅在没有未解决决策且调用者拥有租约时创建；生成不可预测的 `DEC-YYYYMMDD-<随机后缀>`；
- `MarkDecisionNotified` 与 `MarkDecisionDeliveryFailed`：记录邮件尝试与错误摘要，不存邮件正文；
- `ResolveDecision`：仅对匹配的决策编号和选项键写入选择与来源元数据；
- `ClearResolvedDecision`：仅在已将结论消费到原任务或完成归档后调用；
- `Show`：默认给出可安全展示的待决策摘要，隐去地址、令牌和完整邮件搜索条件。

同一时间只允许一个未解决待决策项，避免多封邮件造成选择歧义。若又遇到另一决策，控制器跳过其任务并继续检查其余无依赖候选；没有可执行候选时安静退出。

## 控制器流程

1. 控制器照常获得租约、检查恢复指针和工作区。
2. 轮次开始先读取 `pendingDecision`。若为 `PENDING`/`NOTIFIED`/`DELIVERY_FAILED`/`REPLY_INVALID`，从 Gmail 查找允许发件人对相应决策编号的未消费回信。
3. 只接受严格格式 `DEC-...：选 A`（兼容英文冒号和 `选择 A`）。邮件主题或正文必须含相同决策编号；只消费最新且格式有效的一封。格式不正确时标为 `REPLY_INVALID`、保留原决策且不作推断。
4. 合法回信写入 `RESOLVED`，控制器在本轮优先恢复原任务；恢复时把选项、来源和时间写入该任务的证据或归档。恢复成功后才清理本机待决策记录和项目状态摘要。
5. 任务执行中触发决策边界时，不写业务实现结论；创建待决策记录，更新项目状态摘要，使用 `TZG｜待决策：<中文事项>` 更新自动化任务标题，并发送邮件。成功通知后完成该工作单元、释放租约。
6. 待决策存在时，动态路由排除依赖该选择的原任务及其后继，但仍选择其他主责匹配、依赖满足、无决策依赖的候选。
7. 若邮件发送失败，状态标为 `DELIVERY_FAILED`，项目状态和标题/消息仍显示该事项；后续轮次以受限退避重试，成功后停止重发。通知失败不得调用 `Fail`、不得自动选择、不得将控制器 `AUTO-BLOCKED`。

## 可见性与邮件协议

项目文件 `开发管理/自动工作流状态.txt` 新增“待你决策”区，仅呈现：决策编号、事项、简短背景、选项、推荐项、创建时间、通知状态和回复格式。没有未解决决策时明确写“当前无待决策项”。该文件不包含收件地址、回复邮箱、搜索查询或完整内部错误。

邮件标题采用 `【天章游戏开发｜需要决策】<decisionId>｜<事项>`。正文固定包含：为什么无法由事实源唯一推出、每个选项及影响、推荐项及理由、明确的回复示例、项目状态文件位置和“未回复前该事项不会自行决定”的说明。邮件只在创建时和投递失败后的退避重试时发送；不会为每小时空转重复提醒。

自动化任务的最终消息必须报告待决策编号、可见状态入口、邮件通知结果和本轮是否继续推进其他任务。标题更新失败只记录 memory，不能阻断状态登记或邮件尝试。

## 错误处理与安全性

- Gmail 工具不可用、授权失效、发送失败或收信失败：保留本机和项目状态，记录最小错误类别；不泄露地址、令牌或邮件内容。
- 非允许发件人、错误编号、过期编号、多选项、模糊文本或转发邮件：不解析为决定，保留待决策并记录为无效回复。
- 决策已解决但原任务验证失败：保留已选结论供恢复，不重新要求相同选择；仍遵循既有恢复/失败关闭阈值。
- 人工手动编辑项目状态不改变本机决策事实；只有状态工具与有效邮件回执可解析为决定。
- 在无 Gmail 能力的本地/测试环境中，以可注入的邮件适配器模拟发送、搜索和回信，不连接真实邮箱。

## 验证与验收

实现必须新增或扩展自动化状态工具测试，至少覆盖：schema v1 迁移、创建/显示/清理决策、单一未解决决策约束、租约所有者校验、`Complete` 不清除待决策、合法回信解析、错误发件人/编号/格式拒绝、投递失败重试与决策依赖任务跳过。

`tools/check-automation-workflow.ps1` 必须验证控制器提示不硬编码邮箱或决策 ID，包含决策边界、状态可见性、Gmail 失败兜底和“继续无依赖任务”的规则；同时保持唯一写入控制器约束。

最少运行：

```powershell
pwsh -NoProfile -ExecutionPolicy Bypass -File tools/test-automation-controller-state.ps1
pwsh -NoProfile -ExecutionPolicy Bypass -File tools/check-automation-workflow.ps1 -ExpectControllerActive
pwsh -NoProfile -ExecutionPolicy Bypass -File tools/check-review-text.ps1 -Paths 开发管理,tools,docs/superpowers/specs
git diff --check
```

验收条件：出现决策时能在项目状态、自动化标题/消息和邮件中看到同一决策编号；未回复时控制器不会擅作决定且可继续不依赖它的任务；有效回信仅由指定邮箱触发并能恢复原任务；任何邮件故障均有本地/项目可见兜底，不造成 `AUTO-BLOCKED` 或空提交。
