# Codex 复审不通过后的飞书返工决策设计

日期：2026-08-03
状态：设计已获负责人批准，按本文实施
适用范围：Codex / DeepSeek 小时工作流中的 `codex_review` 不通过或部分通过且需返工

## 1. 背景与根因

现行审核合同要求：Codex 复审不通过时，同一任务卡转为 `blocked`、移出队列，并写入 `开发管理/未通过审核清单.txt`。共享入口随后发送普通 `blocked` 结果通知。

这个状态转换本身是正确的，但通知只有说明文字，没有可执行动作。负责人如果没有仔细阅读消息，任务会长期留在队列之外；自动化也不会再次领取它。因此问题不是 `blocked` 状态错误，而是“需要负责人决定是否返工”没有形成醒目的、可消费的决策闭环。

## 2. 目标

- 保留复审不通过时的 `blocked` 事实，不让未批准返工的任务自动重跑。
- 把普通阻塞通知升级为一次性飞书返工决策卡，让负责人可直接选择处理方式。
- 回复后只做任务生命周期转换；不恢复旧 run、旧会话或旧 worktree。
- 复用现有飞书决策卡、入站回复验证和共享集成锁，不新增第二套 runtime、守护进程或通用重试队列。

## 3. 非目标

- 不把普通失败、验证失败、冲突或崩溃改造成 decision checkpoint。
- 不自动修复复审意见，不自动选择返工责任方。
- 不在飞书长连接进程中修改 Git、任务卡或队列。
- 不因未回复而重复通知、自动重试或占用 owner run。
- 不自动关闭、归档或回滚复审不通过的业务提交。

## 4. 核心边界

### 4.1 与开发中 decision checkpoint 分离

开发中 decision checkpoint 仍只用于“实现过程中必须由负责人决定、且存在合法干净 checkpoint”的场景。它绑定 checkpoint SHA，并在回复后从最新 `master` 创建新 run、新 worktree，通过 `cherry-pick --no-commit` 恢复未完成工作。

复审返工决策不包含 checkpoint，也不允许进入上述恢复路径。复审结论和对应提交已经在 `master`；决策回复只决定同一任务是否、以及由谁重新进入执行队列。

### 4.2 状态事实

决策卡发送后，任务仍为 `blocked`，仍不在当前任务队列中。私有决策请求只是与该阻塞结论绑定的待回复证据，不是新的任务状态或调度队列。

## 5. 飞书交互

只在以下条件同时满足时发送返工决策卡：

1. 当前 run 的 owner 为 Codex，route 为 `codex_review`；
2. 正式结果已经成功集成到 `master`；
3. 同一任务当前投影为 `blocked`；
4. `未通过审核清单.txt` 存在与本次任务和复审提交匹配的有效条目；
5. 当前 run 已按正常成功合同关闭，不存在需要恢复的活动 run。

卡片固定提供三个互斥选项：

- `A`：交回 DeepSeek 返工（推荐）；
- `B`：改由 Codex 返工；
- `C`：暂不返工，保持阻塞。

卡片正文必须通俗展示任务、主要复审问题、当前影响、推荐选择和“未选择前不会自动继续”。普通 `blocked` 结果卡不得与返工决策卡重复发送；若决策卡发送失败，仅记录通知失败，任务继续保持 `blocked`，不得因此改写审核结果或恢复任务。

## 6. 决策证据合同

返工决策请求复用现有飞书 decision transport，但使用独立的 `review_rework` 决策类别。私有请求必须精确绑定：

- `decisionId`；
- `taskId`；
- 被复审的正式提交 SHA；
- 复审结论提交 SHA；
- 当前任务上下文摘要；
- 对应未通过审核条目的摘要；
- 固定选项 `A/B/C`；
- 创建时间、过期时间和发送证据。

回复继续复用现有操作者身份、card nonce、provider message、decisionId 和允许选项验证。不得只凭按钮文字或自然语言猜测任务。

## 7. 回复后的受控转换

共享 owner 入口在选择新任务前检查已经核验的 `review_rework` 回复。两个定时器都可观察该回复，但所有正式转换必须在现有进程持有型集成排他锁内完成；首个成功消费的入口写入结果，另一个入口只观察到已消费状态。

转换前重新核验：

- 任务仍为原 `taskId`，仍为 `blocked` 且不在队列；
- 当前任务摘要、复审提交和未通过审核条目摘要与请求一致；
- 两个 owner 均未占用该 `taskId`；
- `integrationLease=null`，主工作区目标路径无冲突；
- 回复未过期、未消费，操作者身份有效。

各选项只执行以下机械动作：

### A：交回 DeepSeek 返工

- 同一任务卡转为 `external_execute/deepseek/ready`；
- `stateReason` 精确引用对应复审条目；
- 按原有顺序规则重新加入当前任务队列；
- 下一次 DeepSeek 定时轮次创建全新的 run、worktree 和模型会话。

### B：改由 Codex 返工

- 同一任务卡转为 `codex_execute/codex/ready`；
- `stateReason` 精确引用对应复审条目；
- 按原有顺序规则重新加入当前任务队列；
- 下一次 Codex 定时轮次创建全新的 run、worktree 和模型会话。

### C：暂不返工

- 任务继续保持 `blocked` 且不进入队列；
- 将本次决策标记为已消费；
- 不发送新的普通完成通知，不创建 run。

任一前置证据变化、路径冲突、锁竞争超时或回复不一致，都停止转换并报告 `attention_required`；不得自动改用另一 owner、兼容分支或恢复层。

## 8. 提交与通知

A/B 的任务卡、队列和 backlog 投影必须形成一个路径限定的管理状态提交，并在同一进程持有型集成锁内 fast-forward 到 `master`。C 不改变仓库事实时只消费私有回复证据。

A/B 转换成功后发送一条简短确认通知，说明任务已重新排队、责任方以及“尚未开始新 run”；C 只确认继续保持阻塞。通知失败不得回滚已经成功提交的任务状态，也不得重复消费回复。

## 9. 验证范围

- 决策卡：固定 A/B/C、推荐项、通俗说明和严格 schema；
- 回复验证：正确回复、过期回复、重复回复、身份不符、nonce 不符和上下文摘要变化；
- 状态转换：A 转 DeepSeek ready、B 转 Codex ready、C 保持 blocked；
- 隔离：不读取或恢复旧 run/worktree，不走 checkpoint cherry-pick；
- 并发：两个 owner 同时观察同一回复时只允许一次正式转换；
- 集成：锁占用、主工作区路径冲突和 taskId 被活动 run 占用时停止；
- 通知：普通 REST 出站不依赖长连接桥健康；发送失败不改变任务事实；
- 既有 decision checkpoint、共享内核、owner adapter、飞书、PowerShell 和集成隔离测试保持通过。

## 10. 停止条件

命中任一情况立即停止实施并报告：

- 必须把 `blocked` 改成 `pending_decision` 才能实现；
- 必须伪造 checkpoint SHA 或复用 checkpoint 恢复流程；
- 必须新增第二套 runtime、后台守护、通用重试队列或轮询提醒；
- 无法把回复精确绑定到任务、复审提交和未通过审核条目；
- 飞书入站桥必须直接获得 Git 或任务状态写权限；
- 并发消费无法由现有共享集成锁和一次性回复证据约束；
- 实现需要自动回滚、自动冲突解决或自动关闭复审不通过任务。
