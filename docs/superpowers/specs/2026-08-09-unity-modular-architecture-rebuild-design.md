# Unity 模块化架构重建设计

> 日期：2026-08-09
>
> 状态：✅ 设计对话已批准；本文冻结架构目标、迁移边界、阶段闸门、上下文治理和 URP 交接关系，不代表已经建立任务卡、修改 ready 队列、迁移代码、重建场景、安装 URP 或生产正式美术。
>
> 直接前置事实：`AGENTS.md`、`UNITY_STRUCTURE.md`、`docs/superpowers/specs/2026-07-23-minimal-context-loading-design.md`、`docs/superpowers/specs/2026-07-24-event-driven-task-context-optimization-design.md`、`docs/superpowers/specs/2026-08-09-art-production-mainline-priority-design.md` 与实时 `src/` 扫描。

## 一、目标与根因

当前项目不是完全没有模块化：运行时已经形成 `Foundation -> Domain -> Combat -> Gameplay` 的单向 asmdef 基础，任务管理也已经使用短队列、单任务卡和章节／符号级必查范围。但这两项基础尚不足以支撑后续规模增长。

2026-08-09 实时扫描得到：

- `src/Assets/Scripts` 有 87 个 C# 文件、约 30,568 行。
- 运行时代码约 22,707 行，其中宽泛 `TianZhang.Gameplay` 边界约 12,958 行，占约 57%。
- 16 个手写 C# 文件超过 500 行；行数本身不是错误，但多个文件已经同时承担多个可独立变化的职责。
- `DataConfigImporter.cs` 为 6,079 行、约 32 万字符、约 210 个方法，横跨 NPC、环境、册界、金丹、道基／紫府、攻击档案、术法、神通和敌人等多个领域。
- `Adventure`、`Map`、`Settlement`、`World` 与 `Game` 仍存在同一 Gameplay 程序集内的直接双向实现引用，因此当前 asmdef 只隔离了层级，没有隔离上层 Feature。
- `Character`、`GameSession`、`ExplorationController`、`TacticalCombatController` 和 `BattleUIManager` 仍是职责集中点。
- 根 `UNITY_STRUCTURE.md` 很短，但其 open gaps 曾继续引用已经归档完成的 TQ-065、TQ-066 与 TQ-068，证明结构索引若复制任务状态会失真。

本设计的首要目标是：在正式内容和美术规模扩大前，一次性重建 Unity 代码、数据、场景和上下文边界，使普通任务只需加载一个有限模块，且编译边界能够阻止职责重新聚集。

次要目标是：为后续 URP、2.5D 低模 3D 角色、关中正式表现和创角视觉生产提供稳定的运行时所有者与资产接入面。

## 二、已批准决定

1. 架构重建是新的 P1 Unity 前置工程，父项建议使用 `U-ARCH-REBUILD-01`。
2. 重构期间冻结 Unity Runtime、场景、CSV、DataConfig 导入器及相关 asset 的功能开发；路径不冲突的内容文档生产可以继续。
3. 当前游戏只是玩法验证薄切片，不强制兼容旧存档、旧内部 API、旧序列化字段、旧场景／Prefab 绑定或旧 Built-in 视觉。
4. Unity 场景、Prefab 和数据 asset 可以在新架构下重新生成；稳定内容 ID、现行设计事实和已验证规则结果继续保留。
5. 保留已有独立验证且职责清晰的纯规则与数据知识，但所有保留模块仍接受职责、依赖和文件边界审查，不原样搬运 Hub。
6. 采用“原地分阶段重建”，不建立长期并存的 Runtime V2，不从空目录重新发明全部规则。
7. 整个工程可以是一次集中重构，但内部必须按可验证、可回退阶段提交；不使用一个无法定位失败来源的巨型提交。
8. 架构重建前置于 `U-URP-PREFLIGHT-01`。URP 预检只能扫描重构后的正式路径和所有者。
9. 架构重建只恢复功能完整、视觉简陋的正式薄切片；URP 迁移后新增 `U-URP-VISUAL-BASELINE-01` 重建正式薄切片的技术视觉基础。
10. 技术架构审核由 Codex 负责。项目负责人只处理产品方向、范围扩张、排期冲突和停止条件决定，不承担代码级审查。

## 三、非目标

本设计不包含：

- 安装或迁移 URP。
- 生产正式 3D 角色、骨骼、动画、模块化外观或立绘。
- 完成关中场景最终装修、音效和批量正式资源。
- 新增玩法、调整战斗／成长数值或扩写内容。
- 兼容旧存档、旧内部 API、旧场景绑定或旧 Built-in 视觉。
- 建立第二套场景、会话、战斗、保存或内容导入所有者。
- 长期 adapter、双写、静默 fallback 或兼容分支。
- RAG、向量数据库、后台索引器、实时 token 监控或跨对话长期记忆。
- 按行数机械拆分所有文件。
- 在本文中直接建立任务卡、修改队列、改写美术主线或实施源码迁移。

## 四、目标架构

### 4.1 模块形状

```text
Foundation
├─ 通用结果、稳定 ID、基础时间／数学类型
└─ 不引用业务模块

Spatial
├─ 唯一六角坐标、格位、范围、视线、路径查询
└─ 只依赖 Foundation

Content
├─ 不可变配置 schema、目录和稳定数据契约
└─ 不包含 Editor 导入流程和运行时状态

Character
├─ 身份、基础属性、资源、装载和角色只读快照
└─ 不拥有 UI、场景、战斗控制器或修炼流程

Cultivation
├─ 道基、紫府、金丹和修炼状态机
└─ 通过显式输入／结果与 Character 组合

Combat
├─ CTB、攻击解析、伤害、行动、AI 与战斗结果
└─ 消费 CombatantSnapshot，不操作 Character 实现或 UI

World
├─ 世界时间、任务、背包、NPC、悬赏、册界与环境状态
└─ 每个子域有独立状态所有者

Gameplay.Contracts
├─ 跨场景命令、事件、导航接口和只读 DTO
└─ 只有契约，没有实现和全局工具

Features
├─ CharacterCreation
├─ WorldMap
├─ Settlement
├─ Adventure
└─ CombatPresentation

Infrastructure
├─ Persistence
└─ UnityContent

Bootstrap
└─ 唯一组合根

Editor
├─ ContentImporters
├─ SceneTools
└─ Diagnostics
```

Feature 拥有自己的控制器、用例和视图，但不得直接引用兄弟 Feature 的实现。导航、进入上下文、结果返回和跨场景状态只经过 `Gameplay.Contracts`。

### 4.2 依赖方向

```text
Foundation
   ↑
Spatial / Content
   ↑
Character / Cultivation / Combat / World
   ↑
Gameplay.Contracts + Features
   ↑
Infrastructure / Bootstrap / Editor
```

具体规则：

- Domain 不引用 Presentation、Bootstrap、Editor 或兄弟 Feature。
- Combat 不引用 Character 实现；应用边界将角色状态投影为战斗快照。
- Cultivation 不反向取得 Character 可写对象；应用用例组合两者。
- Feature 不引用兄弟 Feature；`Bootstrap` 是唯一可同时引用多个 Feature 实现的程序集。
- `Bootstrap` 只做创建和连接，不承载业务逻辑。
- `Gameplay.Contracts` 只允许接口、事件和 DTO，不得演变为实现工具箱。
- ScriptableObject、Resources 和 Unity 资产加载属于 `Infrastructure.UnityContent`；领域规则不直接查询资源路径。
- Editor 程序集不进入 Player。

### 4.3 文件与自动生成规则

- 一个文件原则上只放一个主要类型，但小型、紧密相关且共同变化的 DTO 可以同文件保存。
- 300～350 行是新手写文件的建议范围，不是硬上限。
- 手写文件超过 500 行时触发职责审查，不自动判定失败。
- 单一内聚算法、完整状态机、确定性数据投影或拆分后反而增加耦合的文件可以超过 500 行；架构证据必须记录保持单体的理由，并禁止继续加入无关职责。
- 只有带 `<auto-generated>` 标记并位于明确生成目录或使用 `*.g.cs` 命名的 C# 文件，才免于手写源码规模审查。当前仓库不存在此类 C# 文件。
- `DataConfigImporter.cs` 与 `SceneBuilder.cs` 是手写生成器，不是自动生成代码，继续接受职责审查。
- CSV 导入生成的 `.asset`、SceneBuilder 生成的 `.unity`、Unity 投影的 `.csproj`／`.sln` 和工具输出不适用 C# 行数规则，分别按数据、序列化或生成物链路管理。
- `.meta` 虽由 Unity 创建，但承载 GUID，不视为可随意删除的临时文件。

## 五、现有代码迁移

迁移使用四种动作：

- **保留并迁移**：职责清晰，只调整路径、程序集或命名空间。
- **拆分**：规则基本正确，但一个类型承担多个可独立变化的职责。
- **重写壳层**：保留领域结果，重写 Unity、场景、UI 或组合编排。
- **删除**：旧原型、重复入口或只服务旧结构的兼容代码不进入新架构。

### 5.1 Foundation 与 Spatial

| 现有内容 | 处理 | 目标 |
|---|---|---|
| `Core/HexCoord.cs`、`Core/HexGrid.cs` | 与 Spatial 类型统一 | `TianZhang.Spatial` |
| `Core/SpatialRules/SpatialHexCoord.cs` | 与 `HexCoord` 选定唯一语义，另一套删除 | `TianZhang.Spatial` |
| `SpatialQueryBoard*` | 保留纯查询，拆开 board、query 与 result | `TianZhang.Spatial` |
| `Grid/TacticalGridModel.cs` | 阶段 2 只迁移格位状态，EnvironmentProfile 持有移交阶段 3 适配 | `TianZhang.Spatial` |
| `Grid/SpatialQueryBoardFactory.cs` | 阶段 2 只跟随纯 Spatial 类型做机械调用更新，EnvironmentProfile 转换与实际迁移留在阶段 3 | `Infrastructure.UnityContent` |
| `Core/CTBEngine.cs` | 阶段 5 与 Combat 战术运行时一起移出 Core；阶段 2 不提前建立 Combat 所有权 | `TianZhang.Combat.Turns` |

阶段 2 完成后 Foundation 不再容纳六角格；CTB 在阶段 5 完成前保留现有所有权，不新增兼容壳。最终架构中 Foundation 不容纳六角格、CTB 或业务枚举。

### 5.2 Character 与 Cultivation

旧 `Character` 不迁移为同名大聚合，按实际职责拆为：

```text
CharacterIdentity
CharacterAttributes
CharacterResources
AbilityLoadout
CharacterProgressionRef
CharacterRuntimeProfile
```

- 生命、灵力、朝向、格位、冷却等战斗期状态进入 `CombatantState`。
- 道基、紫府和金丹状态进入 `CultivationState`。
- `BuildCombatantPanelState` 进入 Combat Presentation 投影器。
- 术法／神通装载进入 `AbilityLoadout`，不再与战斗冷却数组混合。
- `CharacterData` 改为不可变角色定义；运行时对象不直接暴露或承担 ScriptableObject 职责。

`FoundationPurpleMansionStateData.cs` 按语义拆为：

```text
FoundationState
MansionState
GuardianAbilityState
CultivationActionState
ClosedRetreatState
JindanLockState
对应 SaveData / Result
```

金丹证明代码保留已验证规则，按 `Definitions / State / Attempt / Resolution / Ledger` 重组。`JindanProofCoordinator` 只接受显式输入并返回结果，不读取全局会话。

### 5.3 Combat

| 现有内容 | 处理 |
|---|---|
| `CombatResolver`、`DamageCalculator` | 保留规则，拆开输入、计算、拒绝原因和结果 |
| `EnemyAI` | 只消费战斗快照与合法行动集合 |

| `TacticalCombatController` | 删除原大控制器，由聚焦协作者替代 |

替代协作者：

```text
CombatSession
CombatTurnScheduler
CombatCommandService
CombatActionResolver
CombatantRegistry
CombatResultBuilder
```

Combat 不知道场景、按钮、日志、Renderer 或 Character 实现。Adventure 只提交参战快照并消费战斗结果。

### 5.4 World 与 GameRuntime

旧 `GameSession` 替换为薄 `GameRuntime`：

```text
GameRuntime
├─ PlayerState
├─ WorldClock
├─ QuestStore
├─ InventoryStore
├─ NpcStore
├─ BountyStore
├─ CharterStore
└─ NavigationState
```

- 每个 store 独立捕获和恢复自己的快照。
- `GameRuntime` 负责生命周期和原子替换，不实现悬赏、册界或 NPC 修炼规则。
- `AdvanceWorldDay` 进入 `WorldClockService`。
- `RecalculateNpcCultivation` 进入 Cultivation 用例。
- `InvokeCharterFormal` 进入 World Charter 用例。
- `SessionStateSnapshots.cs` 按 Quest、Inventory、NPC、Navigation 和 SaveEnvelope 分开。
- `BountyRuntime`、`BountyStateStore` 和 `InventoryGrantService` 进入对应 World 子域。
- 新架构从独立的新保存 schema 1 开始；它取代而不是延续当前薄切片的 schema 4，不读取或迁移旧存档，稳定内容 ID 继续复用。

册界纯规则按职责重组为：

```text
CharterDefinitions
CharterState
CharterAuthorization
CharterConflictResolver
CharterInvocationEvaluator
CharterCandidateBuilder
CharterCommitService
CharterResult
```

所有长期状态变更只通过 `CharterCommitService` 写入 `CharterStore`。

`DataConfigImporter` 单体替换为：

CsvTableReader
ImportDiagnostics
AssetCommitter

CharacterContentImporter
CombatContentImporter

### 5.7 唯一所有者切换

- 新所有者接管前，旧所有者仍是唯一入口。
- 同一功能不得同时由新旧两套代码写状态。
- 每个阶段只有一次明确切换：迁移消费者、验证、删除旧入口。
- 不为了编译通过增加长期 adapter、兼容门面或双写。
- 稳定 ID、CSV 原始定义和已确认规则结果保留；旧 API、类名、场景绑定和存档格式不保留。

## 六、实施阶段

整个重构是一个 P1 工程，但内部形成可回退阶段提交。失败时回退当前阶段，不保留失败实现形成的兼容层。

### 阶段 0：冻结、隔离与行为基线

- 建立专用架构 worktree 和分支。
- 冻结 Unity Runtime、场景、CSV、导入器和相关 asset 功能开发。
- 内容生产只允许修改路径不冲突的设计文档。
- 固定最小行为基线：新建角色、世界、据点、悬赏、Adventure、战斗、结算、返回，以及当前已批准的保存和册界切片。
- 基线只记录输入、结果、稳定 ID 和状态变化，不记录旧 UI 布局或 Built-in 视觉。

验收：形成有限的重构验收清单，明确必须恢复的结果与允许删除的旧表现。

### 阶段 1：目标程序集骨架

- 建立目标目录、namespace 和 asmdef。
- 建立程序集依赖检查和对应测试程序集。
- 每个模块建立短 README，只记录职责、允许依赖、禁止依赖、公开入口和验证。
- 建立空 `Gameplay.Contracts` 和唯一 `Bootstrap` 壳。
- 检查 Domain 不引用 Feature，Feature 不引用兄弟 Feature，非 Bootstrap 不同时引用多个 Feature 实现，Editor 不进入 Player。

验收：空模块可编译、依赖图无循环，测试能捕获故意制造的非法引用。

### 阶段 2：Foundation 与 Spatial

- 选定唯一六角坐标类型。
- 迁移格位、范围、视线和空间查询。
- 允许为坐标与 namespace 统一机械更新 Character、Combat、Gameplay、Editor 和测试直接调用者，但不得改变这些调用者的业务状态所有权或规则语义。
- 从 `TacticalGridModel` 分离纯格位状态；EnvironmentProfile 数据、运行时和 Unity Content 转换仍由阶段 3 迁移。
- CTB 保留现有所有权，阶段 5 与 Combat 战术运行时一起从 Core 移出。
- 删除重复转换和旧 namespace。
- 建立坐标、邻接、范围、阻挡、方向和可达格纯测试。

验收：仓库只剩一套权威六角坐标语义；Spatial 不引用场景、Renderer、Character 或 Combat；既有 1v1／2v2 空间结果保持一致。

停止条件：两种坐标存在未记录语义差异时，先建立对照测试，不使用隐式转换掩盖；若机械调用更新之外仍必须提前改变 Character、Content 或 Combat 的业务所有权，则停止阶段 2。

### 阶段 3：Content 与导入链

- 分离不可变定义、Unity asset 适配和运行时状态。
- 迁移 EnvironmentProfile schema／runtime，并把依赖它们的 `SpatialQueryBoardFactory` 转换适配落到 `Infrastructure.UnityContent`；Spatial 只接收显式格位、边与查询限制输入。
- 建立领域导入器及共享读取、诊断和原子提交基础设施。
- 依次迁移 Character、Combat、Cultivation、World 和 Settlement 内容。
- 每个领域验证 CSV 到投影、asset、稳定 ID 和引用集合。
- 所有领域完成后删除 `DataConfigImporter` 单体。

验收：任一领域可独立导入；一个领域失败不写其他领域资产；全量导入确定性；共享工具不知道领域字段。

停止条件：需要跨领域半提交、静默默认 ID 或旧新资产双写。

### 阶段 4：Character、Cultivation 与 World

- 拆分 Character 身份、属性、资源、装载和成长引用。
- 建立独立 Cultivation 状态及道基、紫府和金丹子域。
- 拆分 Quest、Inventory、NPC、Bounty、Charter 和 WorldClock 所有者。
- 册界按定义、校验、候选、冲突、提交和结果重组。
- 每个状态所有者建立 Capture／Restore 或等价快照测试。

验收：Character 不持有 UI、场景或战斗控制器；Cultivation 不依赖 Character 实现；World 不存在共享可变状态桶；册界只有一个长期提交入口；纯规则测试不打开场景。

停止条件：为拆循环而创建承载大量无关接口的万能 Contracts。

### 阶段 5：Combat 与战术运行时

- 将 CTB 从 Core 移入 `TianZhang.Combat.Turns`，并在 Character 已完成阶段 4 拆分后建立战斗快照输入，不保留 Character 对 CTB 运行时状态的所有权。
- 将战斗输入固定为 CombatantSnapshot 和攻击档案投影。
- 拆分会话、调度、命令、结算、单位集合和结果。
- EnemyAI 只消费合法行动集合。
- Renderer、按钮、日志和动画移出 Combat。
- 删除 `TacticalCombatController` 的旧 Hub 职责。

验收：Combat 可在无 Scene、MonoBehaviour 和 UI 的测试中确定性运行；CTB、伤害、范围、拒绝原因和 1v1／2v2 关键规则通过；Combat 不引用 Character 或 Feature 实现。

停止条件：迁移开始改变 BattleSim 数值语义或需要用临时公式保持编译。

### 阶段 6：GameRuntime、保存与应用用例

- 建立薄 GameRuntime 和独立状态所有者。
- 建立新的保存 schema 1，不迁移旧存档。
- 保存信封组合各模块快照，不实现模块规则。
- 建立新游戏、清空、保存、恢复和失败关闭。
- 建立导航契约与进入／返回上下文。
- 悬赏、NPC 修炼和册界调用改为独立用例。

验收：GameRuntime 无战斗、悬赏、册界或修炼算法；恢复失败不产生半状态；新档与清空共用初始化入口；Feature 只能通过用例和契约修改状态。

### 阶段 7：Feature、正式场景与最小 UI

- 重写 CharacterCreation、WorldMap、Settlement、Adventure 和 CombatPresentation。
- 建立唯一 Bootstrap 和新正式场景壳。
- 将 SceneBuilder 拆为逐场景 builder 和独立 validator。
- 重建最小可操作 UI，不恢复旧视觉样式。
- Adventure 通过新 Combat API 启动战斗并消费结果。
- 删除 `ExplorationController`、旧 BattleUIManager 和旧场景入口。

端到端验收：

```text
新建角色
-> 世界
-> 据点
-> 悬赏
-> Adventure
-> 战斗
-> 结算
-> 返回
-> 保存／读取后关键状态一致
```

同时确认 Build Settings 只有一套正式入口、Feature 无兄弟实现引用、每个场景只有一个组合根、Hybrid Prototype 不是正式依赖。Built-in 材质、旧 Shader 和旧布局不作为验收项。

### 阶段 8：遗留删除与上下文结构

- 删除空 `TianZhang.Runtime.asmdef`、旧 asmref、废弃 namespace、旧场景和原型入口。
- 扫描旧类名、GUID、Resources key、UnityEvent、Animator 和序列化引用。
- 清理一次性 TQ 脚本和已被正式测试替代的探针。
- 刷新根 `UNITY_STRUCTURE.md`。
- 建立 `UNITY_STRUCTURE.assemblies.md`、`UNITY_STRUCTURE.runtime.md`、`UNITY_STRUCTURE.content.md` 和 `UNITY_STRUCTURE.ui.md`。
- 更新美术主线对旧 Adventure／Exploration 所有者的引用。

验收：没有旧运行时类型的 C#、场景、Prefab 或资源引用；结构图与实时 asmdef、路径和正式场景一致；普通 Unity 任务只需根索引、一个聚焦结构图、模块 README 和目标逻辑单元。

### 阶段 9：总验收与 URP 交接

- Unity EditMode 全套通过。
- 新正式薄切片 PlayMode／批处理流程通过。
- 数据链、asmdef 依赖、旧引用、文本和差异检查通过。

## 七、文档与上下文治理

### 7.1 结构文档

根 `UNITY_STRUCTURE.md` 只保存：

```text
项目与 Unity 版本
正式场景入口
聚焦结构图路由
验证入口
不可触碰区域
最后核验日期
```

根结构图不记录任务 ID、排期、待办或历史完成状态。详细结构按 assemblies、runtime、content 和 ui 分开；普通任务只读取命中的一个聚焦图。

### 7.2 模块 README

每个命名程序集放一份短 README，固定回答：

```text
职责
公开入口
允许依赖
禁止依赖
运行时所有者
数据／配置来源
直接测试
常见修改路由
```

README 不复制完整设计规则、任务状态、历史记录或全部类和方法。实现变化但边界未变时不机械刷新。

### 7.3 普通任务读取顺序

```text
任务卡
-> 根结构索引
-> 一个聚焦结构图
-> 一个模块 README
-> 目标符号与直接测试
```

只有发现真实跨模块依赖时才扩展。任务卡使用 `文档#章节`、`代码::类型.方法`、`数据::稳定ID`、`场景::对象／组件` 与 `程序集::公开契约`，不得把整个 Gameplay 或目录写成默认必读范围。

### 7.4 文件与文档拆分信号

代码在以下情况下要求职责拆分：

- 修改一个行为必须理解三个以上无关职责。
- 一个类型同时拥有领域状态、场景生命周期、UI 和资源加载。
- 多个模块直接读取其内部可变字段。
- 测试无法在不启动无关系统时构造目标。
- 多个任务持续修改同一中心类的互不相关区域。

设计文档只在存在多个事实所有者、不同任务长期读取互不相关部分、独立稳定 ID／审核边界或无关章节反复进入上下文时拆分，不按行数机械拆分。

`docs/superpowers/plans/` 默认视为实施历史；普通任务不读取。`specs/` 只有被当前任务卡、现行规则或用户明确引用时才进入上下文。

### 7.5 防退化闸门

机器检查：

- asmdef 依赖方向。
- Feature 不引用兄弟 Feature。
- Domain 不引用 Presentation、Bootstrap 或 Editor。
- Editor 不进入 Player。
- 正式 Build Settings 场景与唯一 Bootstrap。
- 旧类名和旧入口不在运行时代码或序列化资产中重新出现；设计与迁移文档中的历史名称不计入失败。
- JSON／asmdef 可解析。
- 新增 `*.g.cs` 带自动生成标记。

Codex 架构复审：

- 类型是否承担多个主要职责。
- Contract 是否承载实现逻辑。
- Bootstrap 是否承载业务逻辑。
- README／结构图是否复制任务状态或实现细节。
- 拆分是否真正减少依赖而非增加转发层。
- 大型手写单文件保持单体的理由是否成立。

项目负责人不承担代码审查。遇到产品取舍时，Codex 必须将问题转换为非代码化的选项、影响和建议后请求决定。

### 7.6 一次性上下文验收

选择四个真实任务进行只读演练：

1. 修改一条 Combat 规则。
2. 增加一种 Cultivation 状态。
3. 修改 Settlement 的一个交互。
4. 修改 Adventure 的进入／返回流程。

每项确认能从任务卡一次找到唯一模块，只需一个聚焦结构图和模块 README，无需读取整个 Gameplay、GameSession 或 DataConfigImporter，同时取得完整目标逻辑单元、直接契约和测试。

本验收不建立长期 token 统计系统。

### 8.2 主责与架构证据

- 八个子任务均由 Codex 主责。
- 每个子任务实施后进入独立架构复审；复审不预读整个项目。
- 复审未通过时只返工当前阶段，不提前修改下游。
- 外部责任方不得修改本轮架构边界，但可以继续路径不冲突的内容文档工作。

每阶段提交：

```text
旧职责与所有者
新职责与所有者

迁移后依赖
删除与新增的依赖边
公开契约
验证结果
未迁移范围
大型单文件例外理由（如适用）
```

### 8.3 队列关系

- 当前已经运行的内容任务不在中途抢占，先达到合法终态。
- 随后将 `U-ARCH-REBUILD-01A` 作为 P1 `codex_execute` 插入 ready 队首。
- 01B～01H 依序 blocked，只在前项通过后逐项解锁。
- `U-URP-PREFLIGHT-01` 显式阻塞于 01H。
- Blender、项目骨架和 AI 3D 平台评估在路径与责任方独立时可并行，但不得向 Unity 正式路径接入资产。
- 筑基、金丹和其他非阻断玩法任务维持 P2，不在架构期间修改 Runtime、CSV 或导入器。

本文只冻结这一关系；实际任务卡、backlog 和队列修改必须在本设计书面复核后作为独立管理迁移执行。

### 8.4 分支与提交

- 使用专用架构 worktree 和长期重构分支。
- 01A～01H 每项形成独立提交和验证结果。
- 一个提交只包含该子任务声明路径。
- 当前阶段未通过时不得用下游提交补齐。
- 失败时回退当前阶段提交，不保留旧新双轨。
- 最终集成前在最新 `master` 上重放完整分支并重新运行总验收。
- 活动 run、集成锁、taskId 占用或主工作区路径冲突任一存在时停止集成。
- 用户既有未提交修改不纳入架构提交。

## 十一、共同停止条件与回退

出现以下任一情况，停止当前阶段并回到根因：

- 新边界产生程序集循环。
- 同一状态出现两个运行时写入者。
- 为兼容旧代码开始增加长期 adapter、双写或 fallback。
- 领域规则迁移结果与已验证输入不一致。
- 重构开始修改游戏设计、数值或未批准内容。
- 当前阶段必须跨越两个以上未完成的下游边界才能验证。
- URP、3D 角色或正式美术提前混入架构阶段。
- Content 导入需要跨领域半提交或静默默认 ID。
- Unity 序列化引用无法证明旧入口已清除。
- 修复开始连续叠加补丁或扩大超过当前子任务边界。

回退只使用阶段提交或重新设计当前边界，不保留失败实现形成的平行系统。若现有纯规则无法在新边界中无损迁移，保留失败证据并请求产品语义决定，而不是猜测性重写。
