# 《天章》运行时角色美术与模块化外观设计

> 日期：2026-08-05
>
> 状态：设计对话已批准；本文只锁定角色承载、模块化外观、资源职责与实施闸门，不代表已经完成 URP、模型、动画、创角 UI、装备外观或正式场景接入。
>
> 事实源：玩法与场景状态读取现行 `docs/`、`开发管理/设计-当前状态.txt` 与 `src/`；美术原始文件和正式导出边界读取 `docs/资源管理/美术资源版本管理规范.md`。

## 一、决策摘要

1. 运行时角色采用真实低模 3D，不采用把全身立绘缩小、始终朝向镜头的 Billboard，也不采用像素角色作为主方向。
2. 整体表现定位为固定正交斜俯视的 2.5D“水墨棋偶”：低饱和手绘贴图、分档明暗、克制描边、清晰轮廓和有限附加骨骼。
3. 当前项目仍使用 Built-in Render Pipeline。正式角色美术生产前先独立迁移 URP；迁移不得与角色模型、外观数据或换装逻辑混在同一任务中。
4. 玩家需要有限模块化的外观创建和换装，不建设完整捏脸、身体滑杆或上下装散件组合。
5. 首版玩家提供男、女两套基础体型，二者共用同一 Humanoid 骨架和动画；每套整身服装分别提供两种体型的适配网格。
6. 重要 NPC 继续使用独立精绘水墨立绘。玩家拥有由外观模块组合的标准姿势全身水墨立绘；角色详情显示全身，对话和行动轴分别裁切同一合成结果。
7. 玩家立绘的最终线稿、水彩、人物比例和精细度不在本设计中批准。正式图层生产前必须另做风格样张评审；本轮生成的视觉草图只说明载体和数据关系，不是正式资源。
8. 人形角色按人形骨架族群复用动画；妖兽不套用人形骨架。首批只建设当前正式内容需要的人形族群和石甲兽重型四足族群。
9. 现有 `HybridTacticalPrototype.unity` 继续作为隔离的 2.5D 表现测试台，不拥有第二套 CTB 或战斗规则；实际玩家与石甲兽对战只在正式战斗所有者接入后验证。

## 二、当前事实与问题

### 2.1 玩法与镜头约束

- 游戏是 2D 沙盒世界、六角格战棋玩法的修仙游戏，战斗使用 CTB。
- 单位具有六个明确朝向；移动、攻击、视野、作用路径、高度和占位读取共享六角规则数据。
- 2.5D 只改变表现。Unity `Transform`、碰撞体、模型高度、动画位移和相机不能成为规则事实源。
- `HybridTacticalPrototype.unity` 已有正交斜俯视相机、立体六角地块、点击选格、高亮与共享空间查询，但当前单位仍是 Billboard 标记，场景也不包含正式 `AdventureSceneController` 或 CTB 战斗。

### 2.2 当前角色美术状态

- 已生成苻渊、谢观微两名重要 NPC 的无字立绘、题字氛围版和透明对话立绘。
- 这些立绘使用干笔线稿、半透明水彩、低饱和配色和纸张质感，适合对话、角色详情和剧情演出，不适合直接缩成六角格行动单位。
- 2D 正式 Adventure 表现和隔离 2.5D 原型均仍使用圆点或简单 Billboard 单位标记。
- `src/Assets/Art/` 尚未建立正式角色模型、材质、动画和 Prefab 生产链。

### 2.3 当前数据边界

- `CharacterCreationDraft` 当前只保存姓名、路线、灵根、出身、先天属性、命格标签与技艺分配，没有外观字段。
- `CharacterData` 当前没有外观档案、模型、服装、发型或头像图层引用。
- 当前装备相关字段只覆盖战斗攻击档案等规则引用，不存在可供外观系统直接消费的完整装备模型槽位。
- 因此模块化外观是新的独立数据与表现系统，不能塞入属性、术法、基础攻击或场景渲染字段。

## 三、目标与非目标

### 3.1 目标

1. 建立适配斜俯视六角格的统一运行时角色风格。
2. 让玩家在创建角色时拥有足够明确的外观身份，并允许少量关键换装结果改变模型。
3. 让主场景中实际出现的玩家单位与战斗单位复用模型、骨骼、材质和动画。
4. 让玩家全身立绘、对话半身和战斗头像与当前外观保持一致。
5. 让人形和首个正式非人形敌人分别证明骨骼族群、动画和 2.5D 渲染管线。
6. 保持表现层只消费规则结果，不建立平行占位、移动、战斗、装备或存档所有者。

### 3.2 非目标

- 不建设面部滑杆、独立眼鼻嘴组合、身高胖瘦滑杆或自由骨骼比例。
- 不建设上衣、裤子、袖子、手套、鞋靴的任意散件组合。
- 不建设布料模拟、发丝模拟、动态破损、自由镜头或首版 LOD。
- 不要求每件数值装备都改变外观。
- 不因角色模型任务把节点式 `WorldScene` 或当前面板式 `SettlementScene` 改造成三维行走场景。
- 不在隔离 2.5D 原型中复制 CTB、战斗 UI、AI、伤害或正式遭遇流程。
- 不在本设计中批准玩家立绘的最终风格样张。

## 四、运行时角色美术方向

### 4.1 承载方式

- 角色是完整 3D 模型，能够随单位规则朝向旋转到六个六角方向。
- 模型移动只表现共享规则已经批准的路径。首版禁用动画 Root Motion，动画不能自行改变规则坐标。
- 主场景和战斗场景只有在实际渲染可行动单位时才消费完整模型；节点图、菜单和纯面板不为了展示模型而改变职责。
- 重要 NPC 的高精度立绘与运行模型允许细节层级不同，但必须统一轮廓、主配色、发型、服装结构和标志物。

### 4.2 比例与模型复杂度

- 人形采用约 4.5 至 5 头身的适度变形比例，放大头部、手部、袖袍、武器和身份标志物。
- 普通人形建议控制在约 8,000 至 15,000 三角面；普通妖兽建议控制在约 8,000 至 20,000 三角面。预算服务生产一致性，不作为运行时规则或硬性数值事实。
- 头发、发冠、宽袖、下摆、甲壳和尾部优先以大块面形成轮廓，不制作需要近景才能观察的细碎结构。
- 角色立足点统一为底部中心，模型原点、朝向、缩放、绑定姿势和骨骼命名必须由导出规范固定。

### 4.3 材质与光照

- URP 迁移完成后再确定正式角色 Shader；目标是两至三档明暗、低强度轮廓线、低饱和手绘颜色与克制阴影。
- 普通单位以一张 1024×1024 手绘贴图图集为默认范围，优先表达色块、笔触和材质区分；不建立普遍适用的复杂金属度、粗糙度和法线贴图链。
- 地脉、灵纹等高亮默认不持续发光，只在明确的施法、受激或选中表现中短时增强。
- 阵营、选中和受击反馈通过独立表现参数或效果实现，不永久污染角色基础贴图。

## 五、URP 独立迁移闸门

### 5.1 迁移范围

1. 安装与当前 Unity 版本相容的 URP 包。
2. 创建并绑定项目的 URP Pipeline Asset 与各 Quality 等级配置。
3. 处理现有 Tilemap、Sprite、UI、TextMesh Pro、六角地块、透明高亮和场景材质的兼容性。
4. 验证相机、透明排序、选格射线、色彩空间和场景入口。

### 5.2 迁移边界

- URP 迁移任务不新增角色模型、外观字段、换装组件、动画或正式美术资源。
- 迁移失败不得通过复制场景、保留两套渲染管线或增加静默材质回退掩盖。
- 正式场景、UI、Tilemap、高亮与选格行为未保持一致前，不启动角色美术技术样例。

## 六、骨骼族群与动画

### 6.1 人形族群

- 玩家、普通修士、魔修和人形 NPC 使用统一 Humanoid 骨架、Avatar 和 Animator 契约。
- 男、女基础体型共用骨骼名称、绑定姿势和动画，不因体型选择改变碰撞、占格、规则体型或数值。
- 首批基础动作至少覆盖待机、移动、受击、倒地、基础攻击、施法／能力和防御表现。
- 六向移动不制作六套独立移动动画；角色根节点按规则朝向旋转，播放同一族群的移动动画。

### 6.2 非人形族群

- 妖兽按形体族群复用骨架，不为每个物种默认创建专属运行框架，也不强行套用人形骨架。
- 当前首个非人形族群是重型四足，服务正式石甲兽：厚甲、迟缓、近战和格挡倾向必须在轮廓与动作节奏中可读。
- 石甲兽首批动作覆盖待机、移动、受击、倒地、基础攻击和防御。
- 飞禽、轻型四足、蛇虫、灵体和大型首领只在对应正式内容进入生产时新增族群或专属骨架，本设计不提前建设空目录与空控制器。

## 七、玩家有限模块化范围

### 7.1 角色创建内容

首版批准以下可见选择：

| 类别 | 首版范围 | 实现原则 |
|---|---:|---|
| 基础体型 | 男、女各一套 | 共用骨架与动画，不影响规则 |
| 脸型 | 每种体型 3 个完整预设 | 不拆眼鼻嘴滑杆 |
| 肤色 | 4 档 | 材质预设，不复制模型 |
| 发型 | 6 种 | 固定锚点，避免发丝模拟 |
| 发色 | 6 种 | 低饱和材质预设 |
| 初始服装 | 3 套 | 整身 Outfit，不拆上下装 |
| 服装辅色 | 少量项目预设 | 不开放任意取色器 |

### 7.2 运行时槽位

1. `Body`：男／女基础身体。
2. `Head`：脸型与肤色。
3. `Hair`：发型与发色。
4. `Headwear`：发冠、斗笠等；资源明确声明与发型的隐藏关系。
5. `Outfit`：整套服装，包含上衣、袖袍、下装和鞋靴；同一服装 ID 下提供两种体型网格。
6. `MainHand`：剑、刀、扇、杖等主要器物。
7. `Artifact`：背负或悬浮法器；首版使用固定挂点，不模拟复杂环绕轨迹。

### 7.3 换装边界

- 只有承担主要身份辨识的服装、武器、法器和头饰改变模型。
- 装备规则继续决定实际装备；外观系统只消费已批准的可见投影，不复制装备库存、属性、攻击档案或限制规则。
- 合法空槽使用明确的 `none`，缺失引用不能被解释为空槽。

## 八、玩家模块化立绘

### 8.1 载体

- 玩家拥有标准姿势的模块化全身 2D 立绘，不使用固定主角立绘，也不把实时低模 3D 模型直接放大作为最终对话立绘。
- 角色创建和角色详情显示完整合成立绘；对话框裁切同一合成结果的半身区域；行动轴与小头像裁切头肩区域。
- 外观变化后重新组合一次并缓存，不为每个 UI 表面分别生成不同身份结果。

### 8.2 图层顺序

建议的稳定图层顺序为：

1. 后层长发与背后器物。
2. 基础身体、肤色与脸型。
3. 整套服装。
4. 面部细节。
5. 前层头发。
6. 头饰。
7. 主手器物。
8. 前景法器或明确的附加层。

每个图层必须使用统一画布、姿势、锚点、遮罩和裁切边界。发际线、颈部、肩部、衣领、器物带和手部是首批必须验证的组合接缝。

### 8.3 NPC 与玩家的差异

- 重要 NPC 继续拥有独立姿态、独立构图和氛围处理的精绘立绘。
- 玩家立绘为了组合采用统一姿势和锚点，但线稿、水彩、纸张质感和配色体系应由后续风格样张评审向现有 NPC 立绘靠齐。
- 每个玩家外观选项需要提供对应的 3D 运行模块和 2D 立绘图层；二者共享稳定外观 ID，但不是同一文件或运行时互转结果。
- 本轮预览图不作为最终风格批准证据，也不进入 `src/Assets/Art/` 或美术资源登记册。

## 九、数据职责与组装流程

### 9.1 AppearanceProfile

外观档案只保存稳定 ID 与有限颜色预设，例如：

- `bodyTypeId`
- `facePresetId`
- `skinToneId`
- `hairStyleId`
- `hairColorId`
- `outfitVisualId`
- `outfitPaletteId`
- `headwearVisualId`
- `mainHandVisualId`
- `artifactVisualId`

外观档案不保存战斗属性、装备属性、技能、骨骼 Transform、Prefab 实例或 UI 裁切结果。

### 9.2 AppearanceCatalog

- 作为外观稳定 ID 到 3D 模块、2D 立绘图层、材质预设、挂点和兼容声明的唯一目录。
- 同一 Outfit ID 显式引用男、女两份适配网格和对应立绘图层。
- 发型／头饰隐藏关系、武器握持挂点与法器挂点由资源声明，不由组装器按名称猜测。

### 9.3 CharacterVisualAssembler

- 只读取已验证的 AppearanceProfile 和 AppearanceCatalog，组装运行时模型。
- 负责把兼容的 SkinnedMeshRenderer 绑定到共享人形骨骼，把器物挂到批准挂点，并应用材质预设。
- 不读取或修改角色创建预算、装备属性、库存、CTB、六角占位、AI 或存档事务。

### 9.4 PortraitComposer

- 读取与 AppearanceProfile 相同的稳定 ID，从目录取得对齐的 2D 图层并按固定顺序合成。
- 只产出全身立绘缓存及其裁切结果，不反写外观档案，也不从 3D 模型截图推导身份。
- 缓存失效只由外观 ID 或明确的立绘版本变化触发。

### 9.5 装备外观投影

- 装备系统或角色会话提供已确认的可见装备结果。
- 窄投影层把允许显示的装备 ID 映射为 `mainHandVisualId`、`artifactVisualId` 或 Outfit 变化。
- 投影失败不得更改实际装备；外观层不能通过模型反推装备规则。

## 十、错误处理与存档边界

- 未知外观 ID、缺失目录条目、缺少对应体型网格、骨骼名称不一致、挂点缺失或立绘图层尺寸错误均属于内容错误，拒绝组装并报告稳定原因。
- 不使用随机服装、相近 ID、另一体型网格或默认 Prefab 静默替代错误资源。
- `none` 只表示被 schema 明确允许的空头饰、空器物等合法状态。
- 存档只保存外观稳定 ID 与预设值，不保存 Unity 对象引用和运行时缓存。
- 当前存档不存在外观字段；正式接入前必须另立 schema 与旧档迁移任务。迁移策略不得由本设计中的样例值自动推导。

## 十一、资源目录与生产流程

### 11.1 目录建议

原始工程保存在 `assets/source/characters/`，正式 Unity 导出保存在 `src/Assets/Art/Characters/`。正式目录按用途分为：

- `Common/Rigs/`
- `Humanoid/Bodies/`
- `Humanoid/Heads/`
- `Humanoid/Hair/`
- `Humanoid/Outfits/`
- `Humanoid/Weapons/`
- `Humanoid/Artifacts/`
- `Monsters/Shijiahou/`
- `Animations/Humanoid/`
- `Animations/QuadrupedHeavy/`
- `PortraitLayers/`
- `Materials/`
- `Shaders/`

目录只在对应正式资源首次生产时创建，不预建空目录。

### 11.2 单批资源流程

1. 在 `assets/source/` 编辑 Blender、源贴图和分层立绘工程。
2. 按统一单位、朝向、原点、骨骼、Avatar、画布和锚点导出。
3. 把 FBX、贴图、动画、材质、Prefab 与 2D 图层导入 `src/Assets/Art/`。
4. 创建或更新 AppearanceCatalog 条目。
5. 更新 `docs/资源管理/美术资源登记册.md`。
6. 运行资源版本、Unity 导入、组合和场景验证后再提交正式导出资源。
7. 原始工程按现有规范备份，不能用网盘替代 Git 中的正式构建资源。

## 十二、实施顺序

### 12.1 URP 独立迁移

先完成第五章的迁移与正式场景回归，不生产角色资产。

### 12.2 2.5D 表现测试台

- 在现有 `HybridTacticalPrototype.unity` 上建立真实 3D 单位的表现接口。
- 使用几何占位体先验证模型缩放、六向旋转、地块高度、阴影、选中反馈和摄像机裁切。
- 场景仍不接入 CTB、AI、伤害和正式遭遇。

### 12.3 模块化人形技术样例

制作男、女基础体型、各一个脸型、两种发型、一套双体型服装和一件主手器物；接入共享骨骼与基础动画，证明换装、转向和 Toon 材质。

### 12.4 石甲兽技术样例

制作重型四足骨架、石甲兽模型和批准动作，证明非人形管线而不改变其 AI、攻击档案或数值。

### 12.5 外观与立绘数据切片

建立 AppearanceProfile、AppearanceCatalog、CharacterVisualAssembler 与 PortraitComposer 的最小数据闭环；先消费技术样例，不一次生产全部创角内容。

### 12.6 风格样张闸门

- 分别评审角色模型的 Toon 材质样张与玩家模块化全身立绘样张。
- 玩家立绘必须与现有 NPC 立绘并排比较；在风格获批前只保留技术图层样例，不批量生产脸型、发型和服装立绘。

### 12.7 正式 Adventure 接入

- 让正式 Adventure／战斗渲染路径消费已经验证的 3D 单位表现。
- 实际玩家与石甲兽 CTB 对战只在正式 `TacticalCombatController` 和既有场景所有者中运行。
- 隔离原型不升级为第二正式战斗场景。

### 12.8 创角内容扩充

技术、风格、数据与存档闸门全部通过后，再补齐第七章批准的脸型、发型、颜色和三套初始服装，并接入正式角色创建 UI。

## 十三、验证矩阵

| 范围 | 必须证明的结果 |
|---|---|
| URP 迁移 | 正式场景入口、相机、UI、Tilemap、透明高亮、选格和已有验证保持成立 |
| 模型导入 | 单位、缩放、原点、朝向、Avatar、骨骼名称和挂点符合统一规范 |
| 人形组合 | 两种体型与所有已生产脸型、发型、服装和器物条目可由目录完整解析 |
| 立绘组合 | 全身、半身和头像来自同一 AppearanceProfile，图层无缺失、错位或错误遮挡 |
| 动画 | 六个规则朝向、高低地块、待机、移动、受击、倒地、攻击、施法／能力和防御没有脱骨或明显悬空 |
| 妖兽 | 石甲兽使用重型四足骨架并保持厚甲、迟缓、近战和防御辨识，不读取人形外观档案 |
| 存档 | 保存、读取与跨场景返回后外观稳定 ID 不变，缓存可重建 |
| 装备投影 | 换装改变表现但不改变或复制装备属性与战斗规则 |
| 空间一致性 | 接入模型前后的六角坐标、占位、可达格、射程、视线、拒绝原因和战斗结果一致 |
| 目标尺度 | 固定正交镜头下可辨认阵营、朝向、武器、服装轮廓和石甲兽动作意图 |

视觉检查只验证表现，不替代共享规则日志与既有自动测试。正式资源批次仍需按影响路径运行项目规定的数据链、Unity 和资源版本检查。

## 十四、停止条件

命中以下任一条件时停止当前切片并回到对应根因，不连续叠加补丁：

1. URP 迁移需要修改 CTB、六角空间、伤害、AI 或场景流转规则。
2. 为支持单个服装必须更换人形骨架、复制 Animator 或增加体型专用规则状态。
3. 外观系统开始拥有装备库存、装备属性、角色创建预算或存档事务。
4. 2.5D 原型开始复制正式战斗循环、战斗 UI 或正式遭遇数据。
5. 正式接入要求把节点式 WorldScene 或当前 SettlementScene 改造成新的可行走场景。
6. 缺失资源只能依靠随机替代、相近 ID、静默默认模型或多层兼容分支继续运行。
7. 玩家模块化立绘无法在固定锚点下保持脸型、发型、衣领、器物与遮挡一致；此时回到立绘图层规范，不扩大运行时修补。
