# 每日自动化简报与每周项目总结设计

## 目标

在不增加项目写入者的前提下，调整现有每日自动化简报的阅读逻辑，并新增每周一次的只读项目总结：

- 每日简报从“提交审计清单”改为“自动化推进日报”，说明自动化在时间窗内形成的净成果、未闭环事项和当前后续顺序。
- 每周总结覆盖自动化与人工形成的全部可验证项目进展，说明当前阶段、主要风险和下一周最多三项重点。
- `tzg-hourly-controller` 继续是唯一项目写入入口；日报和周报都不得修改项目文件、执行业务任务、stage 或 commit。

## 当前问题

现有 `tools/get-automation-briefing-source.ps1` 已能从 Automation 提交元数据和提交快照中的任务卡正确区分 `completed`、`blocked`、`frozen`、`pending_decision`、`waiting_reply`、`pending_review` 与 `queue_maintenance`。当前主要问题不在证据提取，而在报告组织：

1. 日报仍以提交和卡片变化为中心，用户需要自行判断一天实际推进了哪些目标。
2. 卡片清理、同一任务的多个闭环提交和队列维护容易占据正文，但不一定代表独立业务成果。
3. 日报没有显示当前队首，因此不能直接回答自动化接下来会做什么。
4. 项目没有一个低频、跨人工与自动化来源的只读阶段总结；交互式“总结”工作流又包含管理文件维护，不适合直接定时执行。

## 职责边界

### 每日自动化简报

- 只汇总带有效 `Automation: tzg-hourly-controller` 元数据的业务提交。
- 只负责解释自动化推进，不纳入普通人工提交。
- 可以读取当前队列和相关任务卡形成运行结束时的后续快照。
- 不代做领域复审，不把提交中的 `Verify` 声明升级为本次重新验证的结论。

### 每周项目总结

- 汇总时间窗内全部 Git 提交，包括自动化与人工提交。
- 以 `docs/`、`开发管理/`、BattleSim 实际结果和 `src/` 当前行为的既有事实边界核验结论；不以提交标题或 automation memory 猜测成果。
- 只读当前队列、任务卡、任务归档、`设计-当前状态.txt` 和与本周变化直接相关的分线 backlog。
- 不执行交互式 `开发管理/总结规则.txt` 中的写入步骤，不维护队列、状态、backlog 或历史摘要。

## 每日简报数据流

1. 以本次运行时间为 `Until`，以上次运行时间为 `Since`，调用现有 `tools/get-automation-briefing-source.ps1`。
2. 按 `Task` 合并同一任务的多个候选提交，以窗口内最新候选提交的已核验任务生命周期作为分类。
3. 对候选提交只读取支持 `Result`、`Impact` 和 `Verify` 所需的最小 diff；不重跑业务验证。
4. 将卡片清理、补充闭环和同一任务的中间提交折叠到该任务，不重复计为独立成果。
5. `queue_maintenance` 仅在实际改变 ready 候选、固定顺序、依赖或阻塞时进入正文；普通维护细节不作为独立业务成果。
6. 在报告结束前只读 `开发管理/当前任务队列.txt`，并按既有顺序读取队首最多三张任务卡，形成带明确快照时间的“接下来”段。

`get-automation-briefing-source.ps1` 的现有职责和输出结构已经满足本次调整，不新增第二个日报数据源脚本。

## 每日简报输出

固定使用以下四段，空段省略：

1. **净成果**：按任务说明解决的问题、实际产出、已确认影响和元数据声明的验证。
2. **未闭环**：只列 `blocked`、`frozen`、`pending_decision`、`waiting_reply` 与 `pending_review`，并说明继续推进所缺条件。
3. **接下来**：列当前固定队列的前三项及已知直接依赖，不自行重排。
4. **异常**：只在元数据无效、生命周期无法核验、提交与 diff 不符、工作区存在未提交路径或 runtime 存在异常时输出。

没有候选业务提交时，明确说明本时间窗没有有效自动化业务成果，但仍可显示当前队首；不得使用旧 memory 填充成果。

## 每周总结数据流

1. 新建独立只读 cron 自动化 `TZG Weekly Project Summary`，每周一 02:00 按 `Asia/Hong_Kong` 项目本地时间运行。
2. 周报 memory 只保存最近一次成功总结的 `Until` 游标。memory 不保存或替代项目成果事实。
3. 正常运行从上次成功游标汇总至本次运行时间；首次运行回看七天。只有成功形成总结后才推进游标，因此失败或错过的轮次由下一次继续覆盖。
4. 读取时间窗内全部 Git 提交的标题、时间、元数据和变更统计；只对拟写入成果的提交读取必要 diff。
5. Automation 提交按 `Task` 和任务生命周期归并。人工提交通过任务卡、任务归档或其修改的权威事实源确认结果；无法确定完整逻辑单元时只列为数据质量问题，不按标题推断。
6. 读取 `开发管理/设计-当前状态.txt`、当前有序队列、相关活跃任务卡和本周变化直接涉及的分线 backlog，形成当前阶段与后续快照。
7. 可通过 `tools/hourly-automation-lease.ps1 -Action Show` 只读检查控制面；有效租约属于正常运行状态，只有逻辑暂停、遗留 recovery 或其他需人工介入的状态才进入风险段。
8. 只用 `git status --short` 判断是否存在未提交路径，不读取或归因无关工作区 diff。

## 每周总结输出

固定使用以下五段：

1. **本周阶段结论**：一句话说明项目当前所处阶段及本周净变化。
2. **已验证进展**：按本周实际涉及的领域归组，例如数据、BattleSim、Unity、内容和管理；不按提交时间逐条流水记账。
3. **当前状态**：说明 ready 队列、关键依赖以及仍未闭环的任务状态。
4. **风险与决定**：只列会影响后续推进、需要人工决定或存在证据冲突的事项。
5. **下周重点**：严格按当前固定队列给出最多三项，不创建任务、不补位、不重排。

人工与自动化来源只在归因有助于理解复审状态或证据强度时标注，不把来源本身当作成果分类。

## 失败与数据质量处理

- 日报候选源执行失败时，报告 `source_error`，不输出旧成果。
- 周报无法读取 Git、当前队列或必要权威事实源时，不推进成功游标，并明确说明总结未完成及缺失边界。
- 元数据缺失、重复或与 diff 不符时单列数据质量问题，不猜测 `Result`、`Impact`、`Verify` 或任务状态。
- 提交快照与当前任务事实不同时，时间窗成果使用提交时事实，当前状态使用运行结束时事实，并明确两者时间边界。
- 工作区未提交内容只报告路径数量或路径列表，不读取无关内容、不归因、不纳入成果。
- 日报和周报不得因发现队列过期、状态冲突或 backlog 缺口而自行修复；只报告给用户或留待每小时控制器的合法责任方处理。

## 配置与事实源

实施时：

- 更新项目内权威提示 `开发管理/自动化简报提示词.txt`，再通过自动化管理能力完整同步现有 `tzg-daily-automation-briefing`；保留其名称、每日 01:00 调度、项目、模型、推理强度、通知策略和 `ACTIVE` 状态。
- 新增 `开发管理/每周项目总结提示词.txt` 作为周报权威提示。
- 通过自动化管理能力创建 `TZG Weekly Project Summary`；使用当前天章项目、本地执行环境、`gpt-5.6-terra`、`medium` 推理强度、周一 02:00 调度和 `ACTIVE` 状态。
- 最小扩展现有 `tools/check-automation-workflow.ps1` 及其测试：要求周报配置与权威提示完全一致，并在一致后将日报和周报识别为只读自动化；其他启用项仍按写入器处理。
- 不直接编辑用户级 `automation.toml`，不新增项目内 runtime、状态机、锁、恢复类型或写入脚本。

## 验收

### 静态验收

1. 日报权威提示与现有自动化 prompt 完整一致。
2. 周报权威提示与新自动化 prompt 完整一致。
3. 日报仍只消费 Automation 业务提交；周报明确覆盖全部可验证 Git 进展。
4. 两个提示均明确禁止修改项目文件、执行任务、stage 和 commit。
5. 日报为每日 01:00，周报为每周一 02:00；项目、模型和执行环境正确。
6. 三个启用自动化中只有 `tzg-hourly-controller` 承担项目写入职责。

### 行为验收

下一次自然日报应：

- 将同一 Task 的多个提交折叠为一个净结果；
- 不把普通卡片清理作为独立成果；
- 正确保留未闭环生命周期；
- 显示运行结束时的当前队首最多三项。

第一次自然周报应：

- 覆盖首次运行前七天；
- 同时识别可验证的自动化与人工成果；
- 按领域而非提交顺序组织；
- 给出当前阶段、风险和严格来自当前队列的最多三项下周重点；
- 成功后只更新用户级周报 memory 游标，不产生项目工作区变化。

## 非目标

- 不修改每小时控制器调度、租约、恢复或责任方调用逻辑。
- 不让日报或周报维护任务卡、队列、backlog、状态文件或归档。
- 不为周报新增项目成果数据库、中央 manifest、第二套任务索引或提交标签要求。
- 不把每周总结替代为交互式“总结”工作流，也不改变用户消息严格等于“总结”时的现有行为。
