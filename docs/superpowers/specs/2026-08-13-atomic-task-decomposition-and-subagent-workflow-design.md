# 原子任务拆分与子智能体协作工作流设计

状态：已批准并于 2026-08-13 按第一阶段实施。

日期：2026-08-13

## 一、问题与目标

当前手动会话与小时自动化都可能领取范围过大的任务。大任务由单一会话从调查、实现一路推进到全量验证时，容易出现上下文拥挤、超时、职责越界和遗漏；但若让自动化控制器动态建立子任务、调度多个执行者并合并多个候选，又会引入新的状态机、恢复和集成复杂度。

本设计采用两层控制：

1. 大型任务只在临近执行时按需检查；一旦确认无法原子闭环，就用一次专门的规划过程完整拆出全部子任务与依赖。
2. 单张原子任务卡内部允许主智能体按需使用子智能体，但对外仍保持单 taskId、单 owner run、单 worktree、单 candidate。

目标是在不扩展现有 schema 5 runtime 和集成协议的前提下，让 Codex、Claude Code、DeepSeek wrapper 与自动化责任链遵循一致的任务粒度与委派边界。

## 二、非目标

- 不让自动化控制器自行判断业务拆分方案或创建任务卡。
- 不新增子任务运行时、子智能体租约、嵌套 run、并行 candidate 或自动合并器。
- 不改变现有 taskId、owner、route、worktree、candidate、复审和排他集成锁合同。
- 不强制每个任务使用子智能体，也不以文件数量或表面难度作为唯一触发条件。
- 不采用实验性 agent team 作为项目基础设施。

## 三、定义

### 3.1 原子任务

一张任务卡同时满足以下条件时，才可作为 ready 执行单元：

- 只有一个明确结果，完成或失败可以独立判断。
- 所有者、允许路径、事实源、停止条件和验证命令已经冻结。
- 不依赖执行期间再决定公共接口、数据所有者、schema、产品语义或不可逆迁移方案。
- 可以由一个主智能体统一审查全部差异、运行最终验证并形成一个 candidate。
- 失败时能够在本任务边界内停止，不要求把半完成状态交给另一张并行任务继续补齐。

### 3.2 大型任务

命中以下任一情况时，说明当前任务可能过大；只有它即将进入 ready 或已经被选中执行时，规划／执行责任方才做最小范围判断。只要无法满足原子任务定义，就不得继续实施：

- 包含两个或以上可分别验收的成果。
- 跨越多个业务所有者、公共接口或相互独立的事实源。
- 实施、迁移和验证可形成不同的依赖阶段。
- 预期无法在一次正常自动化运行预算内完成直接验证和候选收口，或已有同范围超时证据。
- 若使用多个执行者，会需要修改相同逻辑单元、共享可变状态或频繁同步才能继续。

大型不等于单纯“文件多”。机械迁移即使跨很多文件，只要边界、变换和验证完全一致，仍可是一张原子任务；单文件修改若同时承担多个所有者裁决，也可能必须拆分。

## 四、临近执行时的一次性完整拆分规则

### 4.1 不做全量 backlog 预分析

- backlog 可以保留粗粒度父项、条件项和长期方向，不要求提前读取所有事实源或设计完整子任务树。
- 只有当前即将从 backlog 提升为 ready 的一项，或已经位于队首且即将开始写入的一项，才进行原子性检查。
- 检查只读取该项现有任务卡、直接依赖、预期路径、停止条件和验收入口；不为了判断大小而先做完整根因分析或遍历后续任务。
- 若当前项可原子闭环就直接执行；若确认需要拆分，再进入一次完整拆分，不检查其他 backlog 项。

### 4.2 父项与完整子任务集

- 大型父项只保存总目标、依赖关系与整体完成条件，不直接进入 ready 队列。
- 当前父项一旦判定需要拆分，规划责任方必须在同一次规划过程中读取完成拆分所需的直接事实，一次性建立全部已知子任务卡，不让父项在后续轮次反复进入“再拆一张”的流程。
- 每张子任务卡必须有独立 ID、明确前置、字面量 expectedPaths、单一结果、停止条件和最小充分验证。
- 子任务之间按真实数据或接口依赖排序；没有依赖且路径与所有者互不冲突时，才允许成为不同 taskId 的并行候选。
- 完整拆分必须给出全部子任务的依赖图、ready 起点和父项关闭条件；只有当前无前置依赖的第一批叶子进入队列，其余子项保持 blocked。
- 父项只有在全部子项完成并经过其规定的总验收后关闭；子项完成不得自动推导父项完成。
- 完成拆分后，父项只作为汇总状态存在，不再作为执行型任务被自动化领取。

### 4.3 最小原子性检查

当前任务临近执行时，只确认：

1. 不需要执行者在运行中重新选择所有者、schema、公共接口或验收口径。
2. 一个主智能体能够理解和复核全部预期差异。
3. 验证可以在单张卡内得出稳定结果。
4. 预计运行预算足以完成实施、直接验证和 candidate 收口。
5. 若以上任一项明显不成立，对当前父项执行一次性完整拆分；不顺带分析其他 backlog 项。

此检查是任务规划规则，不由自动化脚本使用行数、文件数或模型估算动态判定。

### 4.4 完整拆分中的调查

如果不做根因调查就无法安全确定完整子任务集，则调查属于本次拆分过程，而不是先投放一张业务执行卡再等待下一轮拆分：

- 规划责任方只读取确定所有者、直接根因、实际路径、依赖、停止条件和验收边界所需的事实，不实施业务修改。
- 调查可使用子智能体并行读取互不依赖的事实源，但最终拆分、依赖图和任务卡由主智能体统一形成。
- 完整子任务集形成前，不把父项或不完整的实现切片放入 ready 队列。
- 只有确实缺少用户／外部系统的不可推导决策时才建立 decision checkpoint；获得答案后一次性完成剩余拆分，而不是让业务 worker 逐轮试探。

## 五、原子任务内的子智能体规则

### 5.1 使用条件

主智能体仅在存在边界清晰、可独立返回结果的工作面时使用子智能体，例如：

- 分别调查不同模块或事实源。
- 独立核对测试、数据链或失败证据。
- 对互不重叠的字面量路径实施机械修改。
- 在主智能体完成实现后进行针对性只读审查。

小任务、强耦合修改、需要频繁共享上下文或会争用同一逻辑单元时，由主智能体直接完成。

### 5.2 权限与所有权

- 主智能体必须先读取任务卡并冻结事实源、范围、停止条件和验收口径，再派发有界子任务。
- 子智能体不得领取其他 taskId、改变 route/owner/dispatchState、修改队列和任务卡、创建提交、合并、推送或操作自动化 runtime 与集成锁。
- 子智能体默认只读；允许写入时必须分配互不重叠的字面量路径，并保证同一路径只有一个写入所有者。
- 子智能体不得继续派生子智能体。需要更多工作面时，由主智能体统一调度。
- 子智能体的结果只是证据和候选差异，不能替代主智能体对事实源、完整 diff、验证结果和残留风险的复核。

### 5.3 单候选合同

无论使用多少子智能体，对自动化外层都仍是：

- 一个已领取 taskId。
- 一个 owner run 与 owner worktree。
- 一个由主智能体创建的 candidate。
- 一套由主智能体汇总执行的最终验证。
- 一次既有共享入口核验、重放和排他集成。

子智能体不进入 schema 5 runtime，不拥有独立 candidate，也不改变恢复协议。

## 六、发现任务仍不原子时的处理

### 6.1 写入前发现

若主智能体在读取事实源后发现任务无法按当前卡原子闭环：

- 不开始项目写入，不派生多写者去掩盖任务边界问题。
- 自动化 run 使用现有 `attention_required` 表达停止，并记录稳定原因 `task_requires_decomposition`。
- 不生成业务 candidate，不由 worker 边实施边创建零散子卡。
- 由规划责任方在一次独立处置中完整拆卡、建立依赖图、更新父项和 ready 投影后关闭或替换原 run；父项不再被后续 worker 重复领取。

### 6.2 写入后发现

若实施中才暴露不可拆合的职责冲突：

- 立即停止继续叠加补丁，不提交、不集成。
- 保留 owner worktree、已验证事实和最小失败证据，进入现有 `attention_required` 恢复路径。
- 规划责任方判断哪些差异可保留为新子任务输入；不得由自动化把半完成差异机械拆成多个正式 candidate。

这一路径复用现有状态与恢复规则，不增加新的 runtime state。

## 七、各执行器的一致性

- 手动 Codex、原生 Claude Code、DeepSeek wrapper、Codex 小时责任方和 DeepSeek 小时责任方统一遵守原子任务准入与子智能体权限边界。
- 执行环境暴露子智能体能力时，主智能体可按本设计选择使用；没有该能力时，原子任务仍由单智能体正常执行。
- 缺少子智能体能力不是失败理由；任务本身不原子、且单智能体无法可靠闭环时，才触发拆分停止。
- Claude Code 使用普通 subagent 语义；项目不依赖实验性 agent team。DeepSeek wrapper 是否可用子智能体以当次 Claude CLI 工具暴露为准，不从模型名称推断。

## 八、自动化复杂度边界

本设计不修改自动化控制面的结构：

- schema 5 仍只记录 `runs.codex` 与 `runs.deepseek`。
- 共享入口仍负责 claim、owner worktree、candidate 核验、最新 master 重放、组合验证、排他集成、关闭和清理。
- 自动化脚本不解析“任务大小”，不自动拆卡，也不协调子智能体。
- `task_requires_decomposition` 只是现有 `attention_required` 的稳定原因，不是新状态。

新增成本只发生在当前确认过大的父项：需要一次完整拆分，但不会预分析整个 backlog。相较逐张懒拆，它避免父项被多次重新读取、重复消耗自动化轮次，并换取更短的业务执行、更清晰的回滚范围和更可靠的验证。

## 九、实施落点

书面规范通过复核后，已以最小文档修改落实：

- `AGENTS.md`：加入全执行器共用的原子任务与子智能体总规则。
- `开发管理/AI协作规则.txt`：加入临近执行时的最小原子性检查、当前父项一次性完整拆分、任务内委派、单候选和拆分停止细则。
- `CLAUDE.md`：把“不得另行并行派发”收窄为不得另领顶层任务；明确允许同一已领取任务内按共享规则使用子智能体。
- `开发管理/自动工作流规则.txt`：明确小时 worker 不动态拆卡，子智能体对 schema 5 透明，并复用 `attention_required`。
- `开发管理/自动工作流恢复规则.txt`：补充 `task_requires_decomposition` 的人工处置与关闭前条件。

第一阶段未修改 PowerShell 控制器、任务卡 schema 或检查脚本。只有后续出现规则未被执行的实证，才另立任务评估机械检查；不得预先增加启发式“大小识别”。

## 十、验收

- 五份规则文件对“顶层派发”和“任务内委派”的表述一致，不再互相禁止。
- 不要求全量预分析 backlog；只在当前项临近执行时做最小原子性检查。
- 当前父项一旦确认需要拆分，就在一次规划过程中形成完整子任务集、依赖图、ready 起点和父项关闭条件；父项不再被反复领取拆分。
- 大型父项不可直接实施，各原子子项的所有者、路径、停止条件和验证可以独立读取；边界未知时在同一次拆分过程中完成有限只读调查。
- 自动化使用子智能体后仍只产生一个 owner run、一个 candidate 和一次正式集成。
- 任务不原子时有明确的写入前与写入后停止路径，不会自动生成任务卡或并行 candidate。
- 运行 `tools/check-review-text.ps1 -Paths AGENTS.md,CLAUDE.md,开发管理`、pending whitespace 与 staged diff 检查；由于不修改 docs/CSV/Unity 数据链，不运行无关数据链或 Unity 回归。

## 十一、未采用方案

### 11.1 所有大型任务强制多写者并行

虽然可能缩短局部耗时，但会把路径所有权、同步、失败恢复与多 candidate 合并引入自动化控制面，不符合最小复杂度原则。

### 11.2 所有大型任务一律手动执行

能够规避自动化超时，但会放弃可安全拆分、可机器验收的工作，也不能解决手动主会话的上下文和遗漏风险。

### 11.3 自动化动态识别并拆卡

文件数量、行数和预计时长都不能可靠代表业务原子性。由 worker 自动改变任务拓扑还会混淆规划主责、事实源和恢复边界，因此不采用。
