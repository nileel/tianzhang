# 通用角色立绘到 Tripo 静态模型工作流设计

日期：2026-08-17

状态：负责人已批准书面规格；两轮 DeepSeek V4 Pro 0813 独立审核意见已收口，等待 `A-CHAR-FOURVIEW-TRIPO-WORKFLOW-01` 实施

## 一、目标与边界

本设计把“已批准全身立绘 → 四视图 → Tripo 静态模型生成 → 静态模型外观批准”固化为全角色通用工作流。工作流以降低返工成本为首要原则：每个原子处理阶段只有一个主要目的，问题留在最早能够修正它的阶段，付费操作只能消费已经冻结并获批的输入。

正常路径只有两个负责人验收点：

1. 四视图整组飞书验收；
2. Tripo 静态模型飞书验收。

文件、尺寸、哈希、提示词、槽位清单、参数、私密性、价格区间和任务 ID 等确定性事实由自动检查处理；画面方向、身份与风格由 Codex 视觉预检并交负责人卡片裁决，不形成额外常规人工卡点。

本工作流止于 Tripo 静态模型外观批准。平台自动绑定、动画诊断、原始包下载、Blender 换绑、权重修整、项目统一骨架动作验证和 Unity 接入均属于后续独立工作流；本设计不把它们合并进当前任务，也不因静态模型通过而自动启动它们。

## 二、现有试产暴露的根因

苻渊试产证明，仅保存图片或依赖执行者临场判断不足以稳定复用，必须显式冻结以下事实：

- 正确示例图可能已有可复用提示词；未先检索提示词会造成不必要的倒推和风格漂移。
- “纸偶感”过弱会变成普通柔软织物插画，过强又会变成厚卡纸、折纸或拼装玩具；风格源与身份源必须分离。
- 四视图生成会漂移后发长度、头部轮廓、体型、姿势、服装和手脚；不能只检查脸部相似度。
- Tripo 页面槽位的“左侧／右侧”按输出图片中人脸与鼻尖朝向解释。继续用容易混淆的角色自身左右命名会导致槽位反放。
- 非对称腰扣、玉坠、发饰或纹样若在两张侧图和背图中重复出现，平台可能把同一物件解释为多套环身结构。
- 页面缩略图、加载状态或排列可能让两个相同侧面看起来同时进入输入；必须用原图哈希和带永久标签的验收合图证明实际集合。
- Tripo 模型转动方向不能证明当前视角名称；以鼠标拖动方向命名会把脸朝左和脸朝右再次颠倒。
- 侧面腰带或远侧饰件的暗色背缘可能被误判为正面扣饰；AI 疑点不能代替负责人最终视觉结论。
- 四视图根因与平台随机生成根因需要分流。错误输入只能修图后重新付费生成；输入正确而 3D 随机输出异常时，免费重试才有意义。
- 私密性、模型版本、贴图、PBR、面数和显示价格是提交前事实；不得用历史页面状态推断当前设置。

## 三、设计原则

### 3.1 原子阶段

每个阶段只产生一种主要结果：冻结事实、生产四视图、取得批准、提交模型、采集证据或取得模型结论。阶段不得顺带完成下游绑定、下载或 Unity 接入。

### 3.2 两次人工验收

处理阶段可以拆分为多个原子任务，但正常流程只在四视图整组和静态模型两个位置等待负责人。没有新的视觉判断时，不发送飞书卡片。

### 3.3 事实、风格和角度分离

- 已批准立绘负责角色身份、脸、年龄、发型、服装、配色、比例和标志物。
- 单独批准的模型效果或纸偶示例只负责纸偶体块、平面化材质和纹理方向，不得覆盖角色身份。
- 四视图合同只负责观察角度、姿势、构图和非对称物件在各角度的可见性。

### 3.4 版本化而不覆盖历史

图片、提示词、清单和 Tripo 任务均使用批次与版本号。任一图片或提示词变化都会产生新版本并使旧批准失效；历史失败输入、任务 ID、credits 和证据保持原貌。

## 四、输入合同与事实冻结

工作流只接受已经批准的全身立绘。若立绘本身尚未批准，必须先完成上游立绘工作流，不能在四视图任务中同时改造角色设计。

进入本工作流时先生成不可变 `batchId`，格式为 `<character-id>-<YYYYMMDD>-<sequence>`；同一角色同日的序号只增不复用。目录、manifest、飞书决定、Tripo 操作账本和最终交接均使用同一 `batchId`，批次创建后不得通过重命名改变其身份。

同一批次可在首次付费提交前保存四视图和提示词的修订版本；一旦该批次的付费账本进入 `IN_FLIGHT` 或已经产生任何付费 Tripo 任务，后续任何会改变四视图图片内容、提示词、参考图或槽位映射的返工都必须创建新的 `batchId`。旧批次自此只读保留，不能以增加图片版本号的方式再次取得付费授权。新批次按本节规则重新冻结事实；没有变化的视图可以从旧批次按字节复制，并在新 manifest 中记录来源批次、来源文件和哈希。

事实冻结阶段只读取并记录：

- 已批准全身立绘的字面量路径、尺寸、字节数和 SHA-256；
- 角色直接事实源与本次用途；
- 允许使用的纸偶风格参考及其作用边界；
- 脸、年龄、发色、顶髻、后发长度、胡须、头身比例、姿势、袖袍、鞋、配色和纹样等身份不变量；
- 所有非对称发型、服装、系结、腰扣、玉坠、流苏、法器和纹样的视角可见性矩阵；
- 目标 Tripo 模式的固定槽位顺序和当前项目默认生成参数。

非对称可见性必须逐视角写成明确事实，例如“正面可见一套；脸朝左可见；脸朝右不可见；背面不可见”，不得只写“保持左右一致”。

若正确示例已有提示词，必须先检索并原样记录其来源；只有确认不存在原提示词时才允许从示例图倒推。倒推提示词必须标记为派生事实，不能伪装成历史原词。

该阶段唯一产物是 `source-manifest.txt`。它不生成图片、不上传 Tripo、不消费 credits。

## 五、四视图生产与提示词追溯

### 5.1 固定集合

四张正式候选固定为：

1. `front`：正面；
2. `face-left-side`：鼻尖朝画面左的严格 90° 侧面；
3. `face-right-side`：鼻尖朝画面右的严格 90° 侧面；
4. `back`：严格背面，不露出脸。

平台映射和项目文件名均使用 `front / face-left-side / face-right-side / back`；完整文件名保留角色、批次和版本前缀／后缀，例如 `<character>-face-left-side-<batch>-v1.png`。项目说明中不得再用未附画面语义的 `character-left / character-right` 作为 Tripo 槽位名。

四图必须保持同一身份、紧凑纸偶比例、发型与后发长度、服装结构、配色、纹样、标志物、安静姿势、完整手脚、简单同色背景、均匀中性光照和接触关系。侧面不能用前三分之四视图替代，背面不能把前置饰件复制到身后。

### 5.2 单问题修订

初次四图形成后，每次修订只处理一个明确问题，例如只改头发、只纠正纸偶材质或只移除某侧错误腰饰。身份、比例、姿势或服装结构一旦随局部编辑漂移，该候选直接丢弃，不在同一图片上连续叠加补丁。

付费提交后因输入问题创建新批次时，没有变化的批准视图按字节复制到新批次，不能为了凑齐版本号重新生成。首次付费提交前的局部修订仍在当前批次内派生图片与提示词版本。这样既限制真正的返工范围，也避免已经消费过付费授权的批次再次进入提交入口。

### 5.3 提示词保存合同

四视图定版时必须同步保存 `prompts.md`，且每张图至少记录：

- 完整生成提示词；
- 完整负面约束；
- 使用的身份参考、风格参考和辅助参考及其 SHA-256；
- 使用的生成或精确编辑模式；
- 工具、模型和可见版本信息；提供方没有暴露的内部版本或 seed 必须显式写为 `unknown`，不得猜测；
- 原始生成提示词与每一次保留到最终图的定点编辑提示词；
- 最终图片文件名、版本、尺寸、字节数和 SHA-256；
- 提示词版本与图片版本的一一对应关系。

后续调整必须从对应定版提示词派生新版本。只要提示词、参考图或图片内容变化，旧四视图批准立即失效；不得重新凭最终图片猜提示词，也不得覆盖旧提示词历史。

### 5.4 确定性检查与视觉预检

四视图生产阶段先执行确定性自动检查：

- 文件数量、格式、非空、尺寸、字节数和 SHA-256；
- 文件名、清单槽位和提示词版本映射完整；
- `prompts.md` 记录所有可取得的执行输入，操作者实际使用的生成／编辑提示词不得缺失；只有提供方未暴露的内部版本或 seed 可以写 `unknown`；
- 四张图片不存在 SHA-256 级的重复文件；
- 参考图路径与哈希存在，旧批准输入没有被覆盖。

随后由具备图像输入能力的 Codex 执行视觉预检，只形成疑点和证据，不形成负责人最终通过／失败结论：

- 文件名标签与画面鼻尖方向一致；
- 四图全身完整，身份、后发、比例、姿势、服装、手、脚和背景一致；
- 非对称物件可见性矩阵逐图成立；
- 没有两个相同侧面、镜像伪造、错误裁切、额外人物、文字、UI 或水印。

确定性脚本和 DeepSeek 不得执行或伪造视觉通过。Codex 可以在四视图卡中标记疑点或建议局部返工，但负责人飞书回执仍是整组四视图唯一人工视觉结论。

该阶段唯一产物是四张候选图、`prompts.md`、`manifest.txt` 和带永久标签的 `approval-contact-sheet.png`。它不操作 Tripo。

## 六、飞书四视图验收

四视图验收卡使用 2×2 合图，图框内直接写入“正面／脸朝左／脸朝右／背面”。标签属于验收证据，不写回四张原始输入。

卡片同时显示：

- 角色与批次；
- 四张图片和提示词版本的摘要；
- 头发、纸偶感、比例、服装、手脚和非对称物件检查结果；
- 当前只读 Tripo 预检读到的模型版本、私密性、关键设置和显示价格；
- 本次允许的一次付费生成价格区间。

按钮固定为：

- A：通过整组四视图，并授权一次区间内的 Tripo 付费生成；
- B：退回四视图阶段；
- C：暂缓；
- 现有飞书自定义回复入口继续用于具体修改意见，以及按固定格式 `PRICE_RANGE=<min>-<max>` 提议本批次价格区间。

A 同时冻结四张图片哈希、提示词版本、槽位映射、关键 Tripo 参数和一次付费授权。任一事实变化都会使该卡失效。B 只回到四视图阶段，不产生 Tripo credits。C 不推进任何平台操作。

价格区间自定义回复只接受十进制正整数、`min <= max` 且整条回复严格符合 `PRICE_RANGE=<min>-<max>` 的形式，例如 `PRICE_RANGE=20-60`。有效回复只修改待批准区间：系统必须先使旧卡失效，再生成一张显示新价格区间、仍绑定同一批次当前事实的新四视图卡；自定义回复本身不构成付费授权，只有新卡 A 回执才能授权。格式无效时不改变状态、不失效当前卡，并返回正确用法。

飞书视觉证据通过现有项目飞书决策桥的窄扩展实现：先调用飞书上传图片接口取得 `image_key`，再使用消息卡片图片组件展示可放大合图。官方接口当前要求机器人能力，并对消息图片提供格式、大小和分辨率限制；实现必须在发送前验证这些限制。参考：

- <https://open.feishu.cn/document/server-docs/im-v1/image/create>
- <https://open.feishu.cn/document/common-capabilities/message-card/message-cards-content/image-module?lang=zh-CN>

首次实施前必须完成一次不关联业务批准的飞书图片金丝雀，证明现有自建应用已启用机器人能力、具备图片上传权限，并能在当前负责人会话展示可放大的卡片图片。金丝雀失败时不降级为纯文字视觉审批，也不推进 Tripo。

每次发送按合图内容哈希上传图片。原始 `image_key` 只保存在用户级私有发送意图中，不进入 Git、任务卡或模型输出；项目只记录其哈希。上传成功但卡片投递失败时，该 key 不构成批准，也不自动复用到新的逻辑决定。安全重投同一发送意图时可在提供方允许的窗口内复用；已过期或状态不明时重新上传同一内容，并保留旧 key 哈希作为孤儿资源证据。图片上传、卡片构建或投递失败时，不发送缺失关键证据的审批卡，不默认通过，也不推进 Tripo。

## 七、Tripo 提交与价格授权

### 7.1 默认价格区间

项目默认单次付费生成可接受区间为 `20–60 credits`，包含上下限。负责人可以先通过四视图卡的固定格式自定义回复提议不同区间，再在系统重建的新卡上按 A 明确授权；批次 A 回执冻结的区间优先于项目默认值。

价格区间不是“最多 60”规则，而是对预期生成规格的完整一致性检查：

- 提交瞬间显示价格在已授权区间内时，允许自动提交一次；
- 低于区间下限也停止，因为可能表示模型、规格或计费项目发生变化；
- 高于区间上限停止，因为超出预算授权；
- 价格在区间内的小幅变化不要求重新审批。

### 7.2 一次付费授权消费账本

“一次付费”必须由点击前的原子账本保证，不能只依赖提示词或执行者自律。四视图 A 回执的飞书 `decisionId` 是唯一批准 ID；账本稳定键由批次 ID 与该 `decisionId` 组成，并同时冻结图片 manifest 哈希、提示词 manifest 哈希、Tripo 参数哈希和授权价格区间。

账本复用现有飞书 `send-intent-store` 的 claim 范式，但使用独立的用户级私有子目录，不修改飞书发送意图。它只负责 Tripo 付费授权消费，不建立新的业务状态机。最小状态为：

- `PREPARED`：批准已验证，尚无执行者取得点击权；
- `IN_FLIGHT`：唯一执行者已在排他锁内取得点击权；
- `ACCEPTED`：已取得唯一 Tripo 任务 ID，并完成余额与 credits 对账；
- `ACCEPTED_ANOMALY`：已取得任务但实际扣费或关键返回事实超出授权，后续冻结；
- `OUTCOME_UNKNOWN`：点击可能已发生，但任务 ID、扣费或页面结果不能可靠证明。

只有 `PREPARED` 能在排他锁内原子转换为 `IN_FLIGHT`。任何自动化重入、重复飞书回执、页面恢复或新会话读到其他状态时一律不得点击。执行者必须在点击前完成该转换；若进程在转换后、平台结果确认前中断，只能进入或保持 `OUTCOME_UNKNOWN`，不能把授权重置为 `PREPARED`。恢复必须先以只读方式核对 Tripo 资产列表、提交时间窗、冻结的输入与参数以及余额：账本已有任务 ID 哈希时，用页面观察 ID 的 SHA-256 匹配；账本尚未来得及保存哈希时，只有上述事实能唯一指向一个新任务，才原子补记其哈希。结果唯一后才把原始任务 ID 写入项目 `tripo/generation-record.txt` 并完成恢复；否则请求负责人处置，不发起第二次付费。

账本不保存登录凭证、cookie、token、飞书原始收件目标或操作者原始标识。Tripo 登录继续使用浏览器已有登录会话，本工作流不建立凭证文件。

### 7.3 提交前双重预检

发送四视图卡前先做一次只读预检；实际点击生成前再次读取当前页面。第二次预检必须证明：

- 当前四图哈希与飞书批准完全一致；
- 槽位依次为前／左侧（脸朝左）／右侧（脸朝右）／后；
- 当前页面槽位标签及其实际脸朝向语义仍与已批准映射一致；若平台改版导致语义变化则停止；
- 模型版本、生成模式、目标面数、拓扑、贴图、PBR、分部件、8K 和其他关键设置与批准事实一致；
- 私密性为项目要求的私有状态；
- 显示价格位于授权区间；
- 当前批准尚未消费，也不存在同一批次的已提交付费任务。

任一检查不成立就停止，不点击生成。所有检查成立时，只允许发起一次付费请求，并立即记录批准 ID、平台任务 ID、显示价格、提交前余额、提交后余额和实际 credits。项目 `tripo/generation-record.txt` 保存用于审计和打开结果所必需的原始平台任务 ID 与查看 URL；用户级私有账本只保存任务 ID 的 SHA-256，不保存原始任务 ID。

同一批准不能因页面超时、重复点击、旧飞书回执或自动化重入产生第二次付费请求。若任务 ID、扣费或提交结果不明确，账本进入 `OUTCOME_UNKNOWN`，冻结现场并等待核对，不重复点击。

显示价格必须从生成按钮解析为整数 credits，并在最接近点击的同一页面状态中再次读取。点击后以提交前后余额差额和平台任务记录强制对账：实际扣费位于授权区间且任务 ID 唯一时进入 `ACCEPTED`；实际扣费低于下限、高于上限、与显示价格不一致或关键设置返回不一致时进入 `ACCEPTED_ANOMALY`。异常已经发生的扣费不能伪装成通过或自动回滚；工作流只保存证据、停止所有后续平台操作并请求负责人决定是否申诉或接受。

### 7.4 阶段边界

本阶段只生成静态模型。它不点击平台绑定、动画、导出或下载入口，不运行 Blender，也不写入 Unity 正式路径。

## 八、模型证据采集与视角命名

模型完成后，从一个人工或可复核的正面锚点开始采集四个证据角度：

1. `front`：正面；
2. `face-left-side`：脸朝左的严格侧面；
3. `face-right-side`：脸朝右的严格侧面；
4. `back`：背面。

截图名称只由画面事实决定：鼻尖朝左即 `face-left-side`，鼻尖朝右即 `face-right-side`，背面必须无脸。鼠标拖动方向、拖动次数、模型自身左右或缩略图排列均不能用于命名。四视图输入、证据文件、合图和卡片始终使用 `front / face-left-side / face-right-side / back` 的同一名称和顺序。

每个模型尝试产生一张带永久标签的四角度合图。证据必须覆盖：

- 正侧背主体、头发、顶髻、胡须、手、脚和袍摆完整；
- 纸偶比例、材质和服装结构没有明显漂移；
- 非对称饰件在四角度中的实际可见性；
- 没有额外部件、重复物件、背面前置饰件、破洞或明显几何缺失。

AI 可以在卡片上标记疑点和建议，但不能把疑似暗色轮廓直接写成最终通过或失败。负责人飞书回执是静态模型视觉结论的唯一人工事实。

## 九、免费重试与根因分流

### 9.1 根因分类

模型预检发现问题时，由具备图像输入能力的 Codex 比较四张获批原图、槽位映射和 3D 四角度证据；确定性脚本和 DeepSeek 不承担视觉根因分类：

- `input_failure`：必须指出具体四视图文件、画面区域或 manifest／槽位矛盾，证明问题在提交前已经存在；
- `model_output_failure`：必须指出具体 Tripo 任务 ID 和证据角度，同时证明获批四视图中不存在同一问题，问题只在 3D 输出中出现；
- `unclear`：现有证据不能唯一归类。

没有具体来源证据、2D 与 3D 同时可疑、目标区域被遮挡或执行者对判断有保留时一律为 `unclear`。不能为了使用免费次数把输入问题改写成平台随机问题，也不能把视觉分类伪装成哈希或脚本结论。Codex 的根因分类只决定自动重试建议与卡片说明，不是负责人对该模型候选的最终视觉裁决。

### 9.2 输入问题

`input_failure` 不使用免费重试，也不由 Codex 静默丢弃已经付费的模型候选。工作流发送正常静态模型验收卡，绑定当前 `proposedCandidateTaskId`，展示输入问题证据并明确推荐负责人选择 B。负责人仍可选择 A 接受该候选、选择 B 退回或选择 C 表示模型输出问题。只有负责人选择 B 后，系统才按第四节创建新的 `batchId`，将旧批次完整转为只读历史，只修正有问题的图片并派生新的提示词和图片版本。新整组必须重新通过飞书四视图验收；后续再次付费生成必须由新批次的新 A 回执授权。

### 9.3 模型随机问题

同一付费批次只有一个共享免费重试预算：`freeRetryLimit=2`、`freeRetryUsed=0`、`freeRetryRemaining=2`。自动分支与模型卡 C 共用该计数器；每次点击免费重试前都必须在私有账本排他锁内原子占用一个序号并递增 `freeRetryUsed`，任何入口读到 `freeRetryRemaining=0` 都不得再点击。页面显示更多免费次数不扩大本工作流预算。每次重试还必须在点击前记录页面“免费重试”标识和当前余额，完成后记录新任务、提交后余额与余额差；余额差必须为 `0 credits`。

`model_output_failure` 可以在不请求负责人授权的情况下使用免费重试，但输入、槽位和全部参数必须与已批准请求完全相同：

1. 自动占用并使用第一次免费重试；
2. 采集新的四角度证据并与上次比较；
3. 若 Codex 视觉预检没有继续标记模型输出问题，停止自动重试并进入模型飞书验收；
4. 若仍标记同类或新的模型输出问题且预算尚余一次，自动占用并使用第二次免费重试；
5. 第二次完成后无论预检结论如何都进入模型飞书验收，不继续重试。

“是否发生有意义变化”只作为给负责人的描述性摘要，不再控制是否使用第二次免费重试；这样删除无法稳定实现的半自动语义阈值。每次免费重试都必须保存独立的平台任务 ID、证据合图、变化摘要、免费标识和余额对账。首次结果与所有重试结果都保留，不能只展示最后一次。若重试产生任何非零扣费、免费标识与实际结果矛盾或任务／余额结果不能唯一对账，批次立即进入 `ACCEPTED_ANOMALY` 或 `OUTCOME_UNKNOWN`，停止所有后续平台操作并请求负责人处置；已经原子占用的重试序号不得回退或重放。

### 9.4 根因不明

`unclear` 不猜测、不自动重试。发送异常根因飞书卡，展示四视图与模型四角度，选项为：

- A：四视图有问题，按第四节创建新 `batchId` 后退回修改；
- B：四视图正确，允许进入自动免费重试分支；
- C：暂缓；
- 自定义回复：补充具体判断。

这张卡只在上述具体证据规则仍不能唯一归类时产生，不属于正常路径的第三个人工卡点。实现测试应统计它的触发原因；不得以“谨慎”为由把所有视觉疑点默认转入异常卡。

## 十、飞书静态模型验收

模型卡展示首次结果及已发生的所有免费重试：

- 每次任务 ID、模型统计和四角度合图；
- Codex 标记的疑点与重试前后变化摘要；
- 实际付费 credits、免费重试次数和剩余免费次数；
- Tripo 查看链接。

每张模型卡必须在决定对象和卡片标题中冻结一个唯一的 `proposedCandidateTaskId`。默认候选为当前最新尝试；其他尝试只作比较证据。A 的完整文案必须包含该任务 ID，不能写成无指向的“当前候选”。改选候选只接受整条回复严格符合 `SELECT_TASK=<exact-platform-task-id>` 的形式，且该原始任务 ID 必须已经展示在同一张当前有效模型卡中。有效回复先使旧卡失效，再生成一张绑定所选 `proposedCandidateTaskId` 的新卡；自定义回复本身不构成批准。格式无效、ID 未展示或来自旧卡时不改变状态，并返回正确用法。不得让一次 A 回执同时覆盖多个候选。

卡片固定选择为：

- A：通过卡片标题中明确列出的 `proposedCandidateTaskId` 并交接下游；
- B：输入图有问题，退回四视图阶段；
- C：模型输出有问题；`freeRetryRemaining>0` 时原子消费一次共享免费重试并重新取证，等于 0 时明确显示“无剩余免费重试，结束本批次”；
- 现有自定义回复入口用于暂缓、改选已展示的候选或补充意见。

A 冻结获批 `proposedCandidateTaskId`、证据和结论，并结束本工作流。B 会使旧四视图批准失效，并强制按第四节创建新 `batchId`；旧批次只读保留，新的付费生成必须由新批次的四视图 A 回执重新授权。C 不构成新的付费授权；它与自动分支共同消费同一批次固定两次的免费预算。任何再次付费都必须回到新批次的新四视图批准事件。

## 十一、固定产物与目录

每个角色批次建议使用以下结构：

```text
<character>/<batch>/
├─ source/
│  ├─ [approved-portrait.png]
│  ├─ identity-refs/
│  ├─ style-refs/
│  ├─ auxiliary-refs/
│  └─ source-manifest.txt
├─ fourview/
│  ├─ <character>-front-<batch>-v1.png
│  ├─ <character>-face-left-side-<batch>-v1.png
│  ├─ <character>-face-right-side-<batch>-v1.png
│  ├─ <character>-back-<batch>-v1.png
│  ├─ prompts.md
│  ├─ manifest.txt
│  └─ approval-contact-sheet.png
└─ tripo/
   ├─ generation-record.txt
   └─ evidence/
      ├─ attempt-01-contact-sheet.png
      ├─ retry-01-contact-sheet.png
      └─ retry-02-contact-sheet.png
```

已批准立绘若已有稳定的项目规范路径，则不重复复制，`source-manifest.txt` 只记录该字面量路径和哈希；若来源位于临时目录或项目外且不能作为长期事实源，则按字节复制为可选的 `source/approved-portrait.png`，同时记录原来源、复制文件和两者哈希。`identity-refs/`、`style-refs/` 和 `auxiliary-refs/` 同样只保存当前批次实际消费且项目内尚无规范路径的参考副本；已有规范项目路径的参考不重复复制，只记录其字面量路径和哈希。没有发生的重试不创建空证据。合图只用于验收和审计，不替代四张原始输入。`tripo/generation-record.txt` 保存原始平台任务 ID 和查看 URL 作为项目审计事实；它们不是凭证。私有凭证、飞书收件目标、操作者原始标识、Tripo 登录信息和 token 不进入项目目录或 Git；Tripo 仅使用浏览器已有登录会话，本工作流不创建私有凭证文件。

## 十二、自动化与飞书集成边界

### 12.1 复用现有控制面

工作流继续复用现有任务卡、队列、飞书决策桥、负责人配对、签名回执、旧卡失效、首次有效回复获胜和自定义回复机制。不建立第二个飞书机器人，不建立独立调度器，也不让飞书桥直接修改 Git、任务卡、Tripo 或队列。

处理步骤可以各自成为原子任务；负责人批准由现有 `pending_decision` 生命周期承载。飞书桥只传递经过验证的结构化决定，后续自动化轮次再消费决定并推进对应任务。

### 12.2 飞书桥窄扩展

实现阶段只为现有决策卡增加受限的视觉证据能力：

- 输入是项目已生成并通过大小、格式、路径和哈希检查的验收合图；
- 发送器上传图片并取得 `image_key`；
- 卡片构建器按批准的顺序插入一到数张图片；
- 私有发送意图保存重投所需的 `image_key` 与必要净化哈希，但不保存图片二进制、原始收件人或凭证；项目可见证据只记录 key 哈希；
- 图片上传失败与卡片投递失败保持不同的脱敏错误类别；
- 投递失败不回滚已有图片或模型事实，不默认选择，不自动重发付费操作。

本设计不把飞书桥扩展为通用文件库、聊天机器人、图片编辑器或 Tripo 执行器。

### 12.3 Tripo 操作账本窄扩展

付费授权和免费重试共用一个独立于飞书收件箱的最小 Tripo 操作账本，存放在现有用户级自动化私有状态根下的专用子目录。它只提供：

- 按批次与飞书决定 ID 原子 claim 一次付费点击；
- 保存付费状态、平台任务 ID 哈希、输入／参数哈希和余额对账；
- 原子维护固定为两次的 `freeRetryUsed`；
- 为每次免费重试分配唯一序号并阻止重复点击；
- 在 `OUTCOME_UNKNOWN` 或 `ACCEPTED_ANOMALY` 时失败关闭。

账本不选择角色、不判断图片、不解释飞书回复、不访问凭证、不修改 Git 或任务队列，也不提供通用浏览器操作状态机。账本只保存平台任务 ID 的 SHA-256；原始任务 ID 与查看 URL 只在平台结果明确后写入项目 `tripo/generation-record.txt`。私有账本是防重复扣费和防重复重试的执行证据，不替代项目审计记录或任务卡生命周期。

## 十三、失败语义与停止条件

- 立绘事实、风格源或非对称可见性无法唯一冻结：停在事实冻结阶段。
- 四视图确定性检查失败：停在四视图阶段；Codex 视觉预检只记录疑点，最终由负责人四视图卡裁决。
- 操作者实际使用的提示词、参考链或哈希不完整：不得发送四视图批准卡；只有提供方未暴露的内部版本或 seed 可以显式记录为 `unknown`。
- 飞书图片能力金丝雀失败、卡片缺图、图片与标签错位或回复来自旧卡：不得推进。
- Tripo 模型版本、私密性、关键设置、槽位、价格区间或批准哈希不一致：不得提交。
- 付费授权账本不是 `PREPARED` 或不能原子 claim：不得点击。
- 页面超时、任务 ID 不明或扣费不明：账本进入 `OUTCOME_UNKNOWN`，冻结现场，不重复点击。
- 实际扣费或返回设置超出授权：账本进入 `ACCEPTED_ANOMALY`，保存证据并请求负责人处置，不继续平台操作。
- 付费模型质量失败且根因在输入：不得免费重试。
- 付费后负责人确认返回修改四视图：旧批次转为只读并创建新 `batchId`，不得在旧批次追加版本后再次付费。
- 免费重试没有显示免费标识、余额差非零或任务／余额无法唯一对账：进入 `ACCEPTED_ANOMALY` 或 `OUTCOME_UNKNOWN`，停止后续平台操作。
- 模型随机问题的共享 `freeRetryRemaining` 为 0：自动分支和模型卡均不得再重试，也不得自动再次付费。
- 模型卡未绑定唯一 `proposedCandidateTaskId`，或模型外观未获对应该任务 ID 的负责人 A 回执：不得交接给绑定、下载、Blender 或 Unity 流程。
- 继续实施需要新增重试层、降低验收门、修改批准事实或扩大到下游资源接入：停止并重新请求设计裁决。

## 十四、验证设计

### 14.1 文档与清单

- 确定性检查证明四图、提示词关系、参考哈希、清单映射和版本完整；提供方未暴露字段只能按规则写 `unknown`。
- 合图标签与原图哈希一一对应，不存在 SHA-256 级相同侧面或错位缩略图。
- Codex 视觉预检能输出方向、身份、头发、纸偶感和非对称物件疑点，但不会伪造负责人通过结论。
- 修改图片、提示词、参考图、槽位或参数会使旧批准失效。
- 历史失败批次、任务 ID、credits 和提示词不被覆盖。

### 14.2 飞书卡片

- 图片能力金丝雀覆盖机器人能力、上传权限和当前负责人会话显示；失败时不能降级为纯文字视觉审批。
- 图片上传成功后才发送含 `image_key` 的卡片；超限、零字节、无效格式和上传拒绝均失败关闭。
- 覆盖上传成功但卡片投递失败、安全重投复用、key 过期后重传以及孤儿 key 哈希保留；任何路径都不能产生批准事实。
- 卡片完整展示视觉证据、批次、选项、价格区间和影响摘要。
- 只有已配对负责人、当前决定和首次有效回执可以推进。
- 重复点击、旧卡、错误图片哈希、错误批准 ID 和投递重放不能重复提交 Tripo。
- 自定义回复继续沿用现有签名与会话绑定，不因加入图片绕过身份或幂等检查。
- `PRICE_RANGE=<min>-<max>` 只有在格式、整数范围和顺序有效时才重建四视图卡；回复本身不能授权付费，非法输入不改变状态。
- 多模型候选场景中，决定对象、标题和 A 文案始终绑定同一 `proposedCandidateTaskId`；只有 `SELECT_TASK=<exact-platform-task-id>` 且 ID 已展示于当前卡时才能改选，改选会使旧卡失效并产生新卡。

### 14.3 Tripo 提交

- 显示价格为 20、60 或区间内其他值时，在其余事实一致的前提下允许一次提交。
- 低于 20、高于 60、关键设置变化、私密性变化或输入哈希变化时不提交。
- 同一批次与飞书 `decisionId` 在并发 claim、页面超时、自动化重入、重复飞书回执和崩溃恢复下最多产生一个付费任务。
- `PREPARED → IN_FLIGHT → ACCEPTED` 正常转换通过；非 `PREPARED` 重入不点击，结果不明进入 `OUTCOME_UNKNOWN`。
- 覆盖读取价格后、点击前页面价格变化；提交前后余额差额与任务记录强制对账。
- 实际扣费低于下限、高于上限、与显示价格不符或返回设置变化时进入 `ACCEPTED_ANOMALY`，停止而不自动补交。
- 同一批次发生付费 `IN_FLIGHT` 后，任何四视图内容返工都会创建新 `batchId`；旧批次不能重新进入 `PREPARED` 或产生第二个付费任务。
- 私有账本中的任务 ID 哈希能与平台观察值唯一匹配；项目生成记录保存原始任务 ID 与查看 URL，二者职责不混用。

### 14.4 视角与重试

- 输入与模型证据统一使用 `front / face-left-side / face-right-side / back` 的名称和顺序；两个侧面按鼻尖方向命名，旋转方向不参与标签生成。
- 输入问题、模型随机问题和根因不明三条分支互斥且有具体文件／区域／任务 ID 证据；确定性脚本和 DeepSeek 不执行视觉分类。
- Codex 判为输入问题时只在正常模型卡推荐 B，不静默丢弃付费候选；只有负责人 B 回执才创建新批次并返工。
- 自动分支与模型卡 C 共用 `freeRetryLimit=2` 的单一计数器；并发、重复回执和不同入口都不能使计数超过 2。
- 第一次重试后若 Codex 仍标记模型输出问题且预算尚余，固定使用第二次；“有意义变化”不作为分支条件。
- 输入问题不会消费免费重试；再次付费必须绑定新的四视图批准。
- 所有尝试的任务 ID 与证据完整保留，模型卡不能只显示最后一次。
- 每次免费重试都保存免费标识和前后余额；余额差非零或结果不明时失败关闭，已占用序号不回退。

### 14.5 项目验证边界

设计实施时运行与变更路径相称的任务卡、飞书桥单元／协议、审核文本、空白和 Git 差异检查。没有修改 Unity、Blender、BattleSim、CSV 或正式美术资源时，不运行其无关验证。

## 十五、完成条件

本设计实施完成后，任意已批准角色立绘都能进入同一套可审计流程：四视图提示词和图片可追溯，负责人可在飞书完成两次正常验收，一次付费授权由原子账本保证只消费一次并容忍批准区间内的小幅价格波动，模型随机问题在共享两次预算内使用免费重试，输入问题不会浪费重试，静态模型通过后以飞书决定中冻结的唯一 `proposedCandidateTaskId` 和证据交接给独立下游流程。

工作流成功不等于完整角色美术资源已经进入项目；它只证明 Tripo 静态模型候选已经获得负责人外观批准。
