# 项目最小上下文加载设计

状态：✅ 方案已确认（2026-07-23）；本文只锁定上下文减负方案，不实施规则、任务卡、脚本、索引或 Codex 配置修改。

## 一、目标

随着设定、代码、任务和美术资源增长，复杂任务在开始阶段经常整份读取多份文档，过早占用模型上下文。本文目标是在不降低事实可靠性和领域硬约束的前提下，减少项目资料进入单次复杂任务对话的峰值上下文。

首要目标是扩大一个复杂任务在同一对话中可处理的问题规模。累计 token 成本是次要收益，不作为本方案的主要优化指标。

本文覆盖：

- 设计、剧情与内容生产。
- Unity、BattleSim、数据链路与普通开发任务。
- 审核、交接和开发管理任务。
- 角色、UI、场景等美术资源生产。

本方案只优化一个复杂任务从定界到验证的完整对话，不为同一长期对话连续处理许多无关任务建立永久记忆。

## 二、现状与根因

2026-07-23 的仓库快照显示：

- 根 `AGENTS.md` 为 13,150 bytes、119 行，并在 Codex 会话开始时作为项目规则进入上下文。
- 根 `CLAUDE.md` 为 16,928 bytes，重复了大量共享规则，部分外部 wrapper 口径已经滞后。
- `docs/` 下有 273 个 TXT，合计约 2.0 MB。
- Git 已跟踪 80 个 C#、8 个 CSV 和 18 个 PNG。
- 当前任务卡常把十余份文档、代码和配置统一列为“必读”。
- 功法、术法、神通和剧情生产规则仍以整份规范或多份完整事实源作为默认读取单位。

因此当前根因不是缺少向量数据库，而是：

1. `AGENTS.md` 与 `CLAUDE.md` 重复承载了只在少数任务中使用的细节。
2. “必读”按文件定义，没有区分规则章节、代码符号、数据实体和美术用途。
3. 读取动作经常在任务开始时一次完成，没有先定位当前步骤真正需要的范围。

## 三、方案选择

### 3.1 仅依赖提示词自觉

只提醒 AI 少读文件，不修改项目规则和任务卡。

该方案改动最少，但无法减少固定加载的根规则，也不能稳定约束后续执行器，不采用。

### 3.2 瘦身规则并使用现有精确检索

缩短根 `AGENTS.md` 和 `CLAUDE.md`，把“必读文件”改为“必查范围”，使用现有 `rg`、文件名、标题、符号和行范围先定位再读取。

该方案直接处理当前根因，不引入新运行时和维护面，作为当前实施目标。

### 3.3 立即建设本地混合 RAG

增加索引器、embedding、本地向量数据库、MCP 检索服务、图片向量和索引更新机制。

该方案可能适合未来更大规模，但当前缺少精确检索已失败的证据。现在实施会扩大维护职责，不采用；若后续满足升级条件，再单独设计。

## 四、最小架构

当前方案只保留三项行为：

```text
精简常驻规则
    ↓
按任务确定必查范围
    ↓
使用现有工具先定位、后读取、发现依赖再补读
```

不新增上下文包、索引服务、脚本、数据库或后台进程。

### 4.1 精简根 `AGENTS.md` 与 `CLAUDE.md`

`AGENTS.md` 是共享项目短入口，只保留：

- 全项目通用且必须在任务开始前生效的硬约束。
- 设定、进度、数值、运行时和美术的事实源职责。
- 设计、剧情、数值、审核、自动工作流和美术任务的短触发路由。
- 纯 `1`、纯 `2`、`总结` 等用户快捷指令入口。
- 全项目统一的安全、修改边界和最小充分验证原则。

以下内容移回现有专项事实源，不在根文件复制：

- Claude / DeepSeek wrapper 和每小时控制器的完整执行细节。
- 审核、交接和自动工作流的长流程。
- 大段 Unity、PowerShell、Python 和 BattleSim 开发经验。
- 开发管理文件的长表格解释。
- 已经由专项文件完整定义的重复规则。

根文件只保留触发条件和目标路径。只有任务真正命中路由时，AI 才读取对应专项文件。

`CLAUDE.md` 只保留：

- `ANTHROPIC_BASE_URL` 对实际身份和修改方的判定。
- Claude / DeepSeek 不得领取 Codex 主责或复审任务的硬边界。
- 共享项目规则读取 `AGENTS.md`。
- 具体主责、wrapper、交接和提交边界按需读取 `开发管理/AI协作规则.txt` 与 `开发管理/DeepSeek工作提示词.txt`。

`CLAUDE.md` 不再复制设计规范、数值命令、管理文件表、快捷流程、检查脚本和 Unity 项目信息。

本轮不通过增加多个子目录 `AGENTS.md` 或 `CLAUDE.md` 解决问题。Codex 在会话启动时按项目根到当前工作目录建立规则链；项目通常从仓库根启动，子目录规则不能替代根级短路由。发现规则见 [Codex AGENTS.md 官方说明](https://learn.chatgpt.com/docs/agent-configuration/agents-md.md)。

### 4.2 从“必读文件”改为“必查范围”

“必查”仍是硬约束，但默认单位改为：

```text
文档路径#章节
代码路径::类型.符号
CSV路径::实体ID
资源目录::用途或资源ID
```

规则如下：

1. 必读规范先取得共同约束、任务对应字段和最终检查清单。
2. 参考表、既有内容和背景材料只取得与目标实体直接相关的章节或条目。
3. 修改前必须读取即将修改的完整逻辑单元，例如完整方法、规则段、CSV 行或资源说明。
4. 若章节边界无法覆盖完整语义、检索没有结果或事实存在冲突，回退到直接读取该项权威原文。
5. 现有任务卡不批量重写；后续触及某张任务卡时再将其必读项改为精确范围。

### 4.3 固定“先定位、后读取”

每个复杂任务自动执行：

```text
识别任务类型与目标实体
→ 使用 rg、文件名、标题、ID 或代码符号定位
→ 读取当前步骤所需的少量原文
→ 发现新依赖时再次定位并补读
→ 修改前读取目标完整逻辑单元
→ 执行最小充分验证
```

检索结果只作为导航证据，不能替代原始事实源。

## 五、各领域读取规则

### 5.1 功法、术法与神通

固定取得：

- 对应设计规范中的核心约束和通用约束。
- 本任务所需模板字段。
- 新增内容前置检查清单。

仅在相关时取得：

- 已有内容参考。
- 命名分布和门派分布。
- 特定倍率、成长表、升格方案或丹相边界。

涉及数值结论时，仍必须按项目规则运行 BattleSim。

### 5.2 剧情、任务、NPC 与演出

固定取得：

- `剧情生产规范` 中对应内容类型。
- 通用信息边界、禁止项和审核清单。
- 本任务命中的事实源路由。

按实体取得：

- 涉及地区的相关地图章节。
- 涉及势力的相关门派章节。
- 涉及 NPC 的相关人物字段。
- 涉及高阶、册界或战斗环境时对应的规则章节。

不因剧情规范列出一个目录，就默认读取该目录全部文件。

### 5.3 Unity 与普通开发

先定位：

- 目标类型和方法。
- 直接调用者与被调用者。
- 相关测试。
- 任务卡指定的当前所有者或事实源。

修改前读取目标完整方法、类型或配置实体。只有跨文件接口、公共架构或已有冲突证据要求时，才扩大读取范围。

成功构建日志和无关命令输出不应在对话中展开；只保留失败信息、结果摘要和必要证据。

### 5.4 CSV、JSON 与 Unity 数据

- CSV 先读取表头和目标 ID 行。
- JSON 先定位目标对象和直接引用。
- Unity `.asset` 先读取目标资源及必要引用。
- `.meta` 只用于 GUID、导入和依赖身份，不承载业务说明。
- 数据链路任务仍按直接影响范围核对 docs、CSV、asset、导入器和测试，但不预读同表全部内容。

### 5.5 BattleSim

先取得相关参数、类型、测试和矩阵入口；修改前读取目标完整逻辑单元。任何角色数值平衡讨论仍执行项目规定的 Release 构建与模拟器命令。

### 5.6 美术资源

当前沿用已有目录、README、角色事实源和提示词：

- 读取目标资源类型的工作流和提示词。
- 读取目标角色、场景或 UI 的直接事实。
- 只有直接事实不足时才补读世界背景和更广泛设定。
- 需要比较、生成或编辑图片时才加载图片本体。

当前不增加图片 embedding、视觉索引、同名 sidecar 或资源数据库。只有目录和命名无法可靠区分用途、版本、审核状态或来源时，再单独设计美术元数据方案。

## 六、错误与回退

### 6.1 检索没有结果

依次回退：

1. 精确 ID、符号或标题搜索。
2. 文件名和目录搜索。
3. 同义词或上级概念搜索。
4. 直接读取唯一权威文件。

不得因精确检索失败而猜测内容。

### 6.2 事实冲突

按领域职责判断：

- 设定与设计原文读取 `docs/`。
- 当前进度与任务状态读取 `开发管理/`。
- 数值结论读取 BattleSim 实际结果。
- Unity 当前实现读取 `src/`。

仍无法判断时暂停修改并请求用户决定，不用额外兼容分支掩盖冲突。

### 6.3 归档污染

正常任务默认不检索历史归档。只有追溯原因、审核历史或迁移来源时才进入归档。

### 6.4 Codex 上下文压缩

保持 Codex 默认压缩行为：

- 不调整自动压缩阈值。
- 不新增自定义 `compact_prompt`。
- 不建立上下文容量监控或会话检查点。

只有出现可复现的项目关键信息压缩丢失时，才针对该证据单独评估自定义压缩提示。

## 七、明确不实施

当前方案不包含：

- 本地或云端向量数据库。
- embedding 生成与更新。
- RAG、MCP 检索服务或后台索引器。
- 自定义上下文包或检索清单文件。
- 文档和图片的批量 sidecar。
- 图片视觉向量。
- 上下文容量实时监控。
- 跨对话长期记忆。
- 自定义 Codex 压缩阈值或压缩提示。
- 为本方案批量改写全部现有任务卡。
- 在 `AGENTS.md` 与 `CLAUDE.md` 之间继续复制共享规则。

## 八、一次性验证

实施完成后只做一次最小充分对照，不建立长期监控。

从现有真实任务中各选一个代表，只重放资料定位和必查范围判断，不要求重新生产业务内容或重复运行已经通过且输入未变化的领域验证：

1. 功法、术法或神通设计。
2. 剧情、任务或 NPC 内容。
3. Unity 开发。
4. BattleSim 数值工作。
5. 美术资源生产。

每项检查：

- 是否取得全部领域硬约束和直接事实。
- 是否避免开场整份读取无关文件。
- `AGENTS.md` 与 `CLAUDE.md` 的固定入口是否都不再复制专项规则。
- 修改前是否读取目标完整逻辑单元。
- 产物和验证标准是否与原流程一致。
- 以实际读取的项目文本字符量作为一次性近似指标：五项均不得高于原整文件读取基线，至少四项减少 50%。

验证只记录本次对照结果，不增加运行时仪表或持续采集。

## 九、升级到 RAG 的条件

完成本方案后，只有出现重复、可复现的证据才重新评估本地混合 RAG：

- 多个真实任务中，标题、符号、ID 和文件名检索仍反复漏掉必要语义关联。
- 同名或近义设定导致精确检索无法稳定区分当前权威来源。
- 美术资源的用途、版本、来源或审核状态已无法通过现有目录和命名可靠定位。
- 已采用章节和符号级读取，复杂任务仍因资料加载触及上下文瓶颈。

RAG 若被触发，必须另行完成设计、后端选择、索引新鲜度、权威过滤、失败回退和验证方案；不得把未来接口或数据库提前加入本轮实施。

## 十、完成条件

本方案的后续实施只有同时满足以下条件才算完成：

1. 根 `AGENTS.md` 不再重复专项流程，只保留全局硬约束和短路由。
2. 根 `CLAUDE.md` 只保留身份、授权和共享入口，不再复制共同项目规则。
3. 新增或触及的任务卡使用章节、符号、实体或用途级必查范围。
4. 项目规则明确要求先定位、后读取，并保留修改前完整读取目标逻辑单元的保护。
5. 五类代表任务的一次性对照未发现硬约束或直接事实遗漏。
6. 未引入数据库、MCP、索引器、sidecar、容量监控或自定义压缩配置。
7. RAG 保持为有证据后才启动的独立后续方案。
