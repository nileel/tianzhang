# 每日与每周全项目进度总结设计

## 背景与根因

现有日报 `tzg-daily-automation-briefing` 只调用 `tools/get-automation-briefing-source.ps1`，该脚本只把带有效 `Automation` 元数据的提交纳入候选。人工提交即使已经进入 `master`，也不会出现在日报中。因此日报实际是“自动化推进简报”，不能回答当天整个项目完成了什么。

现有周报已经要求读取时间窗内全部 Git 提交，并明确包含人工与自动化来源；实时 automation prompt 与项目内 `开发管理/每周项目总结提示词.txt` 一致。周报当前不属于只读 Automation 提交的问题，但仍有美术源文件盲区。

项目美术资源分为三类：

- `src/Assets/Art/` 保存 Unity 正式导出资源，并通过 Git LFS 提交；
- `assets/generated-character-art/` 保存仓库内批准的 AI 样张、分层 PNG、提示词和哈希，正常进入 Git；
- `assets/source/` 保存本地原始工程、平台原包、贴图、Blender 工作文件和中间证据；按 `docs/资源管理/美术资源版本管理规范.md`，该目录的新文件默认被 Git 忽略。

`assets/source/` 不是纯 ignored 集合。设计核验时 `git ls-files -- assets/source` 仍返回 6 个历史跟踪文件：静态棋子候选的 FBX、Blend，以及 strict-round-02 的 3 份诊断文本和 1 张联系表 PNG。它们继续属于普通 Git 跟踪路径；只有不在 Git 跟踪集合中的 `assets/source/` 文件才属于本设计的本地美术例外。

因此“读取全部 Git 提交”仍无法发现时间窗内尚未形成正式导出或文本记录、且没有被 Git 跟踪的本地原始美术活动。现有 `docs/资源管理/美术资源登记册.md` 只登记正式资源批次且当前内容滞后，不能独自承担日报或周报的完整美术事实源。

本设计取代 `2026-07-26-daily-weekly-project-briefing-design.md` 中“日报只消费 Automation 业务提交”的范围约束；`2026-08-23-daily-briefing-ready-lifecycle-design.md` 已建立的 Automation 生命周期核验和同 Task 合并语义继续保留。

## 目标

- 日报与周报都覆盖时间窗内已经进入当前 `master` 的全部可验证项目进展，不区分人工或自动化来源。
- 对 `assets/source/` 中未被 Git 跟踪的文件增加严格受限的只读活动发现，使本地原始美术工作不会完全消失。
- 将“可验证成果”和“仅有本地文件活动”分层陈述，不根据文件时间、提交标题或 automation memory 猜测完成状态。
- 日报与周报使用同一候选收集合同，避免两套取数逻辑再次分叉。
- 保持报告只读、现有调度、模型、项目、飞书投递和小时自动工作流不变。

## 方案选择

### 采用：全部提交与本地美术活动双层汇总

全部 Git 提交构成普通开发进度候选；`assets/source/` 中未被 Git 跟踪的本地文件活动构成美术例外候选。美术例外必须与任务卡、任务归档、生成／QA 记录或资源登记册交叉核验后，才能并入“已验证进展”；否则只能列为“本地美术活动（待登记）”。

该方案能在不要求原始二进制进入 Git、不引入新的写入型日报、不强迫每次美术操作提交中央账本的前提下覆盖当前盲区。

### 未采用：只认 Git 内证据

只读取全部提交及已提交的美术记录最简单、证据最强，但会继续遗漏尚未提交记录且未被 Git 跟踪的 `assets/source/` 活动，不满足负责人明确提出的美术覆盖要求。

### 未采用：强制维护逐次美术事件清单

每次生成、导出或返修都提交一条事件记录可以提供最可靠的长期历史，但会扩展所有美术生产流程、增加新的写入义务，并把本次只读报告修正扩大为资产管理重构。本设计不引入该机制。

## 事实源与时间边界

### 成功游标

现有日报以上次运行时间作为 `Since`，没有区分报告是否完整形成；本设计把日报改为与周报一致的成功游标语义。旧日报 memory 中的运行时间键不迁移、不解释为成功游标；切换后的第一次日报没有合法 `lastSuccessfulUntil`，固定回看此前 24 小时。该切换可能与最后一份旧格式日报形成一次时间窗重叠，但不能为了去重猜测旧 memory 的成功状态；后续只使用新游标连续推进。

日报和周报分别在各自用户级 automation memory 中只保存 `lastSuccessfulUntil`：

1. 本次运行时间是 `Until`；
2. 存在合法 `lastSuccessfulUntil` 时将其作为 `Since`；
3. 首次运行或没有合法游标时，日报回看此前 24 小时，周报回看此前 7 天；
4. 只有完整候选收集、报告正文形成和一次飞书调用均已完成后才推进游标；飞书是否获得 provider 接受不影响游标；
5. Git、必要项目事实源或本地美术扫描失败时，报告明确标为未完成且不推进游标。

memory 只保存成功时间边界，不保存提交、美术文件、任务状态或项目结论，不作为成果事实源。

候选时间窗统一使用 `Since < eventTime <= Until`。同一 automation 后续从成功游标继续，避免边界事件重复或遗漏。

### Git 进度

只读取当前 `master` 在时间窗内可达的全部提交。每项候选至少包含提交 SHA、提交时间、标题、Automation 元数据（若有）和变更路径统计：

- Automation 提交继续按 `Task`、提交快照中的任务卡／归档和队列投影核验生命周期，并按同一 Task 折叠为窗口内最新正式状态；
- 人工提交必须由其完整 diff、任务卡／归档或所修改的权威事实源支持，不能只根据标题推断结果；
- 中间 requeue、交接提交、纯卡片清理和无业务变化的队列维护不重复计为独立成果；
- `src/Assets/Art/` 和 `assets/generated-character-art/` 的提交属于普通 Git 进度，不走本地美术例外。
- 已被 Git 跟踪的 `assets/source/` 路径同样属于普通 Git 美术进度，并从本地扫描候选中排除。若提交只证明跟踪文件发生变化、没有任务或 QA 记录支持更多语义，报告只能陈述“跟踪的源美术文件已更新”及相应路径／统计，不能宣称生成完成、质量通过或获得批准。

### 本地原始美术活动

扫描前只读调用一次 `git ls-files --cached -- assets/source` 取得当前 Git 跟踪集合，并把路径统一为仓库相对正斜杠形式。该命令失败属于 Git 候选源失败。只读扫描固定根目录 `assets/source/` 中不在该集合内的文件，不得扩大到其他 ignored 路径或读取现有无关工作区 diff。扫描只采集：

- 仓库相对路径；
- 文件字节数；
- `CreationTimeUtc`；
- `LastWriteTimeUtc`。

文件的活动时间取创建时间和最后修改时间中的较晚者。只有活动时间落入当前时间窗的普通文件才进入候选。扫描不得打开、渲染、解析或计算图片、模型、音频、压缩包及 Blender 文件的内容，也不得修改时间戳、生成缩略图或运行领域验证。

扫描必须拒绝离开 `assets/source/` 的路径和 reparse point。排除规则固定复用 `.gitignore` 的现有 OS／临时文件合同：文件名或模式为 `.DS_Store`、`.DS_Store?`、`._*`、`ehthumbs.db`、`Thumbs.db`、`Desktop.ini`、`*.log`、`*.tmp`、`*.temp`、`*.bak`、`*.swp`、`~$*`，并且不进入 `.Spotlight-V100`、`.Trashes` 目录；Windows 下按大小写不敏感匹配。实现不得自行扩展一个未受测试约束的“既有临时文件模式”集合。若根目录不可访问、枚举不完整、遇到无法安全判定的重解析边界或无法读取必要元数据，则返回稳定 `art_source_error`，本次总结不推进成功游标。

时间戳只能证明本地文件活动，不能证明生成来源、语义、质量、批准状态或任务完成。报告按相关任务／批次归组；同一批次文件过多时折叠为文件数、总字节数、最新活动时间和代表性相对目录。若未登记批次总量仍超过正文容量，必须再聚合为“明确列出的主要批次 + 其余批次数／文件数／总字节数”，使全部检测量进入统计，不得静默丢弃；聚合部分不能升级为已验证成果。

## 美术证据分级与去重

### 已验证美术进展

满足以下任一证据链，并能读取支持结论的完整逻辑单元时，可以进入普通“已验证进展”：

- 时间窗内提交了 `src/Assets/Art/` 正式导出、对应 `.meta`／Prefab／材质以及必要验证；
- 时间窗内提交了 `assets/generated-character-art/` 的批准样张、提示词或哈希记录；
- 时间窗内直接提交了已跟踪的 `assets/source/` 文件；没有其他语义证据时只核验并陈述该跟踪文件的变化，不升级质量或完成结论；
- 时间窗内提交的任务卡、完成归档、平台生成记录、Blender／资源 QA 记录或 `docs/资源管理/美术资源登记册.md` 明确记录 `assets/source/` 相对路径、实际产物、状态和必要的大小／哈希／验证事实；
- 负责人在已提交权威记录中明确批准某项平台或美术结果，且记录没有虚构缺失字段。

已跟踪的 `assets/source/` 文件不会进入本地扫描候选。未跟踪文件若已由同一时间窗的上述文本提交支持，只作为该成果的来源证据，不再单列第二项“本地活动”。

### 本地美术活动（待登记）

本地文件活动没有可核验的 Git 记录时，必须使用独立标签“待登记”，仅陈述批次相对目录、文件数量、总大小和最新活动时间。禁止写成“完成”“通过”“已批准”“已导入”或推断对应任务 ID。

后续时间窗若提交了该批次的生成／QA／登记记录，则在该记录提交的时间窗按已验证进展报告；不回写历史日报，也不把此前待登记活动重复计为第二个成果。

登记册缺行不能否定其他任务或 QA 记录已经证明的成果；登记册、任务事实和文件活动冲突时标为 `evidence_conflict`，不采用较方便的一侧。

## 共享候选收集器

将现有 `tools/get-automation-briefing-source.ps1` 和对应测试重命名为 `tools/get-project-summary-source.ps1`、`tools/test-get-project-summary-source.ps1`，并最小扩展为日报、周报共用的项目进度候选收集器。保留现有 Automation 生命周期解析函数，对外合同同时返回：

- `commits`：时间窗内全部 Git 提交的基础事实；
- `automationGroups`：沿用现有按 Task 核验和折叠后的 Automation 结果；
- `sourceArtActivity`：时间窗内安全枚举到的、未被 Git 跟踪的 `assets/source/` 文件活动；
- `errors`：Git 元数据、Automation 生命周期或本地美术扫描的稳定错误；
- `since`、`until` 和整体 `status`。

日报与周报都只调用这一收集器，不再由日报只取 Automation JSON、周报自行执行另一套 Git 枚举。收集器只提供候选和机械事实，不读取领域全文、不生成自然语言结论、不修改项目文件或 memory。

同一改动更新日报、周报及活动检查器中的全部现行引用；历史设计和计划文档不回写。旧脚本与旧测试直接退休，不保留并行候选源或兼容转发脚本。

### 收集器与报告层分工

共享收集器只机械枚举提交、Automation 生命周期和未跟踪美术文件元数据。人工提交的语义核验由日报／周报的报告层 prompt 执行：只对拟写入正文的提交读取必要 diff，并按项目领域路由读取任务卡、归档或权威事实源的完整相关逻辑单元。日报必须加入周报现有的“只对拟写入成果的提交读取必要 diff”纪律；两者都不得把收集器输出、提交标题或变更统计直接升级为业务结论，也不在报告时重跑领域验证。

## 报告组织

### 日报

日报的中文报告定位改为“每日项目总结”，automation 的用户可见名称精确改为 `TZG Daily Project Summary`；标题继续使用 `天章日报 · YYYY-MM-DD`。正文按以下顺序输出，空段省略：

1. `## 今日进展`：按实际涉及的领域归组全部已验证净进展，包括设计、内容、数据、BattleSim、Unity、美术和管理；不以人工／自动化作为分类。
2. `## 本地美术活动（待登记）`：只列没有足够 Git 证据的 `assets/source/` 活动。
3. `## 未闭环`：列时间窗成果相关及当前事实中的 `ready`、`blocked`、`frozen`、`pending_decision`、`waiting_reply`、`pending_review`，说明所缺条件。
4. `## 接下来`：按运行结束时当前固定队列列最多三项及直接依赖，注明快照时间。
5. `## 异常`：列数据源失败、证据冲突、生命周期不可核验、工作区未提交路径、runtime／锁异常和未投递通知摘要。

没有 Git 进展和本地美术活动时，明确写“本时间窗没有可验证项目进展或本地美术活动”，但仍输出当前状态和接下来。

### 周报

保留现有五段结构，在 `## 已验证进展` 中加入美术领域；如存在未登记活动，在该段之后增加 `## 本地美术活动（待登记）`。其余当前状态、风险与决定、下周重点合同不变。

人工与自动化来源只在解释复审状态、证据强度或责任边界时标注，来源本身不是成果类型。日报和周报仍先形成不超过 6000 个 Unicode code point 的唯一 Markdown 正文，再把同一正文发送到飞书；内容过多时按任务／批次折叠，不得仅因来源是人工或美术而省略整个批次。

## 只读、安全与非目标

- 日报和周报不得修改项目文件、任务卡、队列、backlog、状态、登记册或 `assets/source/`，不得执行项目任务、业务验证、stage、commit 或自动修复。
- `git status --short` 仍只用于报告未提交路径；除 `assets/source/` 的固定元数据扫描外，不读取或归因其他未提交内容。
- 不扫描外部网盘、Tripo、Blender 当前会话、Figma、ImageGen 历史或其他第三方平台来补写成果。
- 不计算全部本地美术文件哈希；正式哈希只引用已提交记录，避免日报退化为高成本资产校验任务。
- 不改变交互式用户消息严格等于“总结”时的 `开发管理/总结规则.txt` 写入流程。
- 不修改小时 worker、schema 5 runtime、owner 路由、任务卡 schema、集成锁或飞书通知协议。
- 不新增项目成果数据库、中央 manifest、后台守护、文件系统 watcher、重试队列或第二套报告状态机。

## 主责与原子边界

本项实施固定由 Codex 单一主责。仓库内共享候选源、测试、日报／周报权威提示、活动检查器、正式集成，以及两个实时 automation 的同步属于同一原子结果；不得把仓库修改单独路由给 DeepSeek，也不得把 automation 同步延后到另一任务或后续轮次。DeepSeek 可以继续提供只读审核证据，但不执行实时 automation 写入或代替 Codex 完成闭环。

## Automation 同步

仓库实现和测试通过后，通过 Codex automation 管理能力更新现有两项 automation：

- `tzg-daily-automation-briefing`：保留稳定 ID，用户可见名称改为 `TZG Daily Project Summary`，prompt 同步为新的日报权威提示；
- `tzg-weekly-project-summary`：保留稳定 ID 和名称，只同步新的周报权威提示。

两者必须原样保留 `ACTIVE` 状态、每日 01:00／每周一 02:00 调度、`gpt-5.6-terra`、`medium` 推理强度、local execution environment、项目目标和通知策略。稳定 automation ID 继续用于通知幂等键，不迁移历史 memory，不创建重复 automation。

仓库权威提示与实时 automation prompt 无法跨 Git 和 automation 管理接口原子更新，因此沿用既有受控顺序：先完成并正式集成仓库改动，再立即同步两个现有 automation，最后从最新 `master` 运行一致性检查。同步失败时报告明确的不一致并停止，不修改调度、不创建替代 automation，也不宣称完成。

## 测试矩阵

共享候选收集器至少覆盖：

1. 同一时间窗同时存在人工提交和 Automation 提交，两者都进入 `commits`；
2. Automation 的 `ready → completed`、`pending_review`、阻塞、待决定和真正不可核验分类保持现有结果；
3. 普通人工提交不因缺少 Automation 元数据进入错误；
4. 时间窗外提交不进入候选，边界使用 `Since < eventTime <= Until`；
5. `assets/source/` 中时间窗内新建或修改的未跟踪普通文件进入 `sourceArtActivity`；
6. 已跟踪的 `assets/source/` 文件从本地扫描排除，其时间窗内提交只进入普通 Git 候选；
7. 时间窗外美术文件和固定 OS／临时文件模式不进入候选；
8. 正式 `src/Assets/Art/` 或 `assets/generated-character-art/` 提交只作为 Git 进展，不重复为本地美术活动；
9. reparse point、越界路径、无法完整枚举或元数据读取失败返回 `art_source_error`；
10. Git 或 Git 跟踪集合读取失败返回 `source_error`，结果不得伪装为无进展；
11. 相同 `Since`／`Until` 输入产生稳定顺序和可重复 JSON。

提示与配置检查至少断言：

- 日报和周报都调用同一共享候选源；
- 两者都明确覆盖人工与自动化提交；
- 两者都包含本地美术证据分级和禁止按时间戳宣称完成的规则；
- 两者都要求报告层只对拟写入成果的人工或 Automation 提交读取必要 diff；
- 日报明确忽略旧运行时间键，首次回看 24 小时，之后只推进 `lastSuccessfulUntil`；
- 日报不再出现“本时间窗没有带有效 Automation 元数据的业务提交”或只统计自动化的合同；
- 日报用户可见名称精确为 `TZG Daily Project Summary`；两项实时 prompt 与项目权威提示逐字一致，调度、模型、状态及项目未变化。

最小验证包括共享候选源单元测试、自动工作流 prompt 一致性测试、审核文本检查、本轮路径空白检查以及暂存后的 `git diff --cached --check`。本项不修改领域输入，不重跑 Unity、BattleSim 或美术 QA。

## 验收条件

- 下一份日报能同时表示时间窗内已经进入 `master` 的人工和 Automation 净进展，不再把人工提交静默排除。
- 下一份周报继续覆盖全部提交，并增加与日报一致的本地原始美术活动边界。
- `src/Assets/Art/`、`assets/generated-character-art/` 与由已提交生成／QA 记录支持的 `assets/source/` 工作被归入美术进展且不重复计数。
- 设计核验时已有的 6 个历史跟踪 `assets/source/` 文件及未来任何跟踪路径均只走普通 Git 候选，不进入 `sourceArtActivity`。
- 只有本地时间戳证据的 `assets/source/` 活动明确标为“待登记”，不被描述成完成或通过。
- 任一必要取数源不完整时总结明确失败边界且不推进 `lastSuccessfulUntil`。
- 报告生成不产生项目工作区变化；现有用户 `src/Assets/Scenes/StartMenuScene.unity` 改动及其他无关未提交内容不被读取或归因。
- 两个现有 automation 除日报用户可见名称和两个 prompt 外的配置均保持不变。

## 回滚

仓库修改应形成一个路径限定提交，包含共享候选源、测试、日报与周报权威提示以及必要的一致性检查调整。回滚该提交后，由 Codex 立即把两个实时 automation 的完整 prompt 和日报用户可见名称同步回回滚后的仓库合同，再运行一致性检查。

不得只回滚 Git 而留下新的实时 prompt，也不得删除稳定 automation ID、重置历史 memory、改变调度或以新增兼容入口代替完整回滚。
