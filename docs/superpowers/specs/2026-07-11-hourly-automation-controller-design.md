# 天章每小时自动工作流控制器设计

> 日期：2026-07-11
> 生命周期：已实施；当前调度优化由 v2 继承
> 历史定位：保留 v1 的初始取舍与证据，不再作为 v2 队列、脏工作区或执行器规则源
> 范围：Codex 桌面自动化、项目内自动工作流规则、运行状态与恢复工具

## 1. 背景与问题

项目已切换到 G1 正式构建链、G2 BattleSim 数值可信度、G3 数据链路语义可信度三道 P0 闸门，并冻结新的剧情、角色、功法、术法、神通和世界设定扩写。现有自动化仍由四条三小时循环写入型工作流协作：WF1 维护队列、WF2 执行 Codex `1`、WF3 调用 Claude/DeepSeek 执行 `1`、WF4 执行 Codex `2`，另有一条只读日报。

近期运行记录暴露了五类结构性问题：

1. WF1、WF2、WF3、WF4 共同修改 `开发管理/自动工作流状态.txt`，运行锁本身会先弄脏工作区。
2. 三小时触发周期与六小时共享锁不匹配，长任务、前台超时和残留子进程会让后续工作流误跳过。
3. WF3 在没有 Claude/DeepSeek 主责任务时仍执行 CLI 预检、超时、恢复和状态提交；此前还曾越权领取 Codex 主责的 TQ-043。
4. WF4 提示中保留已完成任务编号，任务路由可能被硬编码历史状态污染。
5. 项目状态文件只保存最新一轮结果，日报无法从该文件可靠重建运行历史；空转轮次又会制造无业务价值的提交。

本次优化选择“稳定优先”，以单写入者、失败关闭、动态路由和可恢复为核心，不追求多个 AI 同时自动施工。

## 2. 目标与非目标

### 2.1 目标

- 每小时检查一次项目，并在有安全、合法候选时推进一个最小工作单元。
- 任意时刻只有一个自动化拥有项目写权限，消除跨工作流共享锁竞争。
- 严格遵守模型身份、任务主责、内容冻结和 G1/G2/G3 依赖。
- 中断后只恢复能够证明属于原自动化的变更；来源不明时失败关闭。
- 空转、有效锁占用和人工脏工作区不再产生项目提交。
- 自动化配置、项目规则、当前状态和历史运行轨迹各有单一职责。

### 2.2 非目标

- 不在本次优化中执行 TQ-043、TQ-050、TQ-052 或其他业务任务。
- 不自动推送远端、不自动创建 PR、不自动解冻内容。
- 不删除 WF1、WF3、WF4 的历史配置和 memory；只暂停定时运行。
- 不为提高吞吐量引入并行 worktree、多个写入代理或自动合并。
- 不改变用户手动发送纯 `1` 和纯 `2` 时的项目规则。

## 3. 方案选择

采用“单控制器串行调度”：将现有 WF2 原地改造为唯一写入型 `TZG Hourly Controller`，每小时第 15 分钟触发一次。WF1、WF3、WF4 暂停但保留；每日简报继续在每天 01:00 只读运行。

没有采用以下方案：

- 保留三条写入工作流并重新错峰：改动小，但不能消除多个写入者和状态文件竞争。
- 为各工作流建立独立 worktree：隔离更强，但会增加提交合并、中文管理文件同步和恢复复杂度，超出当前项目需要。

## 4. 总体架构

自动工作流分为四层：

1. **Codex 自动化配置**：负责按时唤醒控制器或日报，不保存项目事实。
2. **项目规则**：`开发管理/自动工作流规则.txt` 是调度、路由、锁、恢复和失败策略的唯一规则源。
3. **本机运行状态**：零依赖 PowerShell 工具在 `%USERPROFILE%\.codex\automation-state\tzg-hourly-controller.json` 管理租约、检查点和恢复证据；该文件不进入 Git。
4. **项目结果摘要**：`开发管理/自动工作流状态.txt` 只记录最近有效成果、最近队列校验时间和当前人工阻塞；详细逐轮轨迹由自动化自身的 `memory.md` 保存。

只有 `TZG Hourly Controller` 可以修改项目。日报只读取 AGENTS、规则、状态、任务队列、自动化 memory 和 Git 证据，不能修改文件、stage 或提交。

## 5. 每小时控制流程

每轮严格按以下顺序执行：

1. 通过 Node REPL 读取实际模型身份。身份无法确认时记录准确错误并只读退出，不得修改项目。
2. 调用状态工具获取三小时租约。已有未过期租约时安静退出，不提交跳过记录。
3. 读取本地恢复状态并运行 `git status --short --untracked-files=all`。
4. 若存在中断任务，只在当前变更路径完全包含于该任务记录的 `expectedPaths` 时恢复；出现额外路径则进入 `AUTO-BLOCKED`。
5. 若没有恢复任务但工作区不干净，视为人工或来源不明改动，本轮只读退出。
6. 读取 `AGENTS.md`、自动工作流规则、当前任务队列和必要的审核/交接入口，动态选择本轮唯一分支。
7. 按任务卡与项目规则执行修改和验证；每到关键检查点续期租约。
8. 验证全部通过后，只 stage 本轮相关文件并提交；同步闭环队列、归档和结果摘要。
9. 释放租约并写入自动化 memory。无任务时不改项目文件。

### 5.1 动态路由优先级

本轮唯一分支按以下顺序选择：

1. 恢复同一控制器的中断任务。
2. 处理真实存在的最高风险待复审对象。
3. 在队列失真时执行一次维护。
4. 执行一个依赖满足、状态为“待处理”的最高优先级 Codex 任务。
5. 无候选时安静退出。

控制器提示和规则文件不得硬编码具体 TQ、HANDOFF 或审核清单编号。所有候选必须从当前事实源动态读取。

### 5.2 队列维护触发条件

只有满足任一条件时，队列维护才占用本轮：

- 当前队列少于 5 条。
- 队列含已完成但未归档的条目。
- 任务依赖状态与前置事实不一致。
- 任务主责与当前执行身份不匹配。
- 内容冻结期间有冻结内容进入执行队列。
- 距离上次成功队列校验超过 12 小时。

队列正常时不运行形式化维护，不为更新时间戳制造独立提交。若只更新本机校验时间而项目内容无变化，记录到本机状态和 memory 即可。

### 5.3 任务与复审边界

- 每轮最多处理一个复审对象、一次必要维护或一个最小任务切片。
- 复审严格走 `开发管理/审核入口.txt`，结论只能是通过、部分通过或不通过。
- 执行任务严格走纯 `1` 的 Codex 路由，不消费复审项。
- 内容冻结和闸门依赖是硬约束，自动化不能自行扩展、降级或绕过。
- 验证命令来自任务卡与项目规则；验证失败不得提交“已完成”状态。
- 成功后在同一业务提交中更新任务文件、当前队列、必要归档和项目结果摘要。
- 不自动推送远端。

## 6. 租约、检查点与恢复

新增 `tools/automation-controller-state.ps1`，使用 Windows 文件独占锁保护单次状态事务，并通过同目录临时文件加原子替换写入 JSON。工具不依赖第三方 PowerShell 模块。

### 6.1 本机状态字段

JSON 至少包含：

- `schemaVersion`
- `controllerId`
- `runId`
- `state`：`IDLE`、`RUNNING` 或 `AUTO-BLOCKED`
- `leaseExpiresAt`
- `taskKind`：`recovery`、`review`、`maintenance` 或 `execute`
- `taskId`
- `checkpoint`
- `expectedPaths`
- `recoveryCount`
- `lastQueueAuditAt`
- `lastError`

### 6.2 状态工具操作

工具提供以下明确操作：

- `Acquire`：在无有效租约时创建新运行；有效租约存在则返回专用非零退出码。
- `Renew`：续期当前 `runId` 的三小时租约。
- `Checkpoint`：更新任务类型、任务 ID、检查点和预期变更路径，并同时续期。
- `Complete`：将状态恢复为 `IDLE`，清理任务恢复字段，保留最近队列校验时间。
- `Fail`：记录准确错误；首次中断只建立恢复指针，不增加 `recoveryCount`；带恢复标记的失败才增加次数，第二次恢复仍失败时转 `AUTO-BLOCKED`。
- `Show`：只读输出规范化 JSON，供控制器和日报读取。
- `ResetBlocked`：仅供人工明确解除阻塞，自动化不得自行调用。

租约默认三小时。检查点为 `identity_checked`、`queues_loaded`、`task_selected`、`mutation_started`、`verification_completed` 和 `commit_completed`。任务选择、修改开始、验证完成、提交完成时必须续期。

### 6.3 恢复证明

控制器在 `task_selected` 前记录候选 ID，在 `mutation_started` 前记录允许修改的 `expectedPaths`。租约过期后的下一轮只有同时满足以下条件才可恢复：

- 本机状态指向同一任务且未达到恢复上限。
- Git 当前变更路径非空，并且全部属于 `expectedPaths`。
- 没有额外 staged 文件、未知 untracked 文件或与任务无关的管理文件变更。

任何一项不满足都转 `AUTO-BLOCKED`，不覆盖、不回退、不 stage 现有改动。

## 7. 文件职责与修改范围

### 7.1 新增文件

- `开发管理/自动工作流规则.txt`：稳定规则、路由顺序、队列维护条件、失败关闭和人工解阻入口。
- `tools/automation-controller-state.ps1`：本机租约与恢复状态工具。
- `tools/test-automation-controller-state.ps1`：在临时目录运行零依赖状态工具回归，不接触真实控制器状态。

### 7.2 修改文件

- `开发管理/自动工作流状态.txt`：删除 Git 运行锁和四工作流表，改为最近有效结果、最后队列校验和阻塞摘要。
- `开发管理/状态与建议维护规则.txt`：增加自动工作流规则/状态分层和队列审计触发说明。
- `开发管理/AI协作规则.txt`：把自动控制器路由指向唯一规则源，保留暂停 WF3 的授权边界供未来恢复。
- `AGENTS.md`、`CLAUDE.md`：在开发管理入口和查看规则中加入新规则文件的短路由；不复制完整控制器逻辑。
- Codex 自动化 `tzg-wf2-codex-execute-1`：原地改名并替换为每小时单控制器提示。
- Codex 自动化 `tzg-wf1-queue-and-review-maintenance`、`tzg-wf3-claude-execute-1`、`tzg-wf4-codex-execute-2`：设置为暂停，保留历史配置和 memory。
- Codex 自动化 `tzg-daily-automation-briefing`：改为汇总单控制器、项目结果摘要、自动化 memory 和 Git 证据。

## 8. 失败处理

以下情况统一失败关闭：

- 无法通过规定入口确认模型身份。
- 状态工具异常、JSON 不可解析或状态版本不受支持。
- 工作区存在人工或来源不明改动。
- 恢复任务的 Git 路径超出 `expectedPaths`。
- 任务事实源、依赖、主责或内容冻结状态不明确。
- 必要验证失败、缺失、不可解析或返回零测试等无效证据。

普通无任务、有效租约占用和人工脏工作区只写自动化 memory，不写项目状态、不提交。首次中断不占用恢复次数，之后最多自动恢复两次；第二次恢复仍失败后写入项目结果摘要的 `AUTO-BLOCKED`，等待人工处理。人工处理完成后通过状态工具 `ResetBlocked` 明确解除，不能靠下一轮自动忽略。

## 9. 验证设计

### 9.1 状态工具回归

`tools/test-automation-controller-state.ps1` 必须在独立临时目录覆盖：

1. 空状态成功获取租约。
2. 有效租约拒绝第二个运行。
3. 正确 `runId` 可以续期，错误 `runId` 被拒绝。
4. 检查点和 `expectedPaths` 可持久化并规范化读取。
5. 过期租约允许新运行接管并保留恢复信息。
6. `Complete` 正确清理运行字段。
7. 首次中断建立恢复指针但计数仍为 0；第一次恢复失败后计数为 1，第二次恢复失败后计数为 2 并转 `AUTO-BLOCKED`。
8. `AUTO-BLOCKED` 拒绝自动获取，人工 `ResetBlocked` 后恢复可用。
9. 损坏 JSON 和不支持的 schema 版本均返回非零且不覆盖原文件。

### 9.2 项目静态验证

- `powershell -ExecutionPolicy Bypass -File tools/check-review-text.ps1 -Paths AGENTS.md,CLAUDE.md,开发管理`
- `git diff --check`
- 检索控制器和日报提示，确认不存在具体 TQ/HANDOFF 硬编码。
- 读取全部自动化配置，确认只有 `TZG Hourly Controller` 是启用的写入型自动化；WF1、WF3、WF4 已暂停；日报仍为启用且只读。

### 9.3 首轮运行验收

配置启用后的首个真实小时轮次必须证明：

- 只选择一个路由分支。
- 没有来源不明的 staged/unstaged/untracked 残留。
- 成功时有对应业务提交和完整验证证据；无任务或人工脏工作区时没有项目提交。
- 运行结束后租约为 `IDLE`，或在失败时给出可操作的 `AUTO-BLOCKED` 原因。
- 次日简报能从 memory、Git 和项目摘要追踪该轮结果，不依赖旧四工作流状态表。

首轮真实运行属于部署后运行验收；实施提交只能声明配置与静态验证完成，不能在该轮尚未发生时声称运行验收通过。

## 10. 实施顺序与回滚

实施时先暂停 WF1、WF2、WF3、WF4，防止改造期间自动任务写入项目；随后落地规则、状态工具、测试和文档迁移，完成静态验证后再只启用改造后的控制器。日报最后更新并保持只读启用。

若首次运行暴露阻塞，立即暂停控制器，保留本机 JSON、memory 和项目摘要作为诊断证据；不得重新启用旧 WF1/WF2/WF3/WF4 形成多写入者。修复通过状态工具回归和静态检查后，再人工解除 `AUTO-BLOCKED` 并重新启用控制器。

## 11. 完成标准

本优化在以下条件全部满足时完成：

- 单控制器每小时触发，三条旧写入工作流暂停，日报只读保留。
- 自动工作流稳定规则与当前结果状态完成分层。
- 本机租约/检查点/恢复工具及零依赖测试全部通过。
- 控制器不存在硬编码任务编号，动态路由符合审核入口、纯 `1`、内容冻结和闸门依赖。
- 空转和锁占用不再制造项目提交。
- 文本检查、Git diff 检查和自动化配置静态检查全部通过。
- 首个真实轮次按第 9.3 节完成运行验收，或以明确 `AUTO-BLOCKED` 失败关闭并等待人工处理。
