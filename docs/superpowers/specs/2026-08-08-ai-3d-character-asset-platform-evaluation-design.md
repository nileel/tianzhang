# 《天章》AI 3D 角色资产平台评估设计

> 日期：2026-08-08
>
> 状态：设计对话已批准；本文只批准 Meshy 与 Tripo 3D 的一次性对照试产和选型规则，不代表已经完成模型生成、Blender 修整、骨骼统一、动画、URP 迁移或 Unity 正式接入。
>
> 上位约束：`docs/superpowers/specs/2026-08-05-character-art-and-modular-appearance-design.md`、`docs/资源管理/美术资源版本管理规范.md`。

## 一、决策摘要

1. 正式角色资产采用“AI 3D 平台生成基础资产，Blender 做最小必要修整、骨骼统一与导出验收”的生产方式；不从空白网格开始全手工制作，也不把平台的一键结果直接导入正式 Unity 路径。
2. 首次只以苻渊固定人形 NPC 为样本，对 Meshy 与 Tripo 3D 做一次同输入、同目标预算、同动作集的 A/B 试产。
3. 两个平台各设三个正式生成槽位。成功结果进入质量评估；平台服务错误不计为质量失败，但必须记录，同一槽位只允许原参数补跑一次，仍失败则占用该槽位并计为平台稳定性失败，不继续叠加重试。
4. 每件候选统一以约 12,000 三角面为目标，最终必须落在现行普通人形约 8,000 至 15,000 三角面的建议范围内。
5. 单件固定人形从平台导出到达到本设计验收状态的 Blender 人工修整时间不得超过 60 分钟。超过即判定该件不适合作为个人开发生产基线。
6. 试产结束只选择一个默认主平台，不长期维护双平台并行流程。另一个平台只保留评估结论，不成为每件资产的固定备选步骤。
7. 本次结论只覆盖固定人形 NPC。玩家模块化人形和重型四足仍需在各自技术样例中单独证明，不得从苻渊样本直接外推。
8. 正式生成槽位和计时选型开始前，必须已经存在一份获批的项目统一 Humanoid 评估骨架及待机、移动、攻击三条评估动作；平台自动骨架只能做前置诊断，最终通过必须由候选换绑项目骨架后的结果证明。

## 二、目标与非目标

### 2.1 目标

- 判断哪一平台更稳定地保留苻渊的脸型、束发、短须、宽肩、完整黑袍、白色内襟、稀疏金色缝线、古铜腰扣与青玉坠。
- 判断哪一平台更容易产出可变形、可整理、符合 8,000 至 15,000 三角面预算的基础网格。
- 用实际 Blender 修整分钟数衡量个人开发成本，不以平台宣传图、单次最佳结果或原始 credits 数量代替生产结论。
- 为后续固定人形 NPC 资源批次选出唯一默认平台。

### 2.2 非目标

- 不在本次试产中制作 Unity 正式 Prefab、正式材质、正式 Animator 或正式场景接入。
- 不修改 CTB、六角坐标、AI、伤害、装备、外观数据或存档。
- 不建设平台 API、批处理脚本、自动重试、平台抽象层或双平台兼容层。
- 不用 AI 平台自动骨架替代项目统一 Humanoid 骨架；自动骨架只用于判断网格的绑定与变形潜力。
- 不在本平台评估任务中顺带设计或制作项目统一 Humanoid 骨架、Avatar、Animator 或三条评估动作；缺少这些输入时按第五章停止在前置闸门。
- 不因某平台提供复杂 PBR 贴图就改变项目以低饱和手绘 Base Color 和 Toon 明暗为主的材质方向。

## 三、候选方案与取舍

### 3.1 直接固定 Meshy

优点是多视图、可编辑人形姿势、100 至 15,000 面的 Smart Topology 和原生部件拆分与当前苻渊需求高度吻合；头发、胡须、袍服和饰物更容易分别检查。缺点是尚无本项目实测，平台宣称的干净拓扑不能证明复杂宽袖和长袍的实际蒙皮质量。

### 3.2 直接固定 Tripo 3D

优点是 Smart Low Poly、面数控制、FBX／Mixamo 绑定链路和更广的非人形骨架类型明确，付费方案的模型额度也适合个人开发批量试错。缺点是“生成部件”与纹理、PBR、Quad 输出存在组合限制，复杂人形是否减少实际修整时间仍需样本证明。

### 3.3 一次 A/B 后固定单一主平台

采用本方案。它只增加一次苻渊对照成本，却能以同一角色的实际失败、修整和动画证据替代规格推断。试产后立即收敛为一个默认平台，不把对照过程扩张为永久双平台工作流。

## 四、平台事实基线

以下事实以 2026-08-08 的官方页面为准；后续若平台版本、授权或价格变化，实际生产前重新核对对应页面，不因变化自动改写本设计的验收门槛。

| 项目 | Meshy | Tripo 3D |
|---|---|---|
| 多视图 | 支持多视图图生 3D；Web 文档当前写明 2 至 8 张 | 支持原生多视图生成 |
| 姿势 | 支持人形自定义关节姿势，可输出 A／T Pose | 当前对照以输入视图中的统一 A／T Pose 为准 |
| 低模 | Smart Topology 可指定 100 至 15,000 面并原生拆分部件 | Smart Low Poly 可控低面数；API 当前支持三角面与四边面目标 |
| 部件 | Smart Topology 原生部件拆分 | 可生成部件，但与纹理、PBR、Quad 不能在同一生成请求中并用 |
| 绑定 | 支持人形和四足自动绑定 | 支持人形及多种非人形骨架，并可输出 Mixamo 规格 |
| 动作 | 官方文档当前列出 500 个以上预设 | 官方文档当前列出 100 个以上预设 |
| 导出 | FBX、GLB、OBJ 等；有 Unity 插件 | FBX、GLB、OBJ 等；提供面向 Unity／Unreal 的 Mixamo 流程 |
| 免费授权 | CC BY 4.0、产物公开 | CC BY 4.0、产物公开 |
| 付费授权 | 私有产物，付费用户拥有其合规输入生成的资产 | 付费方案列明私有模型与商业使用 |

## 五、输入合同

### 5.1 角色视觉输入

两平台必须消费同一组已批准参考，不允许为其中一平台另画更有利的结构：

1. 正面 A／T Pose。
2. 角色左侧严格正侧面。
3. 角色右侧严格正侧面。
4. 背面。

“左／右”以角色自身方向为准。两张侧面均使用近似正交的严格 90° 观察，不得用前三分之四角度代替；存在非对称发型、服装、系结、饰物或纹样时，不得简单镜像另一侧。四图必须是同一造型、同一比例、同一发型与服装结构，使用近似正交观察、简单背景和均匀照明。动态立绘和现有模型效果演示图只用于确认身份与美术方向，不能替代任一原始输入视图。前三分之四角度只用于第六章生成后的中性比较图，不属于平台输入合同。

### 5.2 平台参数

- 两平台都使用各自面向游戏资产的推荐生产模式，不强求内部算法参数同名。
- 统一目标为约 12,000 三角面；若平台只显示面数或四边面数，导出后以 Blender 的实际三角化统计为准。
- 每个平台执行三个正式生成槽位。三个槽位保持相同输入、模型版本和生产设置，只允许平台正常的随机差异；未成功的槽位按第一章的稳定性规则处理。
- 关闭不服务本项目材质目标的超高精度或 8K PBR 选项；平台默认颜色只帮助定位身份标志物，不作为色彩风格、材质质量或平台胜负的评分依据。
- 平台名称、模型版本、生成日期、任务 ID、付费／免费授权状态和关键设置记录到试产结果中。

### 5.3 项目统一骨架前置闸门

正式生成槽位开始前必须记录并冻结以下输入：

1. 项目统一 Humanoid 评估骨架的源文件路径、骨骼名称、绑定姿势和正面朝向。
2. 与该骨架匹配的待机、移动、攻击三条评估动作及各自动画文件路径。
3. Unity Humanoid Avatar 映射要求；评估阶段不必创建正式 Avatar 资产，但骨架必须能按同一映射要求导入。
4. 本轮允许使用的换绑与权重转移方法；两平台候选必须采用同一方法，不能为其中一平台另加专用修补流程。

截至 2026-08-08 本次复审，仓库中尚无受追踪的人形 3D 骨架：`src/Assets/Art/Characters/` 只有 `PortraitPresentation/`，`assets/source/characters/` 尚不存在。因此当前可以准备苻渊四视图，但不得开始三个正式生成槽位、60 分钟计时或平台胜负判定。统一骨架与三条动作应由上位设计第 12.3 节的模块化人形技术样例或另一个明确批准的源资产任务提供，不能在本评估中临时猜定。

## 六、单件试产流程

1. 在平台查看器中先检查正、侧、背面是否完整；缺失身体、后发、袍服背面或主要标志物的结果直接失败，不进入 Blender 修补。
2. 使用平台自动骨架及平台预设的待机、移动、攻击做前置诊断，记录平台绑定是否成功及明显变形问题；该结果不计作硬门槛通过，也不能替代项目骨架验证。
3. 导出 FBX；本次不使用 Meshy Unity Bridge，主因是所有正式候选必须先进入统一 Blender 源工程完成骨架、权重和导出验收。作为次要的版本背景，Meshy 文档在本文复审时只明确测试 Unity `6000.0.45f1`，项目当前为 `6000.3.18f1`；该外部事实后续即使变化，也不改变先经过 Blender 的资源边界。
4. 在 Blender 打开候选并开始记录人工修整时间。60 分钟完整包含移除或停用平台骨架、换绑第五章冻结的项目统一 Humanoid 骨架、转移并修正蒙皮权重，只允许处理：
   - 明显穿模、破面、非流形或悬浮部件；
   - 袖袍、头发、胡须、手部和主要饰物的必要形体整理；
   - 换绑项目统一骨架后的有限蒙皮异常；
   - 单位、朝向、底部中心原点和统一绑定姿势；
   - 材质槽、贴图路径和 Base Color 可用性。
5. 不在计时阶段重雕整张脸、重做整套服装、手工重拓扑全身、重画完整权重或补画完整贴图；一旦需要其中任一项，判定该件超过 AI 基础资产的合理修整边界。
6. 只使用第五章冻结的项目统一骨架和三条评估动作检查肩、肘、腕、髋、膝、袍袖、下摆、头发和胡须；平台自动骨架此时不得作为最终播放所有者。
7. 使用与现有“水墨棋偶”演示一致的固定正交斜俯视相机，输出前左、前右、背后三分之四三个视角的中性比较图。
8. 完成后停止计时，记录实际分钟数、失败部位、实际三角面数、材质槽数、平台自动骨架诊断、项目骨架换绑结果和三条项目动作的明显穿模次数。

## 七、硬门槛与评分

### 7.1 单件硬门槛

候选必须同时满足：

1. 正面、侧面和背面均无缺失主体结构。
2. 固定战术镜头下可以辨认苻渊身份轮廓和至少四项主要标志物。
3. Blender 实际三角面数位于约 8,000 至 15,000 范围内，且不依赖第二套外部重拓扑工具。
4. FBX 可正常打开，候选已换绑第五章冻结的项目统一 Humanoid 骨架，并能用该骨架播放同一组待机、移动、攻击；平台自动骨架播放成功不能满足本条。
5. 达到本节状态的人工修整时间不超过 60 分钟，计时明确包含项目骨架换绑、权重转移和有限权重修正。
6. 输入和产物具备可用于商业项目的授权；正式候选只使用付费私有生成。

任一硬门槛失败，该件不参与加权排名。

### 7.2 平台评分

平台至少需要两件候选通过单件硬门槛，才有资格成为默认主平台。对通过件取平均分：

| 指标 | 权重 | 证据 |
|---|---:|---|
| 角色身份与轮廓还原 | 25 | 只按几何轮廓、比例和标志物位置与批准立绘并排比较；平台默认颜色风格不计分 |
| 背面、袍服与附件结构 | 20 | 后视图和 Blender 网格检查 |
| 动作变形与穿模 | 20 | 换绑项目统一骨架后的待机、移动、攻击检查记录 |
| Blender 修整成本 | 20 | 包含项目骨架换绑与有限权重修正的实际人工分钟数 |
| 拓扑、部件与材质可编辑性 | 10 | 实际三角面、部件和材质槽记录 |
| 付费使用成本与导出便利 | 5 | 当次实际 credits、订阅和导出记录 |

最高平均分的平台胜出。两平台平均分差距不超过 5 分时，先选择平均修整时间更短者；修整时间差距不超过 10 分钟时，再选择身份与轮廓还原分更高者。不得以“两个都保留”回避选型。

## 八、失败处理与停止条件

- 某平台不足两件样本通过硬门槛时，该平台直接失去本轮选型资格，不再用额外生成次数寻找偶然最佳结果。
- 两个平台都不足两件通过时，先检查四视图是否在比例、服装结构或背面信息上自相矛盾。只允许修正输入事实后重新进行一轮相同规模的 A/B。
- 第二轮仍全部失败，则停止把通用图生 3D 平台作为固定人形的主生产方式；回到“AI 仅生成参考或基础形体，Blender 制作者建立可控模板”的上一级方案，不增加自动修补、兼容分支或第三个平台。
- 若候选无法在 60 分钟内换绑既定项目统一 Humanoid 骨架并通过三条项目动作，或必须改变既定骨架、绑定姿势、骨骼命名、Avatar 映射、复制 Animator、放宽三角面预算或改动运行时规则才能成立，停止该候选，不修改 Unity 侧约束迁就资产。
- 若平台付费授权、私有性或输入权利无法确认，产物只能用于内部评估，不能成为正式资源。

## 九、选型后的正式资源边界

1. 胜出平台成为固定人形 NPC 的默认基础资产生成工具。
2. 平台原始下载、生成记录和 Blender 源工程保存到 `assets/source/characters/`；该目录是本地原始工程边界，不直接作为 Unity 构建输入。
3. Blender 负责统一单位、正面朝向、底部中心原点、项目 Humanoid 骨架、绑定姿势、骨骼命名、UV、Base Color 和导出设置。
4. 只有通过上位设计中的 URP、2.5D 测试台和角色技术样例闸门后，才把 FBX、贴图、材质、动画和 Prefab 导入 `src/Assets/Art/Characters/`。
5. 正式批次更新 `docs/资源管理/美术资源登记册.md`，并在既有备注中记录所用平台、模型版本、生成日期和授权状态；本设计不新增登记系统或运行时字段。
6. 平台自动骨架和预设动作可以作为评估或动作参考，但项目正式人形继续使用统一 Humanoid 骨架、Avatar 和 Animator 契约。

## 十、实际试产交付物

执行本设计时形成以下最小交付：

- 同一组苻渊四视图输入。
- 第五章冻结的项目统一 Humanoid 评估骨架、三条项目动作及其路径和映射记录。
- Meshy 三个生成槽位和 Tripo 三个生成槽位的完整记录，包括成功候选与稳定性失败。
- 每件候选的三视角比较图、实际三角面数、包含换绑的 Blender 修整分钟数、平台骨架诊断和项目骨架动作问题记录。
- 一张汇总评分表。
- 明确的唯一胜出平台，或按第八章得出的“通用平台路线不成立”结论。

未胜出的模型、失败中间图和服务错误产物不进入正式 Unity 目录。目录只在实际试产开始后按需创建，不预建空目录。

## 十一、验证边界

- 本设计阶段只验证文档无占位符、无内部矛盾、没有超出固定人形平台选型范围。
- 实际试产以平台任务记录、Blender 统计、计时记录和换绑项目统一骨架后的三动作可视检查为事实，不凭文档或平台自动骨架结果判断平台胜负。
- 当前不运行 Unity 编译或测试；没有 Unity 文件、正式资产或运行时行为变化。
- 后续正式资源导出仍按 `docs/资源管理/美术资源版本管理规范.md` 运行资源版本检查和相应 Unity 验证。
