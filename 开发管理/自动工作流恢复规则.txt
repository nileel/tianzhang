# 自动工作流人工处置规则

本文件处理 schema 5 中已存在的 owner run。固定入口每轮先 `Show`；本 owner run 非空时只报告 owner、taskId、runId、state 和脱敏原因，不自动恢复、重跑、重放、关闭、清理或领取新任务。

## 共同核验

- 普通管理上下文先核对 owner、runId、taskId、repository、baseCommit、taskCardDigest、worktree、candidate／canonical branch、提交、进程和 runtime 记录；任一关键证据不一致都保留现场。
- `developing` 表示实施尚未形成合法 candidate；`candidate_ready` 表示 candidate 已核验但尚未形成正式结果；`canonical_ready` 表示正式提交已预构建但未集成；`integrated` 表示 `master` 已 fast-forward 但 run 尚未安全关闭；`attention_required` 表示需要人工判断。阶段只供诊断，不授权自动推进。
- 不把半成品交给另一 owner，不恢复旧模型会话，不创建兼容 branch、第二 recovery 对象、后台重试或自动冲突解决器；不 stash、reset、checkout、clean、revert 或泛化删除 worktree。
- 只有证据满足 `CompleteRun` 的精确关闭合同才可人工关闭；否则保留 run 和 worktree，并在必要时继续暂停两个 automation。

## 各阶段人工处理

- `developing`：核对责任方是否仍运行、worktree 是否干净或包含未提交业务现场。不得用新自动轮次重跑。干净且无业务结果的精确现场可按关闭合同处理；有修改或证据不明时保留。
- `candidate_ready`：核对 candidate SHA、唯一父链、branch、changed paths、candidateResult 和工作树。不得自动重放；由普通管理上下文决定人工完成、关闭或保留。
- `canonical_ready`：核对 canonical base/head、正式路径、任务投影和验证证据。需要集成时必须通过 `tools/invoke-project-integration.ps1` 取得与自动入口相同的进程持有型锁；任何路径冲突或 HEAD 变化都停止。
- `integrated`：先证明 `master` 已包含记录的 formal SHA、任务后置状态正确且没有重复通知／清理风险，再精确调用 `CompleteRun`；不得重复 fast-forward 或业务执行。
- `attention_required`：只报告并等待普通管理上下文核验。runtime 原因不能代替任务卡 blocker；若已构成任务级阻塞，按任务维护规则提交任务卡和队列投影。原因是 `task_requires_decomposition` 时，先确认没有 candidate、正式提交或集成；由普通 Codex 规划上下文只针对当前父项一次性建立全部已知子任务卡、依赖图、首批 ready 叶子和父项关闭条件，使父项退出执行队列并仅保留汇总状态。若 worktree 已有业务差异，先保留并判断其证据用途，不把半成品自动分配给子卡；完成规划事实集成且满足精确关闭合同后才关闭原 run。

## 唯一自动继续例外：decision checkpoint

- decision checkpoint 不是普通失败恢复。它必须具有干净 checkpoint 提交和结构化决策合同，精确绑定 taskId、decisionId、baseCommit、branch、SHA、授权路径、验证证据与任务摘要。
- 共享入口已把任务转换为 `pending_decision` 或 `waiting_reply` 并关闭原 run 后，长连接桥只负责接收和鉴权回复；没有有效回复时不推进。
- 有效回复到达后，下一次对应 owner 调用可机械恢复原 route／owner／`ready` 投影，并从最新 `master` 创建新 run、新 worktree 与新模型会话，通过 `cherry-pick --no-commit` 吸收 checkpoint。旧模型会话不恢复。
- checkpoint worktree 只有在新 run 成功吸收并完成正常安全集成、且精确清理合同满足后才删除。普通崩溃、残留、冲突、验证失败或拒绝 fast-forward 不能进入此路径。
