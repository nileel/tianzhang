# U-TZ-CHARTER-MODEL-01 · 三项遗产与册界纯规则模型

## 来源与当前边界

- `D-TZ-CHARTER-SCHEMA-01` 与 `D-TZ-CHARTER-SAMPLE-01` 已提供唯一的 `CharterRuleDefinitions` 静态定义、一个水府地纪有效样例和失败关闭的外部目录；它们没有调用规则事务。
- `D-TZ-CHARTER-CONFLICT-02` 已把跨阶资格与金丹／元婴冲突迁入唯一的 shared `TianZhang.World.CharterConflictRules`；本卡只消费其输入和决定，不能复制 resolver 或 grant。
- 本卡是无场景、无 UI、无存档的纯规则模型切片。`CharterRuntimeStateData` 继续是动态稳定状态承载，环境档案继续只是事件输出引用。

## 实施范围

- 在 `TianZhang.World` 建立一个不持有场景、Unity 对象、全局单例、存档或 BattleSim 账本的纯规则入口；输入仅为已校验定义、动态状态、稳定 ID 和明确的调用请求。
- 依次校验《开阖九章》的通行条件、太玄界印的公共设施管理／受益资格、节点连通、授权版本、传播范围、现实供给和完整正负提交；缺任一条件时返回稳定拒绝且不替换状态。
- 对成功调用一次性构造新的动态状态并在全部校验成功后替换；事件只输出定义已声明的 `environmentProfile` 引用，不能反向改写环境档案。
- 同变量金丹介入只构造完整 v1 `RuleConflictInstance` 并消费 shared 决定；无合法跨阶授权时拒绝覆盖。命中元婴道路锚点只返回受锚结果，不降格为金丹冲突、不开支或提交覆盖。
- 新增直接 EditMode 测试覆盖通行不等于管理、管理不等于改规则、节点断开、覆盖越界、原子拒绝、金丹冲突、元婴受锚和事件唯一记录；在既有样例验证记录补充实际命令和结果。
- 两个新增 Unity C# 文件的相邻 `.meta` 必须作为同一候选提交的一部分；运行 Unity 验证后再次检查工作树，不得把验证生成的 `.meta` 留为未跟踪现场。

## Codex 独立复审未通过（2026-08-03）

- `JindanSameVariable` 在 `crossTierChallengeRequest=null` 时仍进入 shared 决定并返回成功，违反“无合法跨阶授权时拒绝覆盖”；返工必须要求版本化请求、目录声明与 archive 资格同时成立，并补稳定拒绝用例。
- 成功事务把同一现实供给的 `allocated` 记录追加在旧 `registered` 记录之后；下一次调用仍命中旧记录并再次成功，违反现实供给与正负提交的一次性原子边界。返工必须按稳定 ID 替换／结转唯一供给状态，并覆盖重复调用拒绝。
- 冲突结果目前只对 `Rejected`／`Anchored` 分流，`RightWins` 或 `Neutral` 也会构造规则 `NextState`。返工必须明确哪一侧代表本次册界调用，并证明败方／中立不会提交规则状态或事件；不得在本卡内复制 shared resolver 或新增账本所有者。
- 复审核验临时加入两条反例后，Unity EditMode 为 320 项中 316 通过、4 失败：两项既有基线加上述“缺跨阶请求仍成功”“已分配供给仍可复用”两项新增失败。临时反例已撤回，证据登记在 `开发管理/未通过审核清单.txt`。

## Codex 返工复审部分通过（2026-08-03）

- 已确认原三项返工主体有效：金丹分支缺版本化请求时稳定拒绝，目录声明与 archive 资格仍由既有所有者核验；供给按稳定 ID 唯一结转后不可重复消费；shared 决定的赢家与 `charterCandidateId` 不同或无赢家时不提交规则状态和事件。
- 仍有一项失败关闭缺口：`IsCharterCandidateDeclared` 只判断 `charterCandidateId` 是否等于左或右候选 ID，却未要求两侧候选 ID 互异。左右候选使用同一 `CandidateId` 时，该字段不能唯一锁定哪一侧代表册界调用；任一侧获胜都会得到相同 `WinnerCandidateId` 并成功提交。
- 复审核验临时加入重复候选 ID 反例后，Unity EditMode 为 323 项中 320 通过、3 失败：新增反例得到 `Succeeded=true`，另两项为已登记且与本卡无关的既有基线。临时反例已撤回，最窄返工只需拒绝重复候选 ID（或等价地保证册界侧唯一绑定）并保留直接测试，不得修改 shared resolver。
