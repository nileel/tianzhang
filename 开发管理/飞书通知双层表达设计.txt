# 飞书通知双层表达设计

日期：2026-07-28
状态：已批准；仓库实现完成，实时自动化控制器提示词待管理界面同步

## 目标

自动工作流通过飞书发送决策和任务结果时，继续保留供 AI、研发和审计核对的专业准确内容，并在其后增加负责人能够直接理解的通俗版。

通俗版固定为三个短点，不要求负责人理解代码、文件、提交、测试命令或内部工作流术语，也不代替专业事实。

## 已确认选择

- 展示顺序：专业准确内容在前，通俗版在后。
- 通俗版长度：固定三个短点。
- 生成方式：由处理该任务或提出该决策的责任方在形成专业内容时同步撰写；飞书发送层只校验和展示，不再调用 AI 翻译。

## 不采用的方案

- 不由通知脚本机械改写现有专业字段。机械拼接只能改变标题，无法可靠解释专业内容。
- 不在发送飞书前新增一次 AI 调用。该方案会增加调用成本、失败点和专业版与通俗版不一致的风险。
- 不删除、缩写或用通俗版替换现有专业内容。

## 内容契约

### 任务结果通知

现有任务目标、本次完成、实际影响与明确边界、验证结果、后续关系保持不变。其后新增“给负责人看的通俗版”，固定包含：

1. `发生了什么`：说明解决了什么问题或本轮为什么没有完成，不罗列实现过程。
2. `对项目或游戏的实际影响`：说明玩家体验、游戏内容、项目进度或后续工作的真实变化；没有直接游戏效果时必须明确说明。
3. `你是否需要做什么`：明确写“无需处理”，或给出负责人下一步要做的唯一清晰动作。

对 `completed` 和 `pending_review`，三个短点由业务责任方与专业提交元数据同时形成，并作为提交中的稳定通知元数据保存。自动化提交工具新增 `AutomationPlain` 参数，并固定生成单行：

`Plain: 发生=<负责人短句>；影响=<负责人短句>；需要=<负责人短句>`

三个子字段必须非空、单行、各不超过 200 个 Unicode code point，并由同一任务事实和已执行验证支持。

对 `blocked`、`waiting_decision`、`waiting_reply` 和 `failed` 等没有已核验业务提交的终态，通知适配器必须根据已核验终态、任务标题、任务卡原因和固定后续动作生成三点，但不得把未提交或未核验内容写成已完成：

- `发生了什么`：本轮未形成已核验业务提交以及当前终态。
- `对项目或游戏的实际影响`：任务尚未完成，未确认业务行为变化。
- `你是否需要做什么`：依据终态明确等待决定、等待回复、解除阻塞或检查失败原因。

### 决策通知

现有决策编号、关联任务、专业问题、A/B/C 选项、推荐项和专业影响保持不变。其后、操作按钮之前新增“给负责人看的通俗版”，固定包含：

1. `现在为什么需要你决定`：说明当前卡在哪里，以及为什么不能由责任方自行决定。
2. `不同选择的实际区别`：说明选择会怎样影响游戏内容、项目成本、风险、时间或后续方向。
3. `你现在需要怎么选`：用一句话说明可直接选择推荐项，或在什么偏好下选择其他项。

决定请求增加一个必填的通俗说明对象，例如：

```json
{
  "plainSummary": {
    "situation": "现在为什么需要你决定",
    "impact": "不同选择的实际区别",
    "action": "你现在需要怎么选"
  }
}
```

三个字段必须非空、单行、各不超过 200 个 Unicode code point。提出决定的责任方必须同时提供专业字段与通俗字段；发送层不得根据专业字段临时猜测通俗含义。

## 表达规则

- 优先描述“这件事对游戏或项目意味着什么”，实现细节只留在专业版。
- 通俗版避免代码符号、文件路径、提交号、测试命令、内部状态名和只有参与开发才知道的缩写。
- 确实绕不开的专业词，必须在同一句中补充白话解释。
- 不夸大完成度，不把“通过技术测试”直接写成“玩家已经可以使用”。
- 不确定或尚未验证的影响必须明确写成尚未确认。
- “无需处理”“目前不会直接改变游戏表现”等无动作或无直接影响结论必须明说，不能省略。

## 数据流与职责

### 任务完成或待复审

1. 业务责任方依据任务事实和验证结果，同时形成现有专业元数据与三个通俗子字段。
2. 业务责任方通过 `AutomationPlain` 传入三个通俗子字段，自动化提交工具把专业元数据和 `Plain` 元数据一起写入同一业务提交。
3. 固定调用器和外部责任方 closeout 核对该提交同时包含原有六个专业子字段与三个通俗子字段。
4. 飞书通知适配器从同一已核验提交读取两层内容。
5. 飞书卡片先渲染现有五段专业内容，再渲染三个通俗短点。

### 等待、阻塞或失败

1. 固定调用器先按现有流程核验并记录真实终态。
2. 通知适配器使用终态和任务卡事实形成专业状态说明及固定语义的三个通俗短点。
3. 不创建提交，不伪造业务验证，也不改变终态、租约或恢复状态。

### 决策

1. 责任方确认确实到达新的用户决定事件。
2. 责任方在同一个决定请求中同时写入专业问题、选项、推荐、影响和三个通俗短点。
3. 决策桥对所有字段执行现有安全校验和新增长度、完整性校验。
4. 飞书卡片先显示专业内容，再显示通俗版和回复控件。
5. 回复、签名证据、消费请求、恢复和幂等协议保持不变。

## 失败与安全边界

- 缺少任一通俗字段、字段为空、超长、包含非法控制字符或结构不符时，按现有输入无效路径失败关闭，不发送只有专业版的不完整新通知。
- 发送层不自动补写、截断或猜测通俗内容。
- 飞书投递失败仍只返回脱敏结果，不改变提交、任务卡、租约、recovery、终态类别或退出码，也不自动重试。
- 通俗字段不得进入私有 runtime；任务结果以提交元数据为稳定事实，决定内容沿用现有受控请求和消费文件。
- 不改变决定按钮、自定义回复、消息回复、日报、周报或其他通知类型。

## 最小实现边界

实现应只扩展现有内容契约和卡片渲染链路，不新增服务、队列、状态机或模型调用。预计涉及：

- 自动化规则、责任方提示和提交元数据契约；
- 自动化提交工具及其结构化字段校验；
- 任务结果通知适配器与任务结果卡片；
- 决定请求校验与决策卡片；
- 对应的直接测试和自动工作流一致性检查。

如果实施时发现必须新增独立翻译服务、第二份任务状态或发送重试层，应停止实施并重新确认根因与范围。

## 验收标准

- `completed` 与 `pending_review` 任务结果卡片保留现有五段专业内容，并在其后显示三个非空通俗短点。
- 无提交的等待、阻塞和失败通知不会虚构完成内容，并明确负责人是否需要操作。
- 决策卡片保留专业问题、选项、推荐与影响，并在操作控件前显示三个非空通俗短点。
- 通俗版位于专业版之后。
- 每个通俗短点不超过 200 个 Unicode code point。
- 缺失、空白、超长或非法通俗字段会被拒绝，不会静默降级。
- 已有投递幂等、隐私脱敏、回复、恢复、租约和失败语义不变。
- 日报和周报不受影响。

## 验证范围

- PowerShell 适配器测试：提交元数据解析、无提交终态映射、缺失或非法 `Plain` 拒绝。
- Node 决策卡测试：双层顺序、三个通俗字段、安全字符和长度边界、回复控件不变。
- Node 任务卡测试：现有五段内容完整、通俗版位于其后、无回复控件、非法输入失败关闭。
- 固定调用器和外部 closeout 测试：新提交元数据作为成功门禁，通知失败不改变业务终态。
- 自动工作流文本一致性检查：规则、责任方提示和验证脚本使用同一字段名称与语义。

## 实施结果

- 任务结果通知和决策通知的双层表达、输入校验、卡片渲染、责任方契约及对应测试已经完成。
- 已使用真实自动化任务完成结果验证飞书投递，提供方已接受带三个通俗短点的任务结果通知。
- 自动化故障恢复已清除，最终终态已经补记为成功，目前没有租约或恢复阻塞。
