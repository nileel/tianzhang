# EXP-DATA-002 · 原始字节摘要须与提交内容保持一致

## 状态

active；最后核验日期：2026-10-13；事实源：`U-COMBAT-UNARMED-CONFIG-01` 的 `CAND-U-COMBAT-UNARMED-CONFIG-01-01` 及其验证记录。

## 开工前

仅当配置 CSV 或文本的原始字节会写入派生资产摘要、并且该源受 Git 行尾规范化影响时适用。生成资产或记录摘要前，确认工作树源字节与将提交的字节表示一致；按仓库声明的行尾写入后再生成派生资产，并复核源和资产摘要。只计算逻辑字段的规范化摘要、未提交源文件或不记录原始字节摘要的改动排除。

## 正确处理

先核对源文件的 Git 行尾规则和实际工作树字节，再用与提交内容一致的字节生成派生资产及其 `sourceContentHash`。提交前重新读取源和生成物的摘要；若文本写入工具改变了行尾，恢复符合仓库规则的字节后重导，不得把旧摘要、旧资产或工作树偶然通过的检查当作有效结果。

## 根因与弯路

Windows 文本写入把 `AttackProfiles.csv` 改为 CRLF，Unity 导入和工作树检查据此生成资产摘要而暂时通过；Git 提交时按仓库规则规范为 LF，导致提交后的源字节与已生成 asset 的原始内容摘要不一致。恢复 LF 后原生重导，生产摘要从 `31add96a98bf0f61a4ebd1d0e555097a8cb5223d3ffa0a1886f3c14104220738` 修正为 `6515cf7051e81836664f241ac0bf4de276a4921ee5d3e8b169e567c7c938d447`，并通过最终数据链检查。

## 适用与排除

- 适用：原始 CSV／文本字节参与跨端配置、Unity 派生资产或提交后校验摘要，且 Git 可能转换行尾。
- 排除：字段级规范化摘要、二进制输入、未纳入版本控制的临时文件，以及派生物不保存或比较源字节摘要的流程。

## 证据

`CAND-U-COMBAT-UNARMED-CONFIG-01-01`；`开发管理/U-COMBAT-UNARMED-CONFIG-01-验证记录.txt` 的“发现与修正”；该卡记录的 CRLF 与恢复 LF 后的生产摘要及最终 143 项和数据链验证。

## 失效条件

源摘要改为只基于已规范化的逻辑内容、生成器直接消费并记录 Git 过滤后的确定字节、或该配置不再生成／比较原始内容摘要时，停止引用并重新核验摘要合同。
