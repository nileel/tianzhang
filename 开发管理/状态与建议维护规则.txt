# 状态与建议维护规则

## 文件分层

| 文件 | 角色 | 默认读取时机 |
|------|------|--------------|
| `开发管理/当前任务队列.txt` | 有序 ready 调度索引 | 普通 `1` / `2` 和自动选题时读取 |
| `开发管理/任务卡/` | 已进入近期调度或转为非 ready 的活跃任务唯一事实 | 选中 ID 或发生状态事件时读取 |
| `开发管理/设计-当前状态.txt` | 已验证事实、当前风险快照、版本状态 | 判断系统事实或写总结 |
| `开发管理/任务列表/` | 未完成 backlog 与任务卡短投影 | 空队列、拆任务、解阻塞判断时读取 |
| `开发管理/设计-下一步建议.txt` | 设计 backlog 索引 | 判断设计侧入口 |
| `开发管理/开发-下一步建议.txt` | 开发 backlog 索引 | 判断开发侧入口 |
| `开发管理/审核入口.txt` | 审核、复审与 `2` 的短入口 | 审核、未审核标记或用户发送 `2` |
| `开发管理/AI合作沟通.txt` | 当前交接证据 | 选中匹配复审卡后读取，或写入 handoff 证据时 |
| `开发管理/自动工作流规则.txt` | 定时控制器稳定规则 | 修改或诊断自动工作流 |
| `开发管理/自动工作流恢复规则.txt` | schema 5 owner run 人工处置与 decision checkpoint 例外 | 共享入口 `Show` 返回本 owner run |
| `开发管理/自动工作流状态.txt` | 迁移事实、人工阻塞与恢复证据 | 判断自动化闭环或人工处理 |

## 速查层

1. 资料库固定四层：L0 是 `AGENTS.md` 的领域入口；L1 是各域速查卡，只提供线索；L2 是对应业务文件的唯一事实源；L3 是历史归档。速查卡不得成为事实源，也不得以摘要替代 L2 原文。
2. 速查卡的每条条目固定包含：条目名、一句话摘要、`路径#章节` 指针和状态标记；行数上限、板块划分与域内额外字段由各域 IDX 卡面约定。
3. 速查卡头部必须声明：`线索层，冲突以 L2 事实源为准；来源路径：<L2 路径集合>；版本标记：<版本或核验日期>`。来源路径与版本标记必须能追溯当前索引的 L2，不得用未核验内容补充。
4. 任何任务卡的 `expectedPaths` 触及某张速查卡所索引的 L2 事实源时，必须同时列出该 L1 速查卡路径并更新对应条目；巡检卡负责兜底发现遗漏，但不替代同轮同步义务。
5. 速查卡不复制规则文本、不承载未验证数值，也不新增事实源地位文件。各 IDX 卡完成时，必须记录“该域典型任务实际必读量（速查卡+片段）”，供后续与未使用速查层的读取量对比。

## 自动工作流分层

- 共享入口：`Show` 返回本 owner run 时只报告；普通管理上下文按其 state 路由到 `开发管理/自动工作流恢复规则.txt`。无本 owner run 时不读取人工处置规则。

1. `自动工作流规则.txt` 是稳定策略事实源；控制器提示只引用，不复制实现规则。
2. 本机 schema 5 runtime 只保存 `runs.codex`、`runs.deepseek` 及其候选／正式证据；进程持有型集成锁不持久化，实时 automation 配置不复制到项目状态文件。
3. `自动工作流状态.txt` 只记录需长期保留的迁移事实、人工阻塞、恢复所有权和已核验提交；普通空转、有效锁和逐轮轨迹不写入 Git。
4. 队列只在新任务/切片进入、解除阻塞、解冻、优先级/主责/授权/固定顺序变化、完成、阻塞、待决定、等待回复、复审转换、取消或队列为空时维护。
5. 新任务或重新 ready 的任务一次性按“用户明确顺序 → P 优先级 → 高优先级下游解锁量 → 等待时间 → 稳定 ID”插入固定位置；普通轮次不重算顺序。
6. 明确逻辑阻塞立即写入任务卡和 backlog，并从 ready 队列移除；执行器暂不可用或实时路径冲突只是本轮临时跳过，不改卡、不改顺序。
7. 队列为空时只提升或建立当前能够安全形成的 ready 卡并排序、提交；本轮不执行新任务。没有合法来源时不制造任务，也不制造无事实变化提交。
8. 空队列维护先扫描各分线 backlog 中所有明确标为阻塞的任务，再决定是否制卡：对阻塞描述中明确出现的稳定任务 ID，依次核对 `开发管理/任务卡/<ID>.txt` 与 `开发管理/任务归档/<ID>.txt`；backlog 中“阻塞”字样本身不能证明前置仍未完成。命名 blocker 在活跃卡和完成归档中都不存在时保持阻塞，不猜测完成状态；同一 ID 同时存在活跃卡与完成归档等事实冲突时保持阻塞，不提升下游任务。当本轮确认某个具名前置已完成并从直接下游卡移除该 ID，且这次移除使该卡的 `blockedBy` 从非空变为空时，必须继续读取同一卡完整正文并收口这次状态事件：剩余动作若只是当前仓库与已批准事实即可完成的任务卡准备，就在本轮完成准备并重新判断 runnable；若唯一剩余条件是负责人在两条可确定性形成完整 ready 卡的路线中选择，则按维护型 A／B／C 决策合同把卡转为 `pending_decision`，不在同轮等待回复；其他内容冻结、外部工作面、项目闸门、事实冲突或停止条件继续保持阻塞。不得顺带扫描其他原本就是 `blockedBy=[]` 的活跃卡；现有 `stateReason` 已准确时不得机械重写或制造维护提交。命名前置已完成但仍有其他真实条件时，只在原说明失真时改写为实际剩余 blocker；全部前置已完成且现有事实足以满足 runnable 合同（完整 expectedPaths、验证、完成条件和停止条件）时，同步 backlog、建立完整任务卡并按既有排序规则入队。完成全部阻塞项核对及上述直接受影响卡的收口后仍没有合法候选，才允许无修改返回 `no_candidate`。
9. 维护型决策公开字段使用 `automationDecision`，与 `automationCheckpoint` 互斥。首次投影固定 `pending_decision/awaiting_reply` 且不入队；后续合法 A／B 回复在新的 QueueMaintenance run 中完成卡片准备后转 `ready/resolved` 并插入当时空队列的固定位置 0，C 转 `blocked/resolved`。7 天 TTL 到期转 `blocked/expired`；非法回复转 `blocked/attention_required`。resolved、expired 与 attention_required 记录均不得再次被自动回复检查选择。

runnable 必须同时满足：状态待处理；前置完成；主责已授权给可用执行器；没有待决策；内容冻结与项目闸门满足；任务卡能给出完整预期修改路径与验证；预期路径不与现有人工改动冲突。外部 CLI 只在真实选中合法候选并取得租约后预检；不得因执行器临时不可用改派主责。

## 状态与队列

1. `设计-当前状态.txt` 只写已验证结果、当前版本、已知风险和数据快照；未执行的下一步不写入正文。
2. 状态标记使用“审核完成”“⚠️ 已修改/未审核”“⚠️ 待复核”“❌ 未接入”。完成结论必须可指向验证命令、提交号或审核证据。
3. 当前队列只保存 ID、route、owner、priority、domain、stage、title 和 task-card path；独立卡头是结构化字段唯一事实源，正文保存来源、必查范围、实施范围、禁止项、验证、完成条件和停止条件。
4. `必查范围` 优先使用 `文档路径#章节`、`代码路径::类型.符号`、`CSV/JSON路径::实体ID` 或 `资源目录::用途/资源ID`；路径自身已经是不可再分的短事实源时可以只写路径。
5. 代码必查范围覆盖目标类型和方法、直接调用者与被调用者、相关测试，以及任务卡指定的当前所有者或事实源；CSV 覆盖表头和目标 ID 行；JSON 覆盖目标对象和直接引用；Unity `.asset` 覆盖目标资源及必要引用；`.meta` 只用于 GUID、导入和依赖身份，不承载业务说明。
6. 既有任务卡的路径级 `必读` 默认要求先定位其中与任务相关的章节、符号或实体，不表示整份加载。只有任务卡明确写“完整文件”、无法保持语义边界、检索无结果或存在事实冲突时才读取全文；修改前仍须读取目标完整逻辑单元。
7. Codex 任务完成后归档；外部 AI 业务提交进入待复审，由 `2` 处理。
8. 队列不保存长解释、历史争论或完整审核过程；长期任务留在分线 backlog。

任务卡枚举固定为：`route ∈ {codex_execute, external_execute, codex_review}`；`owner ∈ {codex, deepseek, claude}`；`priority ∈ {P0, P1, P2, P3}`；`domain ∈ {unity, battlesim, data, content, management, automation}`；`stage ∈ {discovery, decision, design, implementation, migration, verification}`；`dispatchState ∈ {ready, blocked, frozen, pending_decision, waiting_reply, completed}`。状态位置固定为：

- `ready` -> active card + backlog + ordered queue
- `blocked/frozen/pending_decision/waiting_reply` -> active card + backlog, never queue
- `completed` -> card moved to 任务归档 and removed from queue/backlog

新卡完成时只移入精确路径 `开发管理/任务归档/<ID>.txt`；每张活跃卡的 `expectedPaths` 必须同时包含 `开发管理/任务卡/<ID>.txt` 与 `开发管理/任务归档/<ID>.txt`。凡任务可能创建、移动或首次导入 `src/Assets/` 下的 Unity 文件或目录，`expectedPaths` 必须同时列出目标及其对应 `.meta`；新目录本身的 `.meta` 也须列出。历史合并归档保持原样，默认检查不递归扫描。

## 建议与闭环

1. 设计/开发下一步建议只作索引，不作 `1` 的默认全文入口。
2. 需要进入近期调度的条目，以稳定 ID 建立或更新唯一任务卡及 backlog 投影，再按状态事件插入队列固定位置。
3. 已完成条目的事实说明转入当前状态，历史过程转入归档。
4. 执行前从队列取得 ID，按任务卡必查范围先定位、后读取；发现新依赖时补读，修改前读取目标完整逻辑单元。执行后只运行任务卡要求的最小充分验证。
5. 完成、阻塞、复审转换等状态事件在同一管理切片内同步更新任务卡、backlog 和队列；普通轮次不补位、不重排。

## 检查脚本入口

- 文本/审核材料：`pwsh -NoProfile -ExecutionPolicy Bypass -File tools/check-review-text.ps1 -Paths AGENTS.md,CLAUDE.md,开发管理`
- docs/CSV/Unity 数据链路：`pwsh -NoProfile -ExecutionPolicy Bypass -File tools/check-data-chain.ps1`
- 严格缺失 asset：`pwsh -NoProfile -ExecutionPolicy Bypass -File tools/check-data-chain.ps1 -FailOnMissingAssets`
- 资产版本边界仅在相关路径变化时运行 `tools/check-asset-versioning.ps1`。
- 只在创建/修改任务卡、改变任务状态、改变队列、队列补位或提交相关管理文件前运行 `tools/check-task-cards.ps1`；普通每小时轮次不运行全量检查器。
- `tools/check-task-cards.ps1 -TaskId <ID> -Postcondition CodexDispatchReady -ExpectedRoute <codex_execute|codex_review>` 只接受同 ID、`owner=codex`、`dispatchState=ready` 且 route 精确匹配的 active 卡；`CodexClosedOrNonReady` 只接受 exact completed archive 或同 ID 的 `{blocked,frozen,pending_decision,waiting_reply}` active 非 ready 卡；`ExternalPendingReview` 只接受同 ID 的 `route=codex_review`、`owner=codex`、`dispatchState=ready` active 卡。维护型状态提交分别使用 `MaintenancePendingDecision`、`MaintenanceResolvedReady`、`MaintenanceResolvedBlocked` 与 `MaintenanceExpiredBlocked`；全局检查同时断言 checkpoint／maintenance 字段互斥及维护型 A／B／C、证据与状态一致。省略 postcondition 时保持全局投影检查；附加 `-OutputJson` 时输出同一检查结果的 `cardCount`、`readyCount`、`taskId`、`taskState` 与 `postcondition` 瞬时证据，不写入 runtime。
- `QueueMaintenance` 以 `tools/check-task-cards.ps1 -OutputJson` 返回的 `readyCount` 作为候选存在性证据，无需再用 `rg` 无匹配证明不存在；但 `readyCount` 只反映已经存在的任务卡与投影，不能替代对 backlog 命名 blocker 的新鲜度检查——只有先完成上述阻塞核对并刷新投影/制卡后，仍无合法候选时才返回 `no_candidate`。
