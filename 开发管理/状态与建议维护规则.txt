# 状态与建议维护规则（⚠️ 已修改/未审核）

> 2026-06-17 Codex / ChatGPT5.5 新增：用于把事实状态、短期任务和长期建议分层维护，降低每次启动的默认上下文消耗，待后续复审。

## 文件分层

| 文件 | 角色 | 默认读取时机 |
|------|------|--------------|
| `开发管理/当前任务队列.txt` | 近期可执行任务，`1` 的首选入口 | 用户发送 `1`、规划本轮要做什么 |
| `开发管理/设计-当前状态.txt` | 已验证事实、当前风险快照、版本状态 | 需要判断当前系统事实或写总结 |
| `开发管理/设计-下一步建议.txt` | 设计 backlog 与阶段性候选任务 | 当前任务队列为空或需要扩展设计路线 |
| `开发管理/开发-下一步建议.txt` | 开发 backlog 与阶段性候选任务 | 当前任务队列为空或需要扩展开发路线 |
| `开发管理/审核入口.txt` | 审核和复审的短入口 | 涉及审核、复审、未审核标记 |
| `开发管理/AI合作沟通.txt` | 当前交接队列 | 需要消费另一个 AI 的交接或写交接 |

## 状态文件规则

1. `设计-当前状态.txt` 只写事实：已验证结果、当前版本、已知风险、数据快照。
2. 未执行的“下一步应该做什么”不写入状态文件正文；只保留必要的风险说明和事实依据。
3. 状态标记统一：
   - `✅ 已审核`：已通过规定审核或复审。
   - `⚠️ 已修改/未审核`：已改但未通过审核。
   - `⚠️ 待复核`：已有实现或数据，但验证不足。
   - `❌ 未接入`：明确尚未实现。
4. 任何“已完成”必须能指向验证命令、提交号或审核依据；否则写“待复核”。

## 任务队列规则

1. `当前任务队列.txt` 只放 5-10 条近期任务，必须能在一轮或少数几轮内提交。
2. 每条任务必须包含：ID、优先级、主责、类型、状态、必读文件、验证命令、完成条件。
3. 完成后优先把队列状态改为“待复审”；审核通过后改为“已归档”并移出队列。
4. 队列任务不得保存长解释、历史争论或完整审核过程；这些内容写入归档、回复、commit log 或 PR 描述。

## 建议文件规则

1. 设计/开发下一步建议作为 backlog，不作为 `1` 的默认全文入口。
2. 进入当前 5-10 条最高优先级的任务，复制到 `当前任务队列.txt` 后再执行。
3. 已完成且通过审核的条目，从建议文件移除或移到已完成摘要；不在建议文件中长期保留大段完成过程。
4. 若某条建议只剩事实说明，应转入 `设计-当前状态.txt`；若只剩历史过程，应归档。

## 完成闭环

1. 执行任务前：从 `当前任务队列.txt` 取 ID，并按任务卡读取事实源。
2. 执行任务后：运行任务卡验证命令，回复中列修改文件、验证结果和残留风险。
3. 提交后：更新任务队列状态；如完成并通过审核，再同步状态文件或建议文件。
4. 推送远端后：从队列移除已归档任务，必要时从 backlog 补入下一条。

## 检查脚本入口

- 文本/审核材料机械检查：`powershell -ExecutionPolicy Bypass -File tools/check-review-text.ps1 -Paths AGENTS.md,dev-mgmt`
- docs/CSV/Unity asset 数据链路检查：`powershell -ExecutionPolicy Bypass -File tools/check-data-chain.ps1`
- 数据链路严格检查缺失 asset：`powershell -ExecutionPolicy Bypass -File tools/check-data-chain.ps1 -FailOnMissingAssets`
