# 审核规则

## 文件职责

- `开发管理/审核入口.txt`：审核时的短入口与按需读取路由。
- 本文件：审核、复审、交接材料与归档细则。
- `开发管理/未通过审核清单.txt`：当前未通过项及其复核建议。
- `开发管理/AI合作沟通.txt`：当前交接线索，不是审核结论或事实源。

## 审核边界

- Codex / ChatGPT5.5 自产主责工作，完成必要验证、记录证据和残留风险后可闭环。
- DeepSeek、外部交接或用户指定复审的修改，必须先标「⚠️ 已修改/未审核」，由 Codex / ChatGPT5.5 依据 diff、事实源和可重复命令独立审核。
- 未审核标记应附修改方、提交号或变更范围；不得预填审核方结论。
- 设计内容核对对应规范与 `docs/` 原文；会改变模拟输出的数值改动运行 BattleSim；代码按影响面运行测试；CSV / asset 核对数据口径和重复项。
- 审核完成后移除正文临时记录。详细过程、验证命令和责任记录进入回复、commit log、PR 描述或归档。

## 最小验证

- 审核目标是确认提交满足任务卡，而不是重做完整任务。
- 默认读取审核入口、`git status`、目标 diff、被改文件必要段落和任务卡完成条件。
- 文档/状态提交运行 `tools/check-review-text.ps1` 与 `git diff --check`；CSV/asset 运行 `tools/check-data-chain.ps1`；代码运行相关 build/test；数值参数、BattleSim 代码或新增模拟结论才运行 BattleSim。
- 若跳过高成本验证，结论中必须说明影响范围和跳过原因。

## 交接材料

交接条目必须写明发起方、接收方、任务或提交范围、修改文件、验证命令及结果、未验证项、残留风险和请求判断。数据快照需说明统计口径；CSV → Unity asset 需区分文件总数、按 CSV ID 匹配的有效覆盖、缺失与额外/旧版 asset。

审核方应把每个风险和疑点映射到 diff、事实源或验证输出；交接本身有误时，先作为审核问题处理。长期阻塞项进入 `开发管理/未通过审核清单.txt` 或相应 backlog，已无后续价值的条目移入 `开发管理/AI合作归档/`。

## 复审

复审仅处理 DeepSeek / 外部交接成果、已按审核反馈修复但仍标为未审核的内容，或用户明确指定的提交 / diff；不是复述修复方声明。

1. 读取审核入口、对应未通过项、修复 diff 或提交及相关事实源。
2. 逐项核对修复结论，并按影响面运行最小必要检查。
3. 文档/CSV 复核临时记录、重复 key、数量口径、编码/BOM 和残留转义文本；代码或数值只在本次改动影响相应范围时运行测试或 BattleSim。
4. 结论为“通过 / 部分通过 / 不通过”。部分通过时，仅移除已解决项，其余继续保留。

DeepSeek 或外部执行方不得复审自己的修改；DeepSeek 经 API 调用时修改方仍为 DeepSeek。纯 `2` 的选题和身份流程见 `开发管理/AI协作规则.txt`。
