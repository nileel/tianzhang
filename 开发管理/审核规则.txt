# 审核规则（✅ 已审核）

> 2026-06-16 Codex / ChatGPT5.5 复审通过：补充 DeepSeek 收到 `1` 自动推进后的审核边界。

## 文件定位

- `开发管理/审核入口.txt`：默认先读的短入口，用于判断本轮还需要读哪些文件。
- `开发管理/审核规则.txt`：审核流程、复审身份、交接材料消费和归档细则。
- `开发管理/未通过审核清单.txt`：当前未通过项和后续复审建议；只在修复或复审清单项时读取对应条目。
- `开发管理/AI合作沟通.txt`：当前交接队列；历史长记录移入 `开发管理/AI合作归档/`。

## 基本规则

- **两步操作**：所有修改必须先「修改」→标注为「⚠️ 已修改/未审核」，再由另一个 AI（或同一 AI 在后续对话中）进行「审核」→标注为「✅ 已审核」后方可视为完成。任何 AI 不得将未审核的修改标记为已完成。
- **默认审核方**：用户未另行指定时，审核方默认定为 ChatGPT5.5 / Codex；执行修改的 AI 不得在同一轮对自己的修改标记「✅ 已审核」。
- **审核追踪**：未审核标记必须附修改方、提交号或变更范围；审核方优先按 git diff、指定提交和文件清单复核，不做无差别全仓重读。
- **事实源复核**：设计内容核对对应规范与 `docs/` 原文；数值结论运行 BattleSim；代码改动按影响面运行相关测试；CSV / asset 任务核对数据口径和重复项。
- **审核记录归档**：审核通过后，应移除正文内临时审核记录；文档只保留当前有效内容和必要短状态，详细审核过程、验证命令、修改方/审核方与依据写入 git commit log、PR 描述、审核回复或归档文件。
- **交接材料定位**：`开发管理/AI合作沟通.txt` 是交接线索和待判断事项记录，不是审核结论、事实源或通过依据。

## AI 交接材料复核规则

审核 DeepSeek 或其他 AI 的交接任务时，先读取 `开发管理/审核入口.txt`，再读取 `开发管理/AI合作沟通.txt` 中与本轮提交、任务 ID 或文件范围匹配的当前条目。历史归档只在当前条目引用或事实缺口需要时读取。

交接材料必须满足：

1. 明确写出发起方、接收方、日期、任务范围或提交号。
2. 列出修改文件、验证命令、验证结果、未验证项和残留风险。
3. 只写“待 Codex / ChatGPT5.5 复审”或“请求判断”，不得预填审核方结论。
4. 数据快照必须说明统计口径；CSV → Unity asset 必须区分文件总数、按 CSV ID 匹配的有效覆盖数、缺失数和额外/旧版 asset 数。
5. 不得包含不可见控制字符、乱码提交号、过期数据口径或与 git diff 不一致的文件清单。

审核方消费交接材料时：

1. 逐项把交接中的风险和疑点映射到 git diff、事实源文件或验证命令。
2. 发现交接材料本身有误时，应作为审核问题指出；必要时要求修复交接文档后再继续复审。
3. 长期阻塞项进入 `开发管理/未通过审核清单.txt` 或下一步建议文件；`AI合作沟通.txt` 不承担永久任务清单职责。
4. 复审通过后，按审核记录归档规则清理正文临时记录；详细过程进入回复、commit log、PR 描述或归档文件。

## DeepSeek 一键推进后的审核边界

DeepSeek 收到用户消息 `1` 后可按 `开发管理/DeepSeek工作提示词.txt` 自动执行、验证并提交，但其成果默认仍是「⚠️ 已修改/未审核」。

1. DeepSeek 可直接提交执行成果，提交信息需体现 DeepSeek 与待 Codex / ChatGPT5.5 复审语义。
2. DeepSeek 不得在同一轮把自己的修改改为「✅ 已审核」。
3. Codex / ChatGPT5.5 后续复审时，必须依据 git diff、验证命令、事实源文件和 `AI合作沟通.txt` 当前交接条目独立判断。
4. 复审通过后，Codex / ChatGPT5.5 才能移除临时未审核标记或改为「✅ 已审核」并提交。
5. 若 DeepSeek 在 `1` 流程中遇到 Codex 主责问题，应只写交接请求，不得硬改架构、数值定论或复杂 Unity 方案。

## 复审规则

复审指对“已按审核反馈修复、但仍标为 ⚠️ 已修改/未审核”的内容进行再次审核。复审不是复述修复方声明，必须独立验证。

复审必须执行：

1. 读取 `开发管理/审核入口.txt`、原始未通过审核清单对应条目、修复方提交或当前 diff、相关规范/事实源。
2. 逐项核对修复方声称已解决的问题，并重新运行对应检查命令。
3. 对文档/CSV 修复，同时检查临时审核记录、重复 key、数量口径、编码/BOM、残留转义文本等机械问题。
4. 对代码或数值修复，按影响面运行测试或 BattleSim；未运行不得给通过结论。
5. 输出结论必须分为“通过 / 部分通过 / 不通过”。部分通过时，只能移除已通过项，未通过项继续保留在清单中。
6. 只有复审通过后，才可移除正文里的临时审核记录并标记「✅ 已审核」；详细复审过程写入回复、commit log、PR 描述或归档文件，不在正文长期累积。

## 复审身份约束

- 执行修复的 AI 不得在同一轮复审自己的修改。
- DeepSeek V4 Pro 经 Codex API 调用时，身份仍是 DeepSeek，不得把修改方写成 Codex。
- 修复方不得预填“审核方：Codex / ChatGPT5.5”或“已复核”；只能写“待复审”。
- Codex / ChatGPT5.5 复审 DeepSeek 变更时，应按事实记录“修改方：DeepSeek，审核方：Codex / ChatGPT5.5，依据：提交号或 diff”。
