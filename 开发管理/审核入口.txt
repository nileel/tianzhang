## 先读规则

涉及审核、复审、未审核标记、交接消费、`1` 执行选题或 `2` 复审选题时，默认先读本文件。只有命中下方路由时，再读取对应长文件或事实源。

## 不可省略的硬规则

1. 修改与复审分离仅适用于 DeepSeek V4 Pro、外部交接或用户明确要求复审的内容；Codex / ChatGPT5.5 自产工作完成必要验证后不进入待复审队列，可按验证证据直接闭环。
2. 审核以 `git diff`、提交号、文件清单和事实源为准，不以交接自述为准。
3. 审核结论只能是“通过 / 部分通过 / 不通过”；验证命令按本次改动影响面最小化执行，必须说明运行或未运行原因。
4. 通过后清理正文临时审核记录；详细过程进入回复、commit log、PR 描述或归档文件。
5. `AI合作沟通.txt` 只保存当前有效交接队列；历史长记录按需查 `开发管理/AI合作归档/`。
6. 轻量优先：只审核文档、状态或队列的提交时，不重跑 BattleSim、Unity 编译或数据链路全量检查；除非该提交修改代码、CSV、asset、数值参数、数值结论，或任务卡明确要求。

## 轻量审核默认流程

1. 先看 `git status --short`，确认本轮相关文件和无关脏改。
2. 审核提交时优先看 `git show --stat --name-only <commit>` 与目标文件 patch；审核当前改动时看限定路径的 `git diff`。
3. 只读取被改文件的必要段落、任务卡完成条件和直接事实源；不默认全仓搜索或通读长文。
4. 按影响面选择最小验证：文档/管理文件运行 `tools/check-review-text.ps1` 与 `git diff --check`；CSV/asset 改动运行 `tools/check-data-chain.ps1`；代码改动运行相关 build/test；BattleSim 代码、数值参数或新平衡结论改动才运行 BattleSim。
5. 审核回复只给结论、依据、已运行检查和未运行检查的原因；避免复述大量原文。

## Token 节流规则

- 默认摘取当前任务相关条目，不全仓重读、不全文件重读历史归档。
- 交接条目写短 ID、提交号、文件范围、验证命令和风险；长过程移入归档。
- DeepSeek 任务先读 `DeepSeek工作提示词.txt` 路由，再按任务类型读取一个任务卡，不默认读取全部任务模板。
- 未通过清单只读当前要修复或复审的编号；完成并通过后从清单移除，详细过程归档。
- `1` 自动推进优先从 `当前任务队列.txt` 取执行型任务；设计/开发下一步建议作为长期 backlog，不作为默认全文启动上下文。
- `1` 自动推进遇到“待复审”任务时一律跳过并继续找下一条“待处理”任务；`2` 才进入复审队列。
- Codex / ChatGPT5.5 自产工作只要求按任务影响面验证并记录证据，不再为了“复审状态”重复排队；DeepSeek 或外部交接成果仍须保留待复审状态，直到 Codex / ChatGPT5.5 在 `2` 或明确审核任务中处理。
- 高频机械检查优先调用 `tools/check-review-text.ps1` 与 `tools/check-data-chain.ps1`，再按输出决定是否读取长文细节。
- 禁止默认全仓 `rg`、全量读取长文或重复运行昂贵模拟；除非最小事实源与最小验证无法判断。
