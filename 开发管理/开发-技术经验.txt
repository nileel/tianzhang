## 编码与文件

- **编码已统一**：项目所有源文件（.cs, .txt, .md）已统一为 UTF-8 with BOM。直接用 ReadAllText/WriteAllText 即可，无需特殊编码处理。obj/ 下构建产物为自动生成，忽略。
- **PowerShell 批量写 txt**：多行中文内容用 `@'...'@ | Out-File -Encoding UTF8` 写入，`@'` 内可含单引号无需转义。注意结尾 `'@` 必须顶格。
- **PowerShell 7 唯一受支持运行时（✅ 已审核）**：项目 PowerShell 脚本只支持 PowerShell 7；当前已通过 winget 安装 7.6.2，入口为 `pwsh`。系统自带 Windows PowerShell 5.1 未被替换，但项目不得调用它。所有独立进程命令统一使用 `pwsh -NoProfile -ExecutionPolicy Bypass -File ...`。
- **注意**：部分历史 .cs 文件可能仍为 GBK 编码（如曾被旧工具编辑过），读写前需检测编码或先转换为 UTF-8 with BOM。

## 编辑原则

- **行级编辑优于字符串替换**：`Replace` 易因换行符/空格差异静默失败。拆成数组 `$lines` 按行号精准编辑更可靠。
- **已有参数优于新增参数**：发现现成接口参数时优先接入，避免新增签名。
- **复杂编辑直接重写整个文件**：多次用正则替换改代码容易导致括号丢失、方法截断。重写比部分替换更可靠、更快。

## 策划配置化规则

- **高频调参内容不得硬编码**：凡是预期由策划反复调整的数值、规则阈值、成本表、权重表或阶段参数，默认使用 `Assets/DataConfig/*.csv → DataConfigImporter 生成 ScriptableObject asset → 运行时代码读取 asset` 的结构。
- **代码只保留安全兜底**：运行时代码可以保留与当前表一致的 fallback 默认值，用于配置缺失时避免崩溃；业务逻辑不得把 fallback 当作主要调参入口。
- **新增配置要可测**：落地新配置时至少补一个测试证明修改配置会改变规则结果，避免“表格存在但逻辑仍读硬编码”的假配置。

## 模拟器

- **模拟器即真理**：任何数值平衡讨论必须先跑 `dotnet run -c Release --project simulations/BattleSim` 看矩阵输出，不要凭感觉判断。
- **模拟器修改先 build 再 run**：修改 Program.cs 后先 `dotnet build --no-restore -c Release` 排查编译错误，再 `dotnet run --no-build` 验证默认参数下输出应与修改前一致（treasureGrade="" 时 bonus=0）。
- **文档跟着模拟器走**：模拟器参数调完，必须同步更新对应的 docs 设计文档（术法/神通倍率等），否则下次对话会出现两边不一致。
- **同境矩阵必须过滤境界**：输出标题写“金丹同境”时，参与样本必须双方均为金丹；如果修炼池里有筑基/练气角色，必须过滤或在标题中标注“混境”。平均回合数同理。
- **对称性改动要双向检查**：`Combat.Simulate` 中 A/B 两套分支必须同时接入同一机制。符胆、雷劫、受击减防、抗性键名这类状态尤其容易只改一边。
- **1v1/2v2 键名必须共用**：二级属性字典不要同时出现 `物抗率/魂抗率` 与 `物理抗性/神魂抗性` 两套键。新增属性时先定义常量或统一 helper，再在 1v1 和 2v2 同时使用。
- **2v2 超时不能默认 A 方胜利**：达到回合上限且双方仍有存活单位时，按双方剩余 HP 比例或明确的平局规则结算，避免群战矩阵系统性偏向左侧队伍。

## BattleSim 建模模式

- **功法成长表优先于权重**：SubGrowthSum 新增 gongFaName 可选参数，有功法名时直接读取 GongFaTables 字典（值=每境每级点数×小境界数，无需权重缩放），无功法名时回退原有权重近似。BuildDef 新增 GongFaName 字段。
- **BuildDef 追加后 N 自动增长**：`int N = buildDefs.Length` 是动态的，新增 Build 无需手动改 N。
- **守一/符胆建模经验**：守一是"累积型buff"（叠层不消耗，受击消耗1层减伤），适合持续作战；符胆是"消耗型爆发"（使用即清零，需重新叠），金丹期偏弱但元婴/化神解锁更强机制后起飞。两者都应在 `Combat.Simulate` 内用局部变量建模，与川流/逝水/秋水保持一致的初始化模式。

## 流程管理

- **下一步建议清理时机**：条目完成并推送远端后，从相应下一步建议文件移除该条→重编号剩余条目。不要在提交前删除（万一回退会丢记录）。
- **角色立绘生成工作流**：生成或整理角色立绘时，先读 `assets/generated-character-art/README.md`；PC 人物介绍与角色资料的当前统一入口是 `assets/generated-character-art/profile-wide/prompts.md`，无字概念原版在 `no-title/prompts.md`，透明全身母版在 `dialogue-transparent/prompts.md`，静态合成预览在 `titled/prompts.md`。16:9 只约束人物介绍 UI、背景、FX 和静态预览，不横向拉伸透明人物母版；人物介绍、对话半身和头像默认裁切同一 RGBA 全身图。透明版先用 image2 生成纯绿幕源图，再本地抠图并验四角 alpha；姓名、道号与印章必须独立分层并逐字验收，复杂汉字优先从已验字样张提取或使用已确认授权的正确字体，不依赖 AI 重写。

## Unity 开发经验

- **先决定战斗框架再写功能**：当前项目目标是 CTB 战棋。若代码使用严格交替回合制，必须明确是临时原型还是正式改设计；不要让 UI 显示 CTB、底层却按交替回合跑。
- **CTB 量纲要可验算**：文档写“每刻 CT += 反应，CT≥100行动”时，反应100应一刻行动。实现若使用归一化速度，必须同步文档或在代码注释中写明换算。
- **冷却惩罚不是冷却倒计时**：文档中的术法冷却惩罚是下次行动门槛/行动轴惩罚，不应简单等同于按钮 CD 或把 CT 扣到0。UI CD、行动轴惩罚、技能可用性要分层。
- **DamageCalculator 注释必须真实**：只有公式、判定顺序、参数量纲与 BattleSim 一致时，才能写“与 BattleSim 对齐”。临时公式要标明“原型公式”，避免误导数值判断。
- **五行实现以 v5.10 为准**：Unity 后续应实现“术法/神通属性 vs 施法者功法属性（内圈）+ 术法/神通属性 vs 目标功法属性（外圈）”，不要再只做功法对功法 ±25%。
- **槽位数组先算上限再初始化**：`MaxSpellSlots/MaxSkillSlots` 必须先确定，再创建冷却数组和按钮数据；否则空装备角色会得到0长度冷却数组。
- **UI 统一画布**：所有 UI 面板（战斗 UI、门派选择等）必须挂载到同一个 UICanvas 下，不要各自创建独立 Canvas。BattleUIManager 在 BuildUI 时创建名为 "UICanvas" 的根 Canvas（DontDestroyOnLoad），其他 UI 组件通过 `GameObject.Find("UICanvas")` 找到并挂载。SectSelectionManager.Start() 已内置此逻辑。

- **VerticalLayoutGroup**：使用自动布局时必须同时勾选 childForceExpandWidth 和 childForceExpandHeight，否则动态创建的按钮不会显示。

- **命名空间不与 Unity 类型冲突**：如 `TianZhang.Tilemap` 与 `UnityEngine.Tilemaps.Tilemap` 冲突 → CS0118。避免用常用 Unity 类名做命名空间。
- **C# 版本兼容**：项目已迁移到 Unity 6，但仍优先使用保守、已验证的 C# 语法；不要为了语法糖引入 Unity 编译链尚未验证的新特性。
- **六角格坐标转换**：不要手写 offset 公式。Unity Grid 的 `GetCellCenterWorld` / `WorldToCell` 是唯一可靠来源。点击检测用全量缓存 + 最近邻查找最稳妥。
- **场景生成**：用 Editor 脚本 (`MenuItem`) 程序化生成，永远不要手写 .unity YAML。
- **视觉反馈**：角色移动需实时更新 Transform；受击加 Coroutine 闪烁；死亡改色。

## Python 文件编辑

- **Python 已接入**：复杂文件编辑（多文件、精确替换、编码转换）优先用 Python 脚本而非 PowerShell 正则替换，避免中文/emoji 编码损坏。
- **.cs 文件编码处理**：优先用 `open(path, "r", encoding="utf-8-sig")` 读取，`utf-8-sig` 写入。如果解码失败则回退到 GBK：先用 `open(path, "rb")` 读原始字节，`raw.decode("gbk")` 解码，修改后用 `content.encode("gbk")` 写回，最后用 PowerShell 转 UTF-8 with BOM。
- **控制台输出编码**：PowerShell 管道到 Python 时 stdout 默认 GBK，遇到 emoji 会崩溃。设 `$env:PYTHONIOENCODING="utf-8"` 解决。Python 内部避免 print 含 emoji 的字符串，改用 `repr()`。
- **方法体替换策略**：字符串 `replace` 容易因换行符（`\n` vs `\r\n`）差异静默失败。改用索引定位 + 括号匹配切割：`content.find("方法签名")` 定位起点，扫描 `{` `}` 计数找到方法体终点，整体替换。比正则或字符串匹配可靠得多。
- **Script 文件方式编辑**：中文路径/emoji 在 PowerShell heredoc 传 Python 时容易损坏。改为 `Out-File -Encoding UTF8 tmp.py` 写入脚本文件再 `python tmp.py` 执行，执行完删除临时文件。

## PowerShell 批量编辑大文件

- **括号平衡验证**：多次 `Out-File` + 行级替换后务必验证 `{` `}` 数量一致。
  `($content -replace '"[\""]*"', '').ToCharArray() | Group-Object | ? Name -match '[{}]'`
- **替换残留检查**：替换方法体后检查旧代码是否完全移除（可能出现新旧代码并存）。
- **字符串插值干扰**：统计括号时先移除字符串字面量（包括 `$"..."` 内括号）。

### .meta 文件绝不可写成单行
- Unity 的 `.meta` 文件是 YAML 格式，必须包含换行符。单行 `.meta` 会导致 Unity 完全无法解析该脚本——不会加入 csproj、不会编译、运行时报找不到命名空间。
- 正确模板（保留尾随空格，那是 YAML 空值占位符）：
```
fileFormatVersion: 2
guid: <32位hex>
MonoImporter:
  externalObjects: {}
  serializedVersion: 2
  defaultReferences: []
  executionOrder: 0
  icon: {instanceID: 0}
  userData:␠
  assetBundleName:␠
  assetBundleVariant:␠
```
> 模板中的 `␠` 是可见占位符；实际写入 `.meta` 时必须将它替换为一个真实 U+0020 空格，不得把该符号本身写入文件。
- 写入方式：`[System.IO.File]::WriteAllText($path, $content, [System.Text.UTF8Encoding]::new($false))`（无 BOM，LF 换行）。不要用 PowerShell 的 `Set-Content` 写 `.meta`——它对字符串列表的处理不可靠。

### .meta 尾随空格是必需的
- `userData: `、`assetBundleName: `、`assetBundleVariant: ` 行末的空格是 YAML 空值语法，删掉会导致 Unity 解析异常。
- `git diff --check` 对此的 trailing whitespace 报错是误报（对比对象是单行版 `.meta` 时尤其如此）。不要为了通过 `git diff --check` 而删除这些空格。

### asmdef 分层后的 csproj 排查
- Unity 生成的 `*.csproj` / `*.sln` 均由 `.gitignore` 排除，不得手工维护或纳入 Git。当前源码按 `TianZhang.Foundation`、`Domain`、`Combat`、`Gameplay`、`Editor` 与 `EditModeTests` 的 asmdef / asmref 分层，不存在活动的 `Assembly-CSharp` 程序集。
- 快速编译使用 `dotnet build src/TianZhang.EditModeTests.csproj`，由其 ProjectReference 覆盖现行命名程序集；权威 Unity 编译与测试使用 `pwsh -NoProfile -ExecutionPolicy Bypass -File tools/run-unity-editmode-tests.ps1`。
- 编译报 `namespace does not exist` 时，先确认脚本所属 `.asmdef` / `.asmref` 及依赖方向，再在对应 `TianZhang.*.csproj` 中核对 Compile / ProjectReference。生成投影缺失时由 Unity 刷新工程，不得给旧 `.csproj` 追加源码或兼容引用。

### PowerShell 写文件陷阱
- `Set-Content -Value [List[string]]` 会将列表序列化为单行 `ToString()` 而非逐行写入。逐行写入用 `[System.IO.File]::WriteAllLines` 或 `$array | Set-Content`。
- 字符串 `Replace` 对换行符（`\n` vs `\r\n`）和缩进空格极为敏感，跨行匹配失败时静默不报错。复杂编辑拆为行数组按索引操作更可靠（已有经验：见"行级编辑优于字符串替换"）。
- `Get-Content` + `Set-Content -Encoding UTF8 -NoNewline` 的管道组合对 `.meta` 小文件可能吞掉换行符。写 `.meta` 一律用 `[System.IO.File]::WriteAllText/WriteAllLines`。

### Unity 场景验证注意
- Hierarchy 只显示当前打开的 .unity 文件。磁盘上场景已更新但 Hierarchy 无变化 → 在 Project 窗口双击该场景重新打开。
- Editor 脚本生成的场景写入磁盘后，不会自动替换编辑器中已打开的同名场景。
