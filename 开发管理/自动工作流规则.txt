# 自动工作流规则

本文件定义 Codex / DeepSeek 两个独立小时定时器共用的唯一编排边界。业务事实仍以任务卡和有序队列为准；模型只负责 candidate，确定性的 PowerShell 共享内核负责 Git、runtime、任务投影、验证、集成、通知和清理。

## 实时入口与事实源

- `codex-hourly-worker` 每小时 `:15` 前台调用 `tools/invoke-hourly-owner.ps1 -Owner codex -Action RunOnce -Model <实际 model>`；`deepseek-hourly-trigger` 每小时 `:45` 前台调用同一脚本并传入 `-Owner deepseek -Action RunOnce`。两个定时器继续独立运行，可分别开发不同 taskId。
- automation 对话的长时间共享入口 cell 只等待同一前台调用；项目业务输出仍是单个结构化终态 JSON，Desktop 展示层在其后追加恰好一个简短 `::inbox-item`。触发层不读队列、任务卡或模型正文，也不管理任何 automation。automation memory 只记录本轮时间与脚本终态摘要，不参与项目事实、选题、runtime 或恢复判断。
- 实时 prompt、schedule、folder、model、notification policy 和 enabled 状态以 automation 配置为准，只通过 Codex automation 管理能力变更，不编辑 TOML。
- 任务唯一活跃事实是 `开发管理/当前任务队列.txt` 的有序行及同 ID `开发管理/任务卡/<ID>.txt`；交接、摘要和 runtime 只提供证据或诊断信息。

## schema 5 runtime 与 owner 并行

- `tools/hourly-automation-lease.ps1` 的私有 runtime 固定为 `schemaVersion=5` 与 `runs.codex`、`runs.deepseek`，使用 ACL、互斥锁和原子写入。持久状态不再保存集成租约、恢复队列或 provider 凭据。
- 每个 owner 同时最多一个 run；Codex 与 DeepSeek 可拥有不同 taskId 的 run，同一 taskId 不得重复领取。Codex 只领取 `codex_execute/codex/ready`、`codex_review/codex/ready` 和 QueueMaintenance；DeepSeek 只领取 `external_execute/deepseek/ready`。
- 新调用先 `Show`。本 owner run 非空时只返回 taskId、runId、state 和脱敏原因，不恢复、重放、关闭或领取新任务；人工处置规则见 `开发管理/自动工作流恢复规则.txt`。
- schema 4 只有在两个 owner run 都为空且旧集成租约为空时才机械迁移到 schema 5；否则返回 `MIGRATION_REQUIRED`，不得猜测、覆盖或自动迁移旧活动现场。
- run 阶段保留 `developing`、`candidate_ready`、`canonical_ready`、`integrated`、`attention_required`，用于准确记录停止位置，不用于跨自动轮次恢复。

## 共享内核与 owner adapter

- 共享入口唯一实现 runtime `Show`／claim／状态写入、worktree 与 branch 生命周期、candidate 核验、路径冲突检查、最新 `master` 重放、正式提交、组合验证、排他集成、`CompleteRun`、通知和成功清理。
- `tools/hourly-owner-adapter.ps1` 只定义 owner 的 route、candidate 启动脚本、模型／身份和正式结果合同。adapter 不读写 runtime，不含 Git 集成、通知或清理逻辑。
- Codex candidate 通过 `tools/invoke-codex-candidate.ps1` 和 `tools/codex-cli-session.ps1` 启动；必须使用 `codex exec --output-schema` 与 `--output-last-message` 的私有结构化终态，不从自然语言正文猜测状态。
- Codex candidate 正常完成提交后，最终 `changedPaths` 只按 run 的 `baseCommit..HEAD` 执行 `git -c core.quotepath=false diff --name-only --no-renames` 生成并排序去重；文件移动必须同时报告源路径和目标路径，不得用 `git show --name-only`、rename detection 或其他压缩表示替代。共享入口继续按同一口径计算真实集合并要求终态精确相等。
- DeepSeek candidate 通过 `tools/invoke-deepseek-responsibility.ps1` 启动，只接受本机 `http://127.0.0.1:15721` 同源 gateway 和 `deepseek-v4-pro`（当前 API 版本 `DeepSeek-V4-Pro-0813`），身份或模型不符立即停止。
- 每个 run 的项目拥有 worktree 固定为 `.worktrees/automation/<runId>/<owner>`。责任方只能在该 worktree 的 candidate branch 实施、验证并形成一个与 run、base、changed paths 和 candidateResult 精确绑定的提交。

## 冻结自动化输入物化

- schema 1 任务卡可选 `automationInputs`；仅 `codex_execute/codex` 卡可声明。每项只含唯一的 `assets/source/` 仓库相对文件路径、正字节数和 64 位 SHA-256，不接受绝对／反斜杠／通配／`.`／`..`／目录、重复路径或其他字段。
- 已 claim 的 run 创建 linked worktree 后、启动 candidate 前，先用同一次任务卡读取结果核对 claim 时冻结的 `taskCardDigest`、route、owner 与 ready 状态；一致后才从主工作区同路径逐文件核验并复制声明项。源、路径链和目标均不得是 reparse point；源缺失、字节／哈希不符或目标预存统一以 `hourly_task_input_validation_failed` 进入现有 `attention_required`，不启动 candidate、不接受证据、不重试、不切换来源也不递归复制目录。
- 副本完成后重新核验并设为只读。candidate 返回后、接受其证据前，源和 worktree 副本必须再次逐项通过路径、字节和 SHA-256 核验；任务上下文 digest 也包含输入合同。
- 成功清理前按 run 的冻结 base 重新读取输入合同并证明忽略副本仍完全一致，随后才按既有精确身份规则移除 worktree 与临时分支。失败现场继续保留给恢复规则处理；原始素材始终不进入 Git。

## 原子任务与任务内子智能体

- ready 任务应已满足 `开发管理/AI协作规则.txt` 的原子任务条件；共享入口和 PowerShell 脚本不根据文件数、行数、预计时长或模型判断任务大小，也不动态创建、拆分或重排任务卡。
- owner 模型读取已领取任务的直接事实后，在业务写入前做最小原子性检查。确认任务无法原子闭环时，不实施、不生成 candidate，以现有失败终态返回稳定 `detailCode=task_requires_decomposition`；共享入口据此把同一 run 更新为 `attention_required`，后续只按 `开发管理/自动工作流恢复规则.txt` 人工处置。
- 实施中才暴露不可拆合的职责冲突时，owner 模型立即停止叠加补丁，不提交、不集成，保留 owner worktree、最小失败证据和已验证事实后进入 `attention_required`。worker 不边实施边创建零散子卡，也不把半成品机械拆成多个 candidate。
- owner 模型可在执行环境实际暴露能力时，按 `开发管理/AI协作规则.txt` 在同一任务内使用子智能体；子智能体对 schema 5 和共享入口透明，不拥有 run、branch、candidate、任务投影或恢复状态。项目不依赖实验性 agent team。
- 任务内委派仍只能写同一 owner worktree 中互不重叠的授权路径；主智能体统一复核事实源与完整 diff、执行最终验证并创建唯一 candidate。没有子智能体能力时，原子任务由主智能体正常完成。

## 最新 master 重放、验证与正式提交

- candidate 完整核验后，共享入口取得 `tools/hourly-integration-lock.ps1` 的进程持有型排他锁，再读取当时最新 `master`、任务卡、队列、依赖和主工作区相关路径；正式结果只在 owner worktree 中基于该 HEAD 重放并在持锁阶段完成组合验证。
- 自动集成与手动正式集成都必须通过同一个排他锁；手动 fast-forward 使用 `tools/invoke-project-integration.ps1`。锁只串行正式重放、验证和集成，不阻止另一 owner 在独立 worktree 开发。
- Codex 正式结果形成一个路径限定提交。DeepSeek 正式结果形成一个原子提交，同时包含业务变化、原任务 `codex_review/codex/ready` 的 `pending_review` 投影和 `开发管理/AI合作沟通.txt` 的交接证据；DeepSeek 不自审、不解锁依赖，后续由 Codex 独立复审。
- 正式提交继续使用 `tools/automation-finalize-commit.ps1 -RequireAutomationMetadata`。DeepSeek 使用 `AutomationState=pending_review`；Codex 使用 `AutomationState=completed`，表示本轮 Codex 责任方结果已闭环。任务卡实际后置状态由 candidate 的 `expectedTransition` 与 postcondition 表示，不得把 `ready`、`blocked`、`archived` 等任务状态写入 Automation `State`。`Result`、`Impact`、`Verify`、`Plain` 必须由实际证据与验证支持。
- 主工作区必须仍位于取得锁时的 `master`，且正式路径不得与 staged、unstaged 或 untracked 人工改动冲突。冲突、事实变化、验证失败或拒绝 fast-forward 均停止并保留现场，不自动解冲突或重试。

## 决策 checkpoint、失败与清理

- 普通失败、崩溃、残留、冲突或验证失败不得使用恢复路径；共享内核记录准确阶段和原因后停止。新的自动轮次只报告该 run。
- 开发中确需负责人决定时，模型必须停止猜测，形成唯一一个干净 checkpoint 提交和结构化 `decisionResult`，精确绑定 taskId、decisionId、baseCommit、branch、SHA、授权路径与验证证据。
- 共享入口把任务机械转换为 `pending_decision` 或 `waiting_reply` 并正式提交，但不合并 checkpoint 业务变化；关闭当前 run 后发送决策卡。长连接桥只负责接收入站回复。
- 有效回复由 decisionId、taskId、当前任务摘要和操作者身份验证。下一次对应 owner 调用先把原任务恢复为原 route／owner／`ready`，再从最新 `master` 创建新 run、新 worktree和新模型会话，以 `cherry-pick --no-commit` 吸收 checkpoint；不恢复旧模型会话。普通失败不能冒充 decision checkpoint。
- Codex 自动复审不通过或部分通过且需返工时，任务仍按审核合同转为 `blocked` 并移出队列，但不发送普通阻塞结果卡；共享入口改发一次性返工决策卡。A 交回 DeepSeek、B 改由 Codex、C 保持阻塞。该决策只绑定 taskId、被复审提交、复审提交、任务摘要和未通过条目摘要，不含 checkpoint；A/B 在核验回复、任务未被 run 占用且取得同一集成锁后把同一卡重新设为对应 execute route／owner／`ready`，下一轮创建全新 run。C 不改仓库事实。无回复、投递失败或证据变化均不得自动返工、重试或走 checkpoint 恢复。
- QueueMaintenance 本轮移除直接下游卡的最后一个具名前置后，若唯一剩余条件是负责人在两条能够确定性形成完整 ready 卡的路线间选择，必须建立独立维护型 `automationDecision`：选项恰为 A／B／C，A／B 的目标状态为 `ready`，C 为 `blocked`，并关闭自定义回复。它与 `automationCheckpoint` 严格互斥，不含 checkpoint 提交，也不得走 `ResumeReady`。
- 首次维护型决策 run 只形成 `pending_decision` 正式投影，调用 `CompleteRun` 后发送一次飞书决策卡并返回 `decision_requested`；同一 run 不读取、等待或轮询回复。投递未获 provider 接受时保留公开待决策事实，私有记录转 `attention_required`，不得静默进入正常等待或自动重发。
- 后续 Codex RunOnce 仅在 `readyCount=0` 时、普通选择与 claim 前，对最早的维护型决策读取一次回复快照。未回复返回 `waiting_decision`，不 claim、不创建 worktree、不写 Git、不重发；A／B 合法回复才领取新的 `QUEUE-MAINTENANCE` run 并只完成任务卡准备与 `ResolveMaintenanceDecision`，C 在新的维护 run 中机械保持 blocked。实际业务始终由后续 execute run 领取。
- 维护型决策沿用飞书桥的 7 天 TTL。到期、非法回复或精确事实变化不得继续等待：事实仍匹配时通过独立状态 worktree 转为 blocked/expired 或 blocked/attention_required；事实已变化时只终止私有记录。终止结果只报告一次，旧决策不再消费或重发。
- 正常成功在 fast-forward 后写入 `integrated` 并调用 `CompleteRun`。只有 worktree 路径、runId、owner、branch、HEAD、正式 SHA、主分支可达性和工作树清洁全部精确匹配时，才删除该 run 的 worktree 与临时 branch；任一证据异常都不清理。

## 通知与 QueueMaintenance

- 普通 TaskOutcome 使用飞书 REST API 直接出站，不依赖长连接桥健康；投递失败只返回脱敏状态，不回滚业务、不恢复 run、不创建重试队列。长连接桥仅负责入站回复。
- QueueMaintenance 只属于 Codex，按 `开发管理/状态与建议维护规则.txt` 维护队列，不执行本轮新业务。它只对“本轮移除最后一个具名前置”的直接下游卡继续收口，不重新分类其他原本 `blockedBy=[]` 的活跃卡。普通事实变化或回复应用返回 `maintenance_completed`；首次维护型决策返回 `decision_requested`；未回复返回 `waiting_decision`；三者都不伪装成业务 `completed`、不发送普通 TaskOutcome。无变化时返回 `no_candidate`，不得机械重写准确说明来制造维护提交。
- 薄触发器对共享入口的单个 JSON 终态只做语法解析与原样透传，不设置 status 白名单；`no_candidate`、`decision_requested`、`waiting_decision`、带决策字段的 `maintenance_completed` 和维护型 `attention_required` 均是合法终态。触发器不得根据任何终态读取或修改 automation 配置。

## Canary、暂停与停止

- 新入口启用前分别运行 `tools/invoke-hourly-owner.ps1 -Owner codex -Action Canary` 和 `-Owner deepseek -Action Canary`，使用专用私有 runtime 与 canary worktree，核验真实模型／gateway、结构化终态、主工作区隔离和成功清理。
- 代码、runtime 迁移、canary 和实时配置全部核验通过前，两个写入 automation 必须保持暂停。系统性错误时同时暂停，保留 runtime、worktree、candidate 和正式证据。
- 不新增第二 runtime、后台守护、通用重试队列、自动冲突解决、事故专用迁移或长期兼容入口。命中设计停止条件时立即停止，不用兼容分支或额外恢复层绕过。
