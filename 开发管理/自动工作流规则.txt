# 自动工作流规则

本文件只定义两个独立小时入口的稳定边界。业务实施、领域验证、审核与任务维护仍以任务卡和对应专项入口为准。

## 实时入口与事实源

- `codex-hourly-worker` 每小时处理 Codex 自己的 `codex_execute/codex/ready`、`codex_review/codex/ready`、既有 Codex run 和空队列维护；不得启动 DeepSeek。
- `deepseek-hourly-trigger` 是无业务判断的薄触发器，只前台调用 `tools/invoke-deepseek-hourly.ps1 -Action RunOnce` 并原样报告结构化终态；不得读取队列、任务卡或模型正文。
- 固定 Windows 脚本 `tools/invoke-codex-hourly.ps1` 与 `tools/invoke-deepseek-hourly.ps1` 是两个生产业务入口。它们共享有序队列，但各自只选择属于自己的第一项合法任务。
- 任务唯一活跃事实为 `开发管理/当前任务队列.txt` 的有序行及同 ID `开发管理/任务卡/<ID>.txt`。候选选择必须先通过完整任务投影检查，不从交接、backlog 或摘要另建候选池。
- 生产 prompt、schedule、folder、model 和 enabled 状态以实时 automation 配置为准，只由自动化任务之外的普通管理上下文通过 Codex automation 管理能力变更；不得编辑 automation TOML，两个 automation 不得管理彼此或自身。
- 电脑休眠、触发延迟或 automation 服务不可用只形成真实缺跑；不增加 Windows Task Scheduler、后台守护进程、补跑或重试层。

## schema 4 runtime 与 claim

- `tools/hourly-automation-lease.ps1` 的用户级私有 runtime 顶层固定为 `schemaVersion=4`、`runs.codex`、`runs.deepseek` 与 `integrationLease`；使用 ACL、互斥锁和原子写入，不保存 provider 凭据或完整私有地址。
- 每个固定入口先调用统一 `Show`。已有本 owner run 时只处理该 run，不选择第二个任务；无 run 时才确定性选题并调用 `ClaimRun`。
- Codex 与 DeepSeek 可以同时拥有不同 taskId 的 run；同一 taskId 不能同时出现在两个 run。owner 不得领取对方 route。
- Codex 只领取 `codex_execute/codex`、`codex_review/codex`；DeepSeek 只领取 `external_execute/deepseek`。同一 owner 内保持队列原相对顺序并跳过另一 owner 的行。
- QueueMaintenance 只在共享 ready 队列真实为空、Codex run 为空、没有待集成结果且无有效 `integrationLease` 时，以保留 ID `QUEUE-MAINTENANCE` 由 Codex claim。DeepSeek 不得领取维护 run。
- schema 1～3 只有在旧 lease、recovery 和逻辑暂停均为空时才可机械迁移；存在旧活动事实时返回 `MIGRATION_REQUIRED`，不得猜测迁移或覆盖。

## owner worktree 与 candidate

- 每个 run 的项目拥有 worktree 固定为 `.worktrees/automation/<runId>/<owner>`，candidate branch 固定绑定 owner、runId、baseCommit。自动责任方只在该 worktree 实施、验证和提交，不直接修改主工作区。
- Codex candidate 通过 `tools/invoke-codex-candidate.ps1` 启动固定 `codex-cli-session.ps1 -Model`；外层已核验并传入的模型值是子会话身份证明，子会话不因缺少 request metadata 重复阻塞。
- DeepSeek candidate 通过 `tools/invoke-deepseek-responsibility.ps1` 启动，只接受本机 `http://127.0.0.1:15721` 同源 gateway，并显式使用 `deepseek-v4-flash`。身份、provider 或模型不符立即失败。
- 责任方只接收已经 claim 的 taskId、runId、baseCommit、worktree 和 candidate branch；不得重扫队列、claim、管理 runtime、创建其他 worktree/branch、修改主工作区、集成或自审。
- 普通 candidate 的实际 changed paths 必须是任务 `expectedPaths` 的子集。QueueMaintenance 只能修改状态维护规则授权的任务卡、当前队列、分线 backlog、设计／开发建议、当前状态和自动工作流状态事实。
- candidate 必须是 baseCommit 的唯一直接后继、worktree 干净、提交元数据和结构化 `candidateResult` 完整。DeepSeek candidate 不修改共享生命周期或 handoff；这些由固定入口在 canonical 阶段机械重建。
- candidate 不是正式交付，不进入日报、不发通知、不解锁依赖。正常运行不自动删除 owner worktree 或证据 branch。

## canonical 与短时集成

- `candidate_ready` 由固定入口在同一 owner worktree 创建 run 专属 canonical branch，并以当前最新 `master` 为 `canonicalBase` 重放候选。
- 集成前重新核验原任务卡 digest、route、owner、ready 投影、依赖、candidate 证据和最新 `master`。任务事实或相关路径已变化、重放冲突、验证失败或证据不完整时转 `attention_required`，主工作区不变。
- Codex canonical 形成一个路径限定正式提交。DeepSeek canonical 机械恢复最新共享投影，创建连续的 `businessCommit` 与仅含 `开发管理/AI合作沟通.txt` 的 `handoffCommit`；原任务就地转换为 `codex_review/codex/ready`，不新建复审卡、不解锁依赖。
- 只有 canonical 全部通过后才申请最长 300 秒的 `integrationLease`。租约只保护主工作区最终复核与一次 `git merge --ff-only <canonicalHead>`，不覆盖开发或长时间验证。
- 集成时 `master` 必须仍等于 `canonicalBase`，主工作区不得在正式 changed paths 上存在 staged、unstaged 或 untracked 冲突。无关人工改动不暂存、不提交、不清理。
- 若另一个 owner 先推进 `master`，且当前 canonical worktree 可核验且干净，则本 run 回到 `candidate_ready`，下一轮只在新 HEAD 上重建 canonical；文本／事实冲突进入 `attention_required`，不自动解冲突。
- fast-forward 后先把 run 标为 `integrated`，再用单个原子 `CompleteRun` 记录结果、清除本 owner run 并释放同一 `integrationLease`。`integrated` 恢复只关闭记录，不重复提交或通知。

## 提交、复审与通知

- 正式 automation 提交继续使用 `tools/automation-finalize-commit.ps1 -RequireAutomationMetadata` 的九字段合同：`AutomationTask`、`AutomationState`、`AutomationResult`、`AutomationImpact`、`AutomationVerify`、`AutomationPlain`。
- Codex candidate 使用 `AutomationState=completed`，只表示本责任方提交闭环；实际任务状态仍由任务卡／归档投影证明。DeepSeek 正式业务提交使用 `AutomationState=pending_review`；handoff 提交不带 Automation 标记。
- `Result`、`Impact`、`Verify`、`Plain` 分别使用 `问题/完成`、`影响/边界`、`验证/后续`、`发生/影响/需要` 的单行结构。九个子字段均非空并由事实和实际验证支持；通俗子字段各不超过 200 个 Unicode code point。
- 非 QueueMaintenance 的成功 `CompleteRun` 后发送一次 `tools/send-feishu-notification.ps1 -Kind TaskOutcome`：DeepSeek 发送已核验 `businessCommit` 的 `pending_review`；Codex 按实际任务转换发送 `completed`、`blocked`、`waiting_decision`、`waiting_reply` 或 `failed`。通知失败只返回脱敏投递状态，不回滚提交、不恢复 run、不重试业务。
- DeepSeek 不得复审自己的结果。Codex 复审读取 `master` 实际组合与审核证据，不用旧 candidate 代替。

## QueueMaintenance 与恢复

- QueueMaintenance 按 `开发管理/状态与建议维护规则.txt` 只提升或建立当前可安全形成的 ready 卡并排序；本轮不执行新业务任务。零候选且无事实变化时以 `no_candidate` 关闭，不制造提交、recovery 或阻塞计数。
- run 状态只使用 `developing`、`candidate_ready`、`canonical_ready`、`integrated`、`attention_required`。恢复细则见 `开发管理/自动工作流恢复规则.txt`。
- 明确 blocker 必须由责任方通过合法任务生命周期提交写回任务卡和队列投影。进程、session、worktree、branch、提交或 runtime 证据不一致时保留现场并进入 `attention_required`，不得用兼容分支、重试层、stash、reset、checkout、clean 或自动删除掩盖。

## Canary、暂停与回滚

- 新生产入口启用前必须运行 `tools/invoke-deepseek-hourly.ps1 -Action Canary`，使用专用私有状态和 canary worktree，证明 Windows PowerShell 7、Git、项目检查、真实 DeepSeek gateway／模型、owner worktree 与主工作区隔离。canary 不读取生产队列、不 claim 生产任务、不修改 `master`。
- 系统性错误时通过实时 automation 管理能力同时暂停 `codex-hourly-worker` 与 `deepseek-hourly-trigger`，保留 runtime、worktree、candidate 和 canonical 证据。
- 只有 `integrationLease=null`、没有 `integrated` 未关闭 run、主工作区已核验且旧 runtime 无活动事实时才允许回滚或重新启用；不得长期保留新旧双 runtime、旧通用 external wrapper 生产路径或第二套调度机制。
