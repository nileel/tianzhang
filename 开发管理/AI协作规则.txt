# AI协作规则

当本项目同时使用 Codex（小时自动化实际模型为 GPT-5.6 Terra）与 DeepSeek V4.1 Flash 时，按本文件分工。用户当次明确指令优先，但不得违反 `AGENTS.md`。

## 总原则

- 设定与设计内容以 `docs/` 原文为准；进度与阶段判断以 `开发管理/` 为准；数值结论以 `simulations/BattleSim` 实际运行结果为准；Unity 实现以 `src/` 当前代码为准。
- 纯 `1` / `2` 都先读 `开发管理/当前任务队列.txt`；选中 ID 后以 `开发管理/任务卡/<ID>.txt` 为活跃任务唯一事实，纯 `2` 再读 `开发管理/审核入口.txt` 和对应证据。
- `当前任务队列.txt` 只保存有序 ready 投影；`设计-当前状态.txt` 只放已验证事实和当前风险；分线 backlog 与建议索引的维护细则见 `开发管理/状态与建议维护规则.txt`。
- 任务卡的 `必读` / `必查范围` 统一按 `开发管理/状态与建议维护规则.txt` 解释：先定位相关章节、符号、实体或用途，再读取当前步骤需要的原文；路径级条目不默认等于整份加载，修改前仍读取目标完整逻辑单元。
- 交接材料只记录当前线索、疑点和待判断项，不能替代 docs、管理文件、BattleSim、Unity 代码或 git diff。
- 普通定时调度先读 `开发管理/自动工作流规则.txt`。`codex-hourly-worker` 与 `deepseek-hourly-trigger` 是两个独立 automation，互不启动、暂停、恢复或管理对方。
- 固定入口 `Show` 返回本 owner run 时只按 run state 读取 `开发管理/自动工作流恢复规则.txt`；无本 owner run 时才按共享队列选择新任务。

## 任务原子性与子智能体

### 临近执行时检查，确认过大后一次拆完

- 不对整个 backlog 做前置分析。只有当前任务即将从 backlog 提升为 ready，或已被选中且尚未开始业务写入时，才读取该卡与直接依赖、预期路径、停止条件和验收入口，做最小原子性检查。
- 一张执行卡必须只有一个可独立判断的结果，所有者、允许路径、事实源、停止条件和验证已经冻结，并能由一个主智能体统一复核全部差异、最终验证和单一 candidate。跨文件数量和表面难度不是单独拆分依据。
- 当前父项一旦确认无法原子闭环，Codex 规划责任方在一次独立规划中读取完成拆分所需的直接事实，一次性建立全部已知子任务卡、依赖图、首批 ready 叶子和父项关闭条件；其余子项保持 blocked。父项随后只保留汇总状态，不再作为执行卡被领取，也不得在后续轮次逐张补拆。
- 完整拆分只处理当前父项，不顺带分析其他 backlog 项。若边界未知，有限只读调查属于同一次拆分过程；只有缺少用户或外部系统的不可推导决策时才建立 decision checkpoint。
- 固定小时 worker 不动态修改任务拓扑。写入前发现已领取任务不原子时，不实施、不生成 candidate，使用现有 `attention_required` 并记录 `task_requires_decomposition`；由普通 Codex 规划上下文一次性完成拆分。写入后才发现时立即停止，不提交、不集成，保留 owner worktree、最小失败证据和已验证事实供人工处置。
- 手动 DeepSeek / Claude 发现当前任务不原子时只报告 `task_requires_decomposition` 并请求 Codex 规划，不修改任务卡、backlog 或队列。手动 Codex 执行完整拆分时只修改当前父项及其子卡、直接依赖和 ready 投影；任何管理写入仍遵守 worktree、路径冲突与排他集成规则。

### 同一任务内的辅助委派

- 主智能体可在执行环境实际暴露能力时，把互不依赖的调查、验证、只读审查或互不重叠的机械修改交给子智能体；小任务、强耦合修改、共享可变状态、频繁同步或重叠逻辑单元由主智能体直接完成。
- 主智能体先读取任务卡并冻结事实源、范围、停止条件和验收口径，再派发具体、有界、可独立返回的子任务。子智能体默认只读；允许写入时必须分配互不重叠的字面量路径，同一路径只能有一个写入所有者。
- 子智能体不得另领 taskId、改变 route / owner / dispatchState、修改任务卡和队列、提交、合并、推送、操作 runtime 或集成锁，也不得继续派生子智能体。子智能体结果只是证据或候选差异，不替代主智能体对事实源、完整 diff、最终验证和残留风险的复核。
- 无论使用多少子智能体，手动或自动执行对外仍只有一个主责、一个任务 worktree、一个最终提交；自动执行仍只有一个 owner run 和一个 candidate。没有子智能体能力时，原子任务由单智能体正常执行，不伪造并行，也不因此扩大任务范围。

### 任务卡中的模型协作提示

- 2026-09-20 用户要求后续所有任务按复杂度选择模型组合。建卡方必须在正文写明“模型协作”；在任务即将 ready、人工重新准备 ready 或选中执行／复审时，依据该卡与直接事实评估当轮复杂度和模型组合。尚未具备执行事实的 blocked 卡可先注明待临近 ready 评估，不猜测结论、不预分析整个 backlog、不批量补写历史卡，也不新增任务 schema 或自动化状态。
- 复杂度依据目标和语义是否明确、跨所有者依赖、已有失败或证据冲突、错误影响及验收难度判断；文件数量或预计时长不能单独定级。简单且验收明确的任务沿用入口默认单模型；复杂根因诊断存在独立只读工作面时，选择 `gpt-5.6-sol / high` 辅助；关键证据冲突、高风险语义或停止条件判断需要独立分析时，选择 `gpt-6-astra / high` 辅助。卡中写明具体理由、辅助问题、只读范围、预期证据和调用触发条件；确无独立工作面时由主责统一处理，并写明理由。
- 执行者必须在业务写入前核对卡中方案与实际能力；执行／复审阶段变化或新事实改变复杂度时重新判断，但不得越过原范围和停止条件。旧卡缺少本段不免除评估，也不因此单独阻塞：当轮结论先记入既有验证记录或结构化验证结果，由后续有权建卡／维护的一方补齐；不得为记录组合擅改已 claim 的任务摘要，DeepSeek candidate 仍不得修改任务卡。
- 主模型仍由入口启动参数决定；提示词不能更换已运行的主模型。辅助模型及推理强度必须以当前原生子智能体工具实际支持为准；只调用能解决当前具体问题的组合，不逐级调用所有模型，不因本条增加无用审查。任务需要更换主模型而现有能力无法满足验收时，如实记录该需求并按原停止合同处理，不能声称已经自行切换。
- 本节授权的跨模型辅助只读；继续遵守上节的同一 taskId、owner run、worktree、主责复核和唯一 candidate 合同。子智能体不得改卡、改队列、提交、操作 runtime/锁或继续派生；不通过 shell 启动第二责任会话，不修改 automation/用户配置来绕过工具缺失。需要写入委派时仍须有互不重叠字面量路径的单独授权，不能由本节推导。
- 记录触发原因、请求的模型/强度、工具返回的会话标识与实际可核实结果；工具未证实的模型或强度标为未核实，不能把提示词中的模型名当调用证明。自动终态 `model` 始终填写入口主模型，辅助调用只记入本任务既有验证记录，不添加控制面字段。
- 工具不支持模型覆盖、目标模型不可用或额度不足时，记录“未执行该模型辅助”，不反复换端点/重启。辅助调用不是新增前置：主责仍能满足原验收则继续；缺少必要能力/证据或越过原停止条件则按既有合同停止。模型意见不能代替缺失的运行时数据、实机画面或用户批准；不能仅写一条限制说明就把未满足的完成条件改算通过。
- 更强辅助模型不改变 owner、route、领域授权或审核独立性；DeepSeek/Claude 调用辅助模型仍不构成 Codex 正式复审，原执行者不得自审。

## 主责

### Codex / GPT-5.6 Terra

- 未决需求、跨事实源产品语义、公共接口和数据所有者的最终裁决；仍有不可逆歧义时交负责人决定，不由模型猜测。
- 当前任务的原子性判断与一次性完整拆分、优先级、授权路径、风险与回滚边界、验收条件，以及 BattleSim→Unity 同步策略。
- 开放式美术方向、交互产品语义、最终视觉/体验验收和用户批准；运行时可见证据必须由实际工具取得。已冻结规格的UI/场景实现与客观截图缺陷诊断可由DeepSeek承担，Codex独立签收。
- DeepSeek 技术候选的独立复审、集成控制、冲突裁决和高风险结果签收。

### DeepSeek V4.1 Flash

- 按规范批量生产内容；每项完成品单独成文件。
- 文档清洗、CSV / Language / asset 对齐、机械一致性检查。
- 输出以文本、代码或数据为主且可由 diff、build、test、BattleSim 或确定性检查闭环的 Unity / BattleSim / 工具实现、bug fix、重构与迁移；不按规模、跨文件数量或表面难度限制。
- 已冻结视觉规格、所有者和验收矩阵的UI/场景代码、序列化接线、既有资源导入与布局修复；支持原生图像输入后，可分析真实截图中的遮挡、截断、层级、对齐和引用缺陷。执行前必须证明本机CLI/网关/模型能读取实际图片，并具备目标Unity/浏览器工具；缺工具不能以文字猜图通过。
- 可提出代码、数据、UI映射与问题根因候选；没有产品语义裁决、最终美术批准、内容解冻或费用授权职责，也不得自审。
- 跨文件、跨模块 Code Agent 根因诊断与实施、技术方案候选、全链回归、边界用例、批量迁移和素材规模扩展。
- 在 Codex 已冻结 schema、回滚边界和验收矩阵后，执行存档、安全或自动化控制面中的明确实现切片；完成后必须交 Codex 独立复审。

### 能力校准后的分派边界

- 2026-09-20核验：DeepSeek默认工作模型改为DeepSeek V4.1 Flash，API准确ID为 deepseek-flash；官方9月10日更新记录确认原生多模态与代码/Agent能力增强。官方同名Terminal-Bench 2.1公布90.6（V4 Pro 0813为87.9）、NL2Repo公布65.4（此前61.5）。这些是厂商公开评测，不是本项目复现，也不推导所有任务全面优胜。
- 官方发布新闻曾说旧Pro会自动路由，更新日志后来明确继续提供Pro服务；本项目显式请求 deepseek-flash，不依赖旧别名。来源与本机验证记录见 开发管理/DeepSeek-V4.1-Flash迁移验证记录.txt，API现行事实以 https://api-docs.deepseek.com/updates/ 为准。
- 输出主要是文本、代码、数据，或已冻结视觉规格且能由真实截图/布局断言与运行时操作闭环时，默认 external_execute / deepseek。复杂诊断、跨模块规模、图片输入本身不再是自动改派Codex的理由；执行仍以完整路径、所有者、停止条件、工具能力与验收为前提。
- 开放式产品/美术语义、最终体验判断、任务编排、正式集成和独立复审由Codex主责；同一任务可以让DeepSeek提供技术/视觉问题候选，但不改变责任边界。已存在的owner/route不因模型升级批量重派；在新建或重新ready时按本段冻结职责。
- 核心架构、公共接口、存档、安全和自动化控制面的明确实现切片可由DeepSeek执行，Codex先冻结所有者/schema/回滚与验收并独立签收。要求改变已锁定语义或扩大范围时停止交回，不加兼容分支。
- 图像能力分三层核验：官方模型支持、当前CLI/网关实际图像请求、目标场景真实工具取证。文本canary通过只证明文本/工具链；任一图片/场景证据缺失均不得宣称完成视觉验收。模型升级不修改automation时刻、通知、enabled状态或owner runtime。

### Claude CLI / WF3-CLAUDE-ONE

WF3 定时器暂停；未来人工恢复或用户明确调用时，Claude CLI 仅有 DeepSeek / Claude 执行范围，不是 Codex 主责角色：

1. 先读取当前进程的 `ANTHROPIC_BASE_URL`；为空时只补读 `~/.claude/settings.json` 的同名字段。`http://127.0.0.1:15721` 同源地址（含 `/claude-desktop` 路径）的实际身份与修改方统一为 `DeepSeek V4.1 Flash`，不得自称 Codex 或 Claude。
2. 其他 Claude CLI 环境的实际身份与修改方为 Claude Code。
3. 普通选题只消费 `route=external_execute`、`dispatchState=ready` 且 owner 与执行器一致的有序队列卡；映射固定为 `owner=deepseek -> DeepSeek V4.1 Flash`、`owner=claude -> native Claude Code`。原生 Claude Code 读取 `开发管理/DeepSeek工作提示词.txt` 时，只继承任务路由、边界和交接格式。
4. `owner=codex`、`route=codex_review`、非 ready 或未明确授权的任务不可执行。用户当次明确指派原生 Claude Code 的具体手动任务仍可执行，但该例外不得改变自动 wrapper 行为。
5. 手动选题前在输出与 automation memory 记录实际身份、修改方及候选任务 ID / route / owner / dispatchState；无合格候选则记录 `skipped_cleanly` 后退出，不改项目文件或创建替代任务。

### 两个独立小时责任链

- `codex-hourly-worker` 与 `deepseek-hourly-trigger` 分别前台调用 `tools/invoke-hourly-owner.ps1 -Owner codex|deepseek` 并原样报告结构化终态；两者保留独立定时器，但不复制编排实现。
- 共享入口统一负责 `Show`、确定性选题、原子 claim、`.worktrees/automation/<runId>/<owner>`、candidate 核验、最新 `master` 重放、组合验证、排他集成、关闭、通知与成功清理。adapter 只保留 route、模型启动、身份和 candidate 合同差异。
- DeepSeek 只接收已经领取的 taskId、runId、baseCommit、candidate branch 和 worktree。它只在 owner worktree 实施、直接验证并创建一个 candidate，不修改共享任务投影或 handoff，不集成、不自审、不管理 runtime 或 automation。
- 共享入口核验 DeepSeek candidate 后，在最新 `master` 上形成一个原子正式提交，同时包含业务变化、`codex_review/codex/ready` 的 pending review 投影和 `AI合作沟通.txt` 交接证据；审核前不解锁依赖。
- Codex 与 DeepSeek 可以并行开发不同 taskId；自动与手动正式集成统一由进程持有型排他锁串行化。任务事实、最新 `master`、相关人工改动或证据变化阻止集成，不自动解冲突或叠加重试。
- 共享 `当前任务队列.txt`、分线 backlog 或审核清单不构成全局串行理由。真实业务前置与同批固定顺序必须在任务进入 ready 前落实，避免可预见的共享管理投影并发；没有真实依赖的不同 taskId 仍可并行开发。若最新 `master` 只改了同一共享文件中的无关条目，现有整路径证据仍不足以自动合并，当前 run 继续按路径冲突停止，由普通管理上下文取证；不得删减 `expectedPaths`、恢复旧模型会话或绕过人工 dirty 与集成锁保护。
- owner 模型可按本文件在同一已领取任务内部使用子智能体，但子智能体对 schema 5、共享入口和候选合同透明；所有工作必须收敛到同一 owner worktree、同一主智能体最终验证和单一 candidate。
- run 的 `developing`、`candidate_ready`、`canonical_ready`、`integrated` 与 `attention_required` 只保留诊断阶段；本 owner run 非空时新的小时轮次只报告，不自动恢复、重放、关闭或领取新任务。只有精确绑定且已有有效回复的 decision checkpoint 可由新 run、新 worktree 和新模型会话受控继续。

## 验证成本控制（适用于所有工作）

1. 默认使用与风险、改动范围和失败后果相称的最小充分验证集，只运行能直接证明本轮产物正确的检查；普通文档、局部规则或小范围实现不默认运行全项目回归，也不默认安排规格复审与质量复审各一轮。
2. 在任务选定时一次性列出必需验证，完成修改后尽量合并执行一次。若相关代码、事实源、配置、依赖、Git 基线和实际执行目标均未变化，已通过的同范围检查不得因流程阶段切换而重复运行。
3. 合并、切换实际执行目标或更新外部配置后，只对受影响边界做一次针对性复验；不得把“重新确认”扩大为无关的全套测试。检查失败时先定位失败层，只重跑修复所影响的检查和最终必要门禁。
4. 只有以下情形才升级为全量回归、独立复审或多阶段验证：共享基础设施与自动化控制面；安全、权限、写入隔离与恢复；不可逆删除或迁移；核心架构、公共接口、数据语义与数值平衡；DeepSeek/外部交接的正式复审；事实源冲突、已有失败证据；用户明确要求。升级时也应合并检查、避免对未变化范围重复取证。
5. 最小验证不得跳过领域硬约束：数值平衡仍运行 BattleSim，Unity/C# 仍运行任务直接涉及的 build/test，审核路由仍按审核规则执行，提交前的路径隔离、行尾空白与 Git 差异检查仍保留。

## 交接

1. 派工时明确主责、任务类型、允许修改范围、必读事实源和验证命令；外部责任方只接受有序队列已选中的 `external_execute` 同一任务卡。
2. DeepSeek 的修改只能标「⚠️ 已修改/未审核」，不得预填审核方结论；自动外部执行由共享入口把业务变化、pending review 投影和 handoff 证据收敛为一个原子正式提交。
3. 需要审核或判断时，DeepSeek 在 `AI合作沟通.txt` 写入短 ID、方向、任务/提交范围、修改文件、已验证、未验证、残留风险、请求判断和建议下一步。
4. Codex 消费交接时先读审核入口和匹配条目，再以 diff、事实源和可重复命令独立验证。
5. 长期阻塞项进入未通过清单或 backlog。Codex 复审通过后，把 `AI合作沟通.txt` 中同一 taskId 已消费的全部交接轮次原文迁入 `AI合作归档/<TaskId>-交接归档.txt`；返工时只迁已被新证据替代的轮次，保留当前返工证据。没有匹配交接时不创建空归档，且不得改动其他任务条目。

## 快捷工作流：`1` / `2`

当用户消息去除首尾空白后严格等于 `1` 时，按有序队列推进一个当前 AI 可执行的执行型任务，不做复审。当消息严格等于 `2` 时，Codex / GPT-5.6 Terra 按有序队列推进一个复审任务；DeepSeek 只可补齐交接材料，不得自审。其他消息按用户明确要求执行。

### 通用步骤

1. 先确认身份：Codex 通过 Node REPL 读取 `nodeRepl.requestMeta['x-codex-turn-metadata'].model`；每小时共享入口经 `tools/codex-cli-session.ps1` 启动的 Codex 责任方使用 adapter 以 `-Model` 和首条 stdin 输入传递的核验结果，不因 `codex exec` 不继承 request metadata 而重复阻塞；DeepSeek 按 `开发管理/DeepSeek工作提示词.txt` 的身份锚定；WF3-CLAUDE-ONE 还执行本文件的身份与授权自检。
2. 纯 `1` / `2` 先读取 `AGENTS.md` 与 `开发管理/当前任务队列.txt`；选中行后读取同一 ID 的 `开发管理/任务卡/<ID>.txt`。纯 `2` 再按审核入口加载该项需要的未通过条目、交接证据和目标 diff；DeepSeek 还读其工作提示词。
3. 检查 `git status --short`；存在无关改动时只处理本轮相关文件，绝不 stage 无关改动。
4. 纯 `1` 从队首向后选择当前 AI 可执行的第一项 `codex_execute` 或 `external_execute`；不消费 `codex_review`。
5. 手动 Codex / DeepSeek / Claude 纯 `1` 选中 ready 任务后，先按“任务原子性与子智能体”做只读最小检查。不原子时不得开始业务实施：DeepSeek / Claude 停止并请求 Codex 规划；Codex 若在本次独立规划中完整拆分，必须先创建专用 `.worktrees/` 任务分支，只提交当前父项、全部子卡、直接依赖和 ready 投影。确认原子后、任何项目写入前，同样必须在 `.worktrees/` 创建任务分支 worktree，并只在该 worktree 内实施、验证和创建角色要求的路径限定提交。合并前从主工作区重新调用 schema 5 `Show` 并重读同一任务卡与队列；只有两个活动 run 都不占用同一 taskId、集成锁空闲、任务仍为原 route / owner / `dispatchState=ready`、队列投影未改变，且待合并路径不与主工作区 staged、unstaged、untracked 改动冲突时，才通过 `tools/invoke-project-integration.ps1` 持有同一锁执行 fast-forward。固定小时入口只在 `.worktrees/automation/<runId>/<owner>` 实施，并由共享脚本持有同一锁重放、验证和集成。
6. 纯 `2` 从队首向后选择第一项 `codex_review`；DeepSeek / Claude 不得自审。
7. 路径冲突或执行器暂不可用时可在本轮继续检查下一行，但不修改顺序；明确逻辑阻塞必须先转状态并移出队列。
8. 队列为空时才读取分线 backlog 进行一次维护，本轮不执行新任务。
9. 选定真实对象后、读取实施细则前，调用 `tools.codex_app__set_thread_title`：`1` 为 `TZG｜<中文简述>`，`2` 为 `TZG｜复审：<中文简述>`。简述使用任务卡或复审事实源的中文标题；无候选或改名失败不阻断流程。
10. 命中审核、未审核、交接或复审路由时，按审核入口读取细则与相应事实源；普通执行任务按任务卡必查范围先定位、后读取，发现新依赖时补读，修改前读取目标完整逻辑单元。不得处理另一个 AI 主责的高风险任务，应写入交接请求。
11. 完成后按“验证成本控制”选择最小充分验证集并合并执行一次，只提交本轮文件；完成队列任务时同步更新同一任务卡、backlog 和 `当前任务队列.txt`。固定小时入口的 candidate／正式提交统一遵守 `tools/automation-finalize-commit.ps1 -RequireAutomationMetadata` 的九字段合同；`AutomationState=completed` 只表示 Codex 责任方提交闭环，DeepSeek 正式业务提交使用 `pending_review`。`Result`、`Impact`、`Verify`、`Plain` 分别使用 `问题/完成`、`影响/边界`、`验证/后续`、`发生/影响/需要` 的单行结构，并由实际事实与验证支持。QueueMaintenance 以全局 `readyCount` 证明结果；零候选且无变化时不制造提交。

### 角色例外

- Codex / GPT-5.6 Terra 的 `1` 按队列顺序处理其主责执行型任务，不消费 `codex_review`；其自产工作完成必要验证后可闭环。
- Codex / GPT-5.6 Terra 的 `2` 按队列顺序处理第一项 `codex_review`；通过后按审核规则关闭，未通过则更新未通过清单。
- DeepSeek 的 `1` 只做其主责执行型任务；所有修改标为未审核，自动外部执行由共享入口把业务变化、pending review 投影和交接证据收敛为一个原子正式提交，手动执行遵守当前任务卡与交接合同。
- DeepSeek 的 `2` 不得复审自己；仅补齐交接材料、验证输出和请求复审范围。

## 冲突处理

用户当次明确指令 > `AGENTS.md` > `开发管理/` 当前状态 > `docs/` 原文 > BattleSim / Unity 实际代码。数值平衡结论必须有 BattleSim 运行结果；发现 docs、BattleSim、Unity 不一致时，先指出冲突并确定主事实源，再同步相关文件。
