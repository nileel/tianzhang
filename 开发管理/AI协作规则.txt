# AI协作规则

当本项目同时使用 Codex / ChatGPT5.5 与 DeepSeek V4 Pro 时，按本文件分工。用户当次明确指令优先，但不得违反 `AGENTS.md`。

## 总原则

- 设定与设计内容以 `docs/` 原文为准；进度与阶段判断以 `开发管理/` 为准；数值结论以 `simulations/BattleSim` 实际运行结果为准；Unity 实现以 `src/` 当前代码为准。
- 纯 `1` / `2` 都先读 `开发管理/当前任务队列.txt`；选中 ID 后以 `开发管理/任务卡/<ID>.txt` 为活跃任务唯一事实，纯 `2` 再读 `开发管理/审核入口.txt` 和对应证据。
- `当前任务队列.txt` 只保存有序 ready 投影；`设计-当前状态.txt` 只放已验证事实和当前风险；分线 backlog 与建议索引的维护细则见 `开发管理/状态与建议维护规则.txt`。
- 任务卡的 `必读` / `必查范围` 统一按 `开发管理/状态与建议维护规则.txt` 解释：先定位相关章节、符号、实体或用途，再读取当前步骤需要的原文；路径级条目不默认等于整份加载，修改前仍读取目标完整逻辑单元。
- 交接材料只记录当前线索、疑点和待判断项，不能替代 docs、管理文件、BattleSim、Unity 代码或 git diff。
- 普通定时调度先读 `开发管理/自动工作流规则.txt`；只有自动化 `Show` 返回非空 recovery 时才追加读取 `开发管理/自动工作流恢复规则.txt` 的 decision / interruption 恢复细则。

## 主责

### Codex / ChatGPT5.5

- 跨文档系统设计、架构判断和代码评审。
- BattleSim 数值评估、矩阵和结论可靠性判断。
- 阶段规划、优先级、风险与 BattleSim→Unity 同步策略。
- 总结及复杂 Unity 方案。

### DeepSeek V4 Pro

- 按规范批量生产内容；每项完成品单独成文件。
- 文档清洗、CSV / Language / asset 对齐、机械一致性检查。
- 已明确设计的局部 Unity / BattleSim 实现、bug fix、UI 文案和导入字段补齐。
- 回归清单、边界用例和素材规模扩展。

### Claude CLI / WF3-CLAUDE-ONE

WF3 定时器暂停；未来人工恢复或用户明确调用时，Claude CLI 仅有 DeepSeek / Claude 执行范围，不是 Codex 主责角色：

1. 先读取当前进程的 `ANTHROPIC_BASE_URL`；为空时只补读 `~/.claude/settings.json` 的同名字段。`http://127.0.0.1:15721` 同源地址（含 `/claude-desktop` 路径）的实际身份与修改方统一为 `DeepSeek V4 Pro`，不得自称 Codex 或 Claude。
2. 其他 Claude CLI 环境的实际身份与修改方为 Claude Code。
3. 仅可领取“待处理、非复审、主责明确为 DeepSeek V4 Pro、Claude Code 或 Claude / DeepSeek”的任务。原生 Claude Code 读取 `开发管理/DeepSeek工作提示词.txt` 时，只继承任务路由、边界和交接格式。
4. Codex、ChatGPT5.5、Codex / gpt-5.5 或未明确授权给 DeepSeek/Claude 的任务不可领取，除非用户当次明确指派 Claude Code 的具体任务。
5. 选题前在输出与 automation memory 记录实际身份、修改方、允许主责及候选任务 ID / 主责 / 状态；无合格候选则记录 `skipped_cleanly` 后退出，不改项目文件或创建替代任务。

### 每小时控制器内的 Claude / DeepSeek wrapper

`tzg-hourly-controller` 可以在同一租约内串行调用 Claude CLI 作为 DeepSeek / Claude 执行器，但这不会恢复 WF3，也不会赋予子进程 Codex 权限。wrapper 沿用上节主责限制：只可处理状态为待处理、非复审，且主责明确为 `DeepSeek V4 Pro`、`Claude Code` 或 `Claude / DeepSeek` 的候选；不得领取 Codex、ChatGPT5.5、Codex / gpt-5.5 或未明确授权任务。

调度器必须先真实选中合法外部候选、取得单写入租约并给出任务授权范围，才预检 Claude CLI、`ANTHROPIC_BASE_URL` 和代理身份；无合法外部候选时不得预检或空转调用。外部责任方启动后自行读取任务卡与必要事实源，并端到端完成：

1. 调用 `tools/automation-workspace-guard.ps1` 记录基线，确认授权范围与人工改动不冲突。
2. 实施修改、运行任务直接要求的最小充分验证并标记「⚠️ 已修改/未审核」；成功后把同一任务卡更新为 `route=codex_review`、`owner=codex`、`dispatchState=ready`，在原队列行就地同步且保持同一 ID、标题和正文，不创建第二张复审卡。
3. 使用 `tools/automation-finalize-commit.ps1` 和路径限定的 expected paths 创建 `businessCommit`；提交只含业务、上述同一任务卡/队列状态和直接验证结果，保持 `State: pending_review`。由 `tzg-hourly-controller` 派发时启用 `RequireAutomationMetadata`，`CommitMessage` 只传单行标题，并以 `AutomationTask`、`AutomationState=pending_review`、`AutomationResult`、`AutomationImpact`、`AutomationVerify` 分别传入事实字段；finalizer 固定生成 `Automation: tzg-hourly-controller` 正文。
4. 随后只修改 `开发管理/AI合作沟通.txt`，登记真实 `businessCommit` SHA、已验证、未验证和残留风险，再以同一 finalizer 创建只含交接文件的 `handoffCommit`；第二次不得重跑领域检查。`handoffCommit 不使用 Automation 标记`，也不启用元数据门禁。

外层 Codex只接收 `completed`、`needs_decision`、`blocked` 或 `failed`，以及两个 SHA 或恢复 session；不得读取业务 diff、重跑业务验证、stage 或 commit。外部责任方不得自审、扩大授权路径、并行派发、stash、reset、checkout、clean 或推送远端。需要负责人决定时，外部 CLI 保存原 session 后退出，并由原 session 续跑。

## 验证成本控制（适用于所有工作）

1. 默认使用与风险、改动范围和失败后果相称的最小充分验证集，只运行能直接证明本轮产物正确的检查；普通文档、局部规则或小范围实现不默认运行全项目回归，也不默认安排规格复审与质量复审各一轮。
2. 在任务选定时一次性列出必需验证，完成修改后尽量合并执行一次。若相关代码、事实源、配置、依赖、Git 基线和实际执行目标均未变化，已通过的同范围检查不得因流程阶段切换而重复运行。
3. 合并、切换实际执行目标或更新外部配置后，只对受影响边界做一次针对性复验；不得把“重新确认”扩大为无关的全套测试。检查失败时先定位失败层，只重跑修复所影响的检查和最终必要门禁。
4. 只有以下情形才升级为全量回归、独立复审或多阶段验证：共享基础设施与自动化控制面；安全、权限、写入隔离与恢复；不可逆删除或迁移；核心架构、公共接口、数据语义与数值平衡；DeepSeek/外部交接的正式复审；事实源冲突、已有失败证据；用户明确要求。升级时也应合并检查、避免对未变化范围重复取证。
5. 最小验证不得跳过领域硬约束：数值平衡仍运行 BattleSim，Unity/C# 仍运行任务直接涉及的 build/test，审核路由仍按审核规则执行，提交前的路径隔离、行尾空白与 Git 差异检查仍保留。

## 交接

1. 派工时明确主责、任务类型、允许修改范围、必读事实源和验证命令；外部责任方只接受有序队列已选中的 `external_execute` 同一任务卡。
2. DeepSeek 的修改只能标「⚠️ 已修改/未审核」，不得预填审核方结论；外部执行任务按本文件的 `businessCommit` + `handoffCommit` 边界自行创建本地提交。
3. 需要审核或判断时，DeepSeek 在 `AI合作沟通.txt` 写入短 ID、方向、任务/提交范围、修改文件、已验证、未验证、残留风险、请求判断和建议下一步。
4. Codex 消费交接时先读审核入口和匹配条目，再以 diff、事实源和可重复命令独立验证。
5. 长期阻塞项进入未通过清单或 backlog；已处理且无后续价值的交接条目移入归档。

## 快捷工作流：`1` / `2`

当用户消息去除首尾空白后严格等于 `1` 时，按有序队列推进一个当前 AI 可执行的执行型任务，不做复审。当消息严格等于 `2` 时，Codex / ChatGPT5.5 按有序队列推进一个复审任务；DeepSeek 只可补齐交接材料，不得自审。其他消息按用户明确要求执行。

### 通用步骤

1. 先确认身份：Codex / ChatGPT5.5 通过 Node REPL 读取 `nodeRepl.requestMeta['x-codex-turn-metadata'].model`；每小时控制器经 `tools/codex-cli-session.ps1` 启动的 Codex 责任方使用控制器以 `-Model` 和首条 stdin 输入传递的核验结果，不因 `codex exec` 不继承 request metadata 而重复阻塞；DeepSeek 按 `开发管理/DeepSeek工作提示词.txt` 的身份锚定；WF3-CLAUDE-ONE 还执行本文件的身份与授权自检。
2. 纯 `1` / `2` 先读取 `AGENTS.md` 与 `开发管理/当前任务队列.txt`；选中行后读取同一 ID 的 `开发管理/任务卡/<ID>.txt`。纯 `2` 再按审核入口加载该项需要的未通过条目、交接证据和目标 diff；DeepSeek 还读其工作提示词。
3. 检查 `git status --short`；存在无关改动时只处理本轮相关文件，绝不 stage 无关改动。
4. 纯 `1` 从队首向后选择当前 AI 可执行的第一项 `codex_execute` 或 `external_execute`；不消费 `codex_review`。
5. 纯 `2` 从队首向后选择第一项 `codex_review`；DeepSeek / Claude 不得自审。
6. 路径冲突或执行器暂不可用时可在本轮继续检查下一行，但不修改顺序；明确逻辑阻塞必须先转状态并移出队列。
7. 队列为空时才读取分线 backlog 进行一次维护，本轮不执行新任务。
8. 选定真实对象后、读取实施细则前，调用 `tools.codex_app__set_thread_title`：`1` 为 `TZG｜<中文简述>`，`2` 为 `TZG｜复审：<中文简述>`。简述使用任务卡或复审事实源的中文标题；无候选或改名失败不阻断流程。
9. 命中审核、未审核、交接或复审路由时，按审核入口读取细则与相应事实源；普通执行任务按任务卡必查范围先定位、后读取，发现新依赖时补读，修改前读取目标完整逻辑单元。不得处理另一个 AI 主责的高风险任务，应写入交接请求。
10. 完成后按“验证成本控制”选择最小充分验证集并合并执行一次，只提交本轮文件；完成队列任务时同步更新同一任务卡、backlog 和 `当前任务队列.txt`。由 `tzg-hourly-controller` 启动的 Codex 执行、复审和队列维护统一使用 `tools/automation-finalize-commit.ps1 -RequireAutomationMetadata`；`CommitMessage` 只传单行标题，并以 `AutomationTask`、`AutomationState=completed`、`AutomationResult`、`AutomationImpact`、`AutomationVerify` 分别传入事实字段，finalizer 固定生成 `Automation: tzg-hourly-controller` 正文。

### 角色例外

- Codex / ChatGPT5.5 的 `1` 按队列顺序处理其主责执行型任务，不消费 `codex_review`；其自产工作完成必要验证后可闭环。
- Codex / ChatGPT5.5 的 `2` 按队列顺序处理第一项 `codex_review`；通过后按审核规则关闭，未通过则更新未通过清单。
- DeepSeek 的 `1` 只做其主责执行型任务；所有修改标为未审核，按外部两提交边界完成业务提交与交接提交。
- DeepSeek 的 `2` 不得复审自己；仅补齐交接材料、验证输出和请求复审范围。

## 冲突处理

用户当次明确指令 > `AGENTS.md` > `开发管理/` 当前状态 > `docs/` 原文 > BattleSim / Unity 实际代码。数值平衡结论必须有 BattleSim 运行结果；发现 docs、BattleSim、Unity 不一致时，先指出冲突并确定主事实源，再同步相关文件。
